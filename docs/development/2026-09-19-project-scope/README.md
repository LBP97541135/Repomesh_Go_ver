# 项目、仓库与 Issue 范围修复

2026-09-19。本地源码基线为 `9a34331` 加工作区原有修改；未覆盖原有环境、认证修复和插件移除工作。任务来源是用户要求制定计划并执行“项目包含仓库，先建项目、再选仓库、后建 Issue”的修复。[修复计划](../../plan/project-repository-scope-repair.md)记录实施顺序。

## 实际修改

- `frontend/`：项目列表和选中项目由壳层统一管理，按账号保存、验证偏好；无选择时进入项目管理。先创建空仓库项目，再通过项目 PATCH 明确接入仓库。仓库页只展示当前项目成员。项目、候选和 Issue 选项读取全部分页，加载失败显示错误。
- Issue 创建：用户明确勾选本次工作范围，固定 projectId、仓库集合、创建上下文修订、文本和幂等键；网络失败重试保持原请求。移除隐式建项目、选择首个项目／仓库和自动全选。工作台详情、任务、会话、拓扑和交付查询使用实际项目或计划身份，切换时隔离旧响应。
- `web/`：旧项目创建入口也改为先保存基本信息，再在项目设置中接入仓库。
- 后端：空仓库项目可保存，创建项目归入当前账号组织。Issue 选项核固定配置、用户读取、App 工作授权和运行时 App 密钥，分页不改变全局就绪结论；最终提交保留原有范围和事务校验。
- 发现与执行：候选池限定到 Issue 已选项目仓库，扫描画像按完整仓库 URL 与账号组织精确关联。审批和物化再校验范围，生成计划使用实际批准分档；审批变化后的旧计划不能物化。重规划不能突破 Issue 范围。
- 迁移 0042：增加 `plans.issue_id` 与 `task_repository_scopes`，规范仓库 ID 以复合外键约束项目成员关系、Issue 身份和 Issue 工作范围；触发器阻止绕过服务直接写越界任务或伪造绑定。调度及 coordinator 仅消费有合法 Issue 仓库绑定的任务。关联执行计划／任务的 Issue 可归档，清除返回冲突。
