# 先建立多仓库项目：页面与接口对齐

**历史入口记录，现行关系已替代（2026-09-09 修订）：** 本文保留项目先保存与 DESIGN-001 的确认过程。侧栏聊天、整条草稿转正、Issue 独占用户主会话等旧绑定已由 [ADR-0019](../../../../adr/0019-conversation-issue-separation.md)和[会话与独立 Issue 页面专题](../../../../current/conversation-issue-separation-design.md)替代。创建快照、默认新建／可选已有会话及具体 REST／Issue SSE 已按[创建契约](../../../../current/issue-page-create-api-contract.md)采用；首次消息或页面建项提交后的准备触发按 [ADR-0018 后续补充](../../../../adr/0018-provision-instance-after-first-draft.md)。本文链接的 `repomesh-project-first.html` 为拆分前历史原型，当前原型见新专题。

状态：保留已确认的项目入口顺序和准备期补充保障；下文旧聊天流程、接口建议和待确认项是当时记录，不作为当前创建契约。项目创建本身及会话消息的完整协议仍继续设计。

## 本轮用户要求

用户提供仓库多选创建窗口，明确“多仓库项目应该在一开始就建立”。因此首次使用应先从可参与仓库中选择项目范围、建立长期多仓项目，再在项目内输入需求；不能以默认已有项目掩盖创建入口，也不能把第一次需求输入同时解释成创建项目。

完整业务入口：建立多仓项目 → 在项目内输入需求 → 保存 Draft Issue 与首条消息 → 进入 Manager 主房间讨论 → 与 Manager 明确创建正式 Issue。已有项目直接复用，同一项目可接收多条草稿及正式 Issue。

长期项目先建立与首条草稿后准备实例现已分别确认：创建项目先保存资料，第一条 Draft Issue 与首条消息落库后异步准备／恢复项目实例，见 [ADR-0018](../../../../adr/0018-provision-instance-after-first-draft.md)。后端专项稿其余细节仍为 proposed，不把具体页面与接口一并冻结。

## 原型与页面

本节历史版本 [repomesh-project-first.html](../prototypes/repomesh-project-first.html) 从没有项目的状态开始，保留上一版深色风格。更早的草稿与房间版本也已收录到[页面原型目录](../prototypes/README.md)，原展示文件保留；两者均不再作为当前原型。用户截图只作为界面参考，不引入截图产品的业务规则。

1. 打开“创建多仓库项目”，展示搜索框、当前账号可参与的仓库及复选框，显示已选数量。未选仓库时不能继续，搜索与返回上一步保留选择；仓库列表刷新不能静默扩充已选范围。一个仓库也可组成项目，沿用既有单仓参与规则。
2. “继续”进入项目名称与用途页面，查看已选仓库及继承的配置引用；遵循 J1，不选分支、不在此重复输入模型密钥。原型中“继续”仅切换步骤，“创建项目”才保存项目。
3. 项目创建成功后出现在左侧项目分组，进入该项目的需求输入页。此时还没有任何 Draft Issue、正式 Issue 或 ChangeSet；也不以创建成功冒充实例／Manager Ready。
4. 首条需求发送后只出现草稿，展示实例与本次对话准备；首条消息为“已保存，待投递”，没有伪造 Manager 回复。准备期间可继续保存补充，每条显示独立投递状态。产品窗口外分别模拟就绪、逐条投递、结果未知／核查、Manager 接收及回复，以继续体验转正和仓库房间；这些不是要求用户手动操作的业务按钮。具体运行机制尚未实现。
5. 左侧“新建”可建立后续项目，切换项目保持事项归属。取消创建不会创建后台业务对象；提交后的超时不能当作取消未创建，仍需核查结果。

选择仓库后补充名称／用途的两步排版仍是界面提案。准备期间允许保存补充已于 2026-09-09 获用户采用，当前原型已启用；按钮文案与各状态的具体契约不随方向确认全部冻结。

## 权限及配置边界

沿用 [project-configuration-design.md](../../../../current/project-configuration-design.md) 的 J1—J3：账号访问能力、GitHub App 能力、项目接入范围和具体 Issue 影响范围分别核验。可参与但 App 授权不全的仓库可以在选择列表说明原因，不能冒充可执行；项目允许保存并表达待配置或部分受限，后续只涉及可用仓库的工作不因无关仓库失效而整体禁止。

名称、用途、明确仓库集合及配置引用形成项目资料；模型、环境、预算等配置核验与实例实际就绪分别表达。配置不足不删除已保存项目，也不能绕过后续对话或执行的必要条件。账号关联本身不授予 App 安装权；页面不隐式扩大安装范围。

原型使用已关联的示例账号；没有实现真实账号连接、App 安装、配置核验或预算查询。项目创建示例可保存含授权缺口的范围；后续示例工作只选择最多两个授权可用仓库，转正前明示，不能当作生产选仓逻辑。

## REST／SSE 影响（未冻结）

| 页面动作 | 拟议接口能力 | 必须表达的结果与异常 |
| --- | --- | --- |
| 搜索并选择仓库 | `GET /api/repository-options`，建议支持关键词与分页 | 当前用户可参与的仓库、稳定仓库身份及操作能力／缺失原因。分页与搜索不丢失此前选择，不能只按可变名称关联。 |
| 建立项目 | `POST /api/projects` | 提交名称、用途、明确仓库集合及配置引用，返回稳定项目身份、配置核验状态与逐仓限制。不得创建草稿或正式 Issue，也不得把结果定义为实例 Ready。 |
| 进入或恢复项目 | `GET /api/projects/{projectId}` 与项目列表 | 当前可见项目及归属、配置与限制。项目存在、配置可用与实例就绪分别表达。 |
| 项目内发送需求 | 沿用创建 Draft Issue 能力 | 必须已有稳定项目归属；首条消息与草稿按原设计保存。首条草稿落库后准备实例，具体就绪与投递契约另定。 |
| 异步变化 | 项目状态需要可查询快照；是否新增项目 SSE 订阅待定 | 若配置核验或运行准备异步变化，应表达真实状态，不能仅凭创建响应推断完成。原会话 SSE 契约本轮未冻结。 |

提交项目时重新核验当前权限及所选仓库的稳定身份；权限变化要区分“不再可读／可参与”和“仍可参与但执行授权不足”。不能静默丢弃所选仓库后创建一个范围不同的项目。前者需要用户重选或明确处理，后者按 J3 保存可说明的受限状态；具体返回码与原子保存范围后续对齐。

同一次项目创建使用稳定逻辑操作标识，避免重复点击或超时重试生成重复项目；结果未知先查询原操作。名称相同不等于同一个项目，名称唯一性及跨项目复用仓库规则不在本轮新增。搜索失败显示重试与保留选择，真正没有可参与仓库时引导检查账号／仓库访问；真实授权操作不由本原型执行。

### ADR-0018 的原型同步

已移除原型中的“启动时点待确认”说明。项目创建不设置准备或 Ready；首次草稿、首条消息及待办保存后，原型才展示异步准备。每条草稿单独模拟主房间就绪，项目 Manager 就绪不自动把同项目后续草稿标为可对话。已有实例可复用，但仍须取得本草稿实际房间的关联与就绪依据。消息投递、接收与处理继续以事实区分；原型按钮合并推进这些示例事件，不表示生产端可以推测成功。

本次仅对齐已采用时序及其页面状态，没有新增 REST 路径、字段、状态码或冻结 SSE；原型内部变量不构成接口定义。项目／会话快照与变化通知需要分别表达项目准备、Manager 可用、本条房间准备及消息投递事实，具体契约继续对齐。权限、配置或容量受限时按 ADR-0018 保留真实原因及原项目／草稿／操作归属；原型这轮仍只演示正常准备路径。

### DESIGN-001：准备期间追加消息（方向 accepted）

页面与后端第 1／3 轮对齐无分歧后，页面询问“是否采用‘准备期间允许保存补充，就绪后依序投递’？”，用户明确回复“采用”。决定证据与通信原文见 [页面通信日志](design-communication-page-log.md)。这是该方向的确认，不批准整个后端专项稿或 DESIGN-002。

准备期间保留输入框，补充保存到原草稿，成功后逐条显示“已保存，待投递”；不重复创建草稿、项目实例或主房间。首条与补充进入同一草稿的服务端保存顺序，实际 Manager 和本条房间就绪后依序尝试投递；就绪瞬间的新消息也不能插队。顺序不等于模型逐条处理／回复有序，也不承诺跨系统 exactly-once。

前序投递未知先核查，该草稿后续显示等待原因，不扩大为其他草稿的全局停发。准备失败保留已保存消息；保存失败保留输入，保存结果未知按原操作核查，不换键盲重试。保存及实际投递分别核验当前权限和适用限制；已保存不等于永久授权或保证可投递，读取历史也遵守当前权限。

代价是维护消息与待办、顺序、幂等和核查，并接受前序结果不明时后续等待。消息与投递待办一起持久化，拟沿用 `POST /api/draft-issues/{draftId}/messages`；REST 表达保存事实，快照／SSE 按证据表达待投递、传输接收及 Manager 接收。Ready、传输成功都不能单独推断 Manager 已理解补充。

具体路径／字段／状态码／事件／重放与排序算法仍未冻结；追加与转正竞争、内容快照覆盖到哪条消息、跨阶段路由及底层上下文承接另行设计。后来补充不能追认到先前转正依据。原型为继续后续演示，暂等全部消息模拟接收及回复后才显示转正入口，这不是新增产品转正规则。

## 原型检查

2026-09-09 DESIGN-001：已走查项目保存无事项、首条加两条准备期补充只形成一条草稿，三条各显示待投递且无 Manager 回复；房间就绪不改变接收状态。模拟第一条结果未知时后续等待，就绪后追加第四条也不插队；核查后按 2、3、4 顺序投递，传输成功仍显示 Manager 接收待确认，模拟接收回复后再更新。第二条草稿仍独立等待房间，切回第一条保留消息及状态。等待页 1024／736／360 像素无横向溢出。唯一控制台资源错误为预览 favicon.ico 404，未发现脚本运行异常。仅内存演示，未验证真实保存失败、权限撤销、持久化、队列幂等和 SSE；这些场景继续细化。

ADR-0018 同步后补查：项目保存仍无事项；首条草稿显示实例准备且无 Manager 回复或转正入口；模拟取得就绪及回复后才能继续转正；同项目第二条草稿保留独立房间准备状态，不因第一个房间就绪而误判已接收。原先已就绪房间切换回来状态保留。等待视图在 1024／736／360 像素视口检查无横向溢出，浏览器无控制台错误或警告。

已走查空选择限制、跨搜索保留多选、名称／用途校验、返回上一步保留内容、含授权缺口的三仓项目保存、创建项目不产生事项、随后保存草稿且不伪造 Manager 接收，以及就绪演示后明确转正只关联可用仓库。取消创建保持项目数不变；第二个项目与第一个项目的事项分别归属；单仓项目可完成示例流程。1024／736／360 像素视口下选仓页没有横向溢出，360 像素下名称／用途页亦检查通过。修复了预览不提供的图标引用，最终浏览器无控制台错误或警告。全部是内存原型检查，不代表后端实现或权限验收。
