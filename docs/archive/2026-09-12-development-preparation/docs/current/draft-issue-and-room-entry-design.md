## 场景与理由

### 输入需求 → 草稿主房间

默认从简洁的新建对话页开始。输入框上方选择长期多仓项目，侧栏展开项目下的草稿和正式 Issue，草稿有单独标记。已有正式事项显示标题和最近时间，进入后才展开编号及状态。

首次发送后保存需求草稿及首条消息，进入 Manager 主房间。首次发送不是正式 Issue 创建动作，不出现主 ChangeSet、正式计划或工作执行。这样用户可先讨论目标，不会把一次想法输入解释成执行意图。

原型中的 Manager 回复为预设示意。正式服务应分别表达消息保存、投递、Manager 接收与回复；实例未就绪不能显示 Manager 已接收。

### 明确创建 → 正式 Issue

原型用主对话中的“与 Manager 明确创建 Issue”按钮表达明确意图，保留继续补充的输入框。点击时加入用户的明确创建消息，再展示 Manager 的创建结果。普通补充消息不会自动创建 Issue。

成功后保留当前可见会话，侧栏同一事项从草稿标记切换为正式事项，显示正式编号、状态及任务／验证／历史入口。草稿身份与正式 Issue 建立明确关联。是否复用底层 room／session 标识、如何承接草稿上下文仍待设计，原型只展示连续的用户体验。

“明确创建”是用户本次要求的事项边界，不是重新引入计划批准或开工审批。正式流程继续遵循当前 YOLO、权限及验收规则。

### Manager 开启仓库房间 → 引导进入

主房间出现“仓库房间已开启”的轻量引导，列出仓库、Leader／Worker 和活动状态。只对实际已关联、Ready 且当前用户可读的房间提供进入动作；准备中或失败不能伪装成可进入。

进入后保留 Issue 上下文，显示 Leader／Worker 协作记录及本仓工作环境，底部给出返回 Manager 补充要求的入口。顶层“仓库房间”可重新找到所有关联房间，避免引导消息被后续对话淹没。

原型在明确创建后直接跳到“计划与两个仓库房间已就绪”的模拟状态，以便连续体验。它不表示创建接口同步完成规划、启动、派工或房间准备；正式 UI 必须等待各自事实。

## REST、SSE 与状态草案

以下是页面交互的拟议契约，不是已采用的路径、字段或完整 API 规范。

| 场景 | REST／SSE 草案 | 状态和一致性 |
| --- | --- | --- |
| 左侧项目与事项 | `GET /api/projects`，`GET /api/projects/{projectId}/inbox` | 仅返回当前可见项目和事项，区分草稿与正式 Issue；分组归属不来自 UI 猜测。 |
| 首次发送 | `POST /api/projects/{projectId}/draft-issues` | 保存 Draft Issue 与首条消息，返回草稿身份及主房间准备状态；不建立正式 Issue／主 ChangeSet／执行任务。需要后续投递时遵循业务与待办同事务。 |
| 主房间快照 | `GET /api/conversations/{conversationId}` | 返回业务归属、房间准备状态、当前修订、消息及权限；业务对象身份与上游会话身份分开。 |
| 草稿补充 | `POST /api/draft-issues/{draftId}/messages` | 已保存、待投递、已接收和已处理分别表达，不能通过普通发送隐式转正。 |
| 明确创建 | `POST /api/draft-issues/{draftId}/formalizations` | 核验明确创建意图、项目权限、所见草稿修订及幂等键；正式 Issue、主 ChangeSet、后续待办同事务保存，草稿关联转正结果。 |
| 正式事项补充 | `POST /api/issues/{issueId}/messages` | 沿用正式事项归属；消息保存不表示计划已更新或生效。 |
| 变化订阅 | `GET /api/conversations/{conversationId}/events`，SSE | 房间消息、转正结果、仓库房间准备及权限变化通知。以 REST 快照校准；事件可重放与游标契约待细化。 |
| 查看仓库房间 | `GET /api/issues/{issueId}/repository-rooms` 与具体房间读取 | 后端核验 Issue、房间、仓库关联和当前读取权限；上游管理凭据不交给浏览器。 |

草稿草案状态：已保存／讨论中／转正处理中／已关联正式 Issue。房间准备状态单独表达；不能将“草稿已存”解释为“Manager 就绪”。正式 Issue 状态继续与执行、验证和交付状态区分。

## 权限与异常

- 草稿创建、继续讨论和正式创建各自重新核验当前项目权限；仓库范围继续受项目边界和发起人有效授权限制。草稿不授予执行权限。
- 同一逻辑创建沿用同一幂等键；重复提交应返回同一转正结果，同键不同内容拒绝。一个草稿已转正后不可重复产生另一条正式 Issue。
- 转正时草稿修订已变化：返回冲突并展示最新内容，不能把对旧内容的明确意图套到新内容上。HTTP 超时先按原操作标识核查，不能换标识重建。
- 主房间尚未就绪：草稿保存结果仍可见，说明准备／投递状态。准备失败保留需求，给核查或重试入口；不冒充 Manager 已回应。
- 仓库房间失败或尚未关联：显示原因和准备状态；只有实际 Ready 的房间有进入动作。
- SSE 断开显示同步中断，重连后补查缺口；旧快照不应继续显示为实时。重复和乱序事件不能重复创建 UI 事项或改变已核验的归属。
- 权限撤销后，REST 与 SSE 都核验当前权限；读取权限丢失时移除不可见正文，不能仅禁用发送按钮。仓库写权限失效与读权限失效分别处理。

上述异常目前为契约讨论，不宣称原型实现了真实权限、持久化幂等或事件重放。

## 与现有架构的衔接

后端侧已收到本轮更新，细化见[后端讨论稿](../../../../current/draft-conversation-backend-design.md)。首条草稿后准备实例已按 [ADR-0018](../../../../adr/0018-provision-instance-after-first-draft.md) 采用，业务会话身份、底层上下文承接和转正并发的其余方案仍待确认。

页面侧此前建议“首次草稿和首条消息持久化后，异步准备／恢复项目实例”，用户随后已采用，见 ADR-0018。理由是由真实项目 Manager 从头承接，代价是正式创建 Issue 前可能已有资源及模型消耗，首次对话也可能等待准备。

页面配套提案：发送成功后显示“草稿已保存”，进入主房间页面；消息显示“已保存，待投递”，房间单独展示准备、等待资源或准备受阻及原因。实际房间和 Manager 就绪后再投递，消息接收／处理状态由对应证据更新。准备失败保留草稿与消息，核查原操作后继续，不要求用户重新创建草稿。页面可见、进程已启动、实际房间 Ready、Manager 已处理分别表达。当前权限、配置和容量约束继续适用，草稿期不授予正式执行权限。

实例准备时点已确认。稳定业务会话身份与底层上下文承接、转正唯一性与内容修订、消息竞态仍待逐项对齐；具体 REST 路径、返回码和 SSE 契约未冻结。现有本地模拟不构成实际就绪与投递能力的验收。

本次用户要求明确替代 ADR-0001 等文档中“首次输入即正式 Issue”的入口部分。ADR-0016 的业务／待办同事务原则、正式 Issue／主 ChangeSet 归属仍成立，只是正式创建触发点后移。

旧原型用已配置且 Manager 就绪的项目示例；最新项目入口原型另示意草稿已保存但对话未就绪。产品按 ADR-0018 在首条草稿落库后准备实例，不能从这些模拟推导上游草稿存储或上下文恢复能力已实现。

## 评审与检查边界

原型支持新建草稿、追加讨论、明确转正、按项目查看事项、搜索、查看仓库房间、返回 Manager、任务详情、验证证据和历史。全部数据为内存模拟，刷新重置。未改生产业务代码，未安装、部署、写远端或创建真实任务。

已用浏览器走查：首次发送产生草稿、普通补充不转正、明确创建后显示正式编号且不再保留重复创建入口、仓库房间只读及返回、任务节点详情、验证证据展开、历史和跨项目事项切换。1024／736／360 像素视口下检查主房间，无横向溢出；浏览器无控制台错误。该检查不等于后端幂等或产品验收。
