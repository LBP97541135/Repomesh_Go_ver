# 项目管理契约检查

日期：2026-09-12。范围是首批项目创建、编辑、配置引用、查询与恢复，以及它们与认证、模型应用、Issue 创建的衔接。依据当前工作树中的现有设计核对，不以旧 HEAD 代替尚未提交的现行文档。

结论：项目归属、增仓、事务、幂等及原操作恢复的主体规则已覆盖，可以支持已确定的独立管理单元开发。文档存在四类可直接修正的不一致，已在本次修订。另有两处读取字段缺口，需要继续补齐候选，不能将首批完整配置摘要和模型替换预览标为已可验收。

本次不新增产品字段、端点或采用决定。已采用的 RM-API-01 r3 保持；认证、模型、配置来源、恢复及 P9 仍按各自具体候选范围判断。产品仍是工程骨架，没有业务实现或运行验证。

## C01 旧认证内部步骤与后续候选冲突

原[身份内部稿](../../current/backend-first-development-access-draft.md) §3.4 写“撤销服务端会话／该浏览器未完尝试后清Cookie”，§3.2 也未限制注销的绑定代次。若旧注销响应在新登录后到达，删除 Cookie 的响应头会清掉新会话凭据；撤销全部浏览器尝试也会影响新一代登录。

[认证候选 §4](../../current/authentication-browser-api-draft.md#4-回调与本地事务)及[首批总包 A4](../../current/first-batch-complete-review.md)已规定只影响请求 session 及其绑定代次，注销不发送删除 Cookie 头。本次据此同步旧稿，补入迟到注销验收。回调步骤同时沿后续候选改为先到固定 resultPage，再核原尝试与当前身份，由用户明确继续。

这是候选之间的同步，不是采用认证方案。内部会话记录、连接刷新互斥和原有责任保留。

## C02 无变更配置保存的修订语义

[项目浏览器契约 §5](../../current/first-batch-browser-api-contract.md#5-配置引用与固定版本)原文写显式配置 PATCH 后“随后改变 projectRevision／creationContextRevision”；同文 §7 允许无实际变化不提升修订。[持久化 §2.4](../../current/backend-first-batch-persistence.md#24-项目创建更新与配置版本)也允许无变化保存，但前句无条件写“分配configurationRevision”。

场景是默认、profile、secret、配置选择及有效参数都没变，用户仍显式保存原配置。按无条件升修订实现会使其他窗口的创建条件或编辑修订过期。

本次统一为先重新解析；配置选择、固定版本或有效值实际变化才产生对应修订，完全无变化保留原修订，仍保存该操作成功回执。此规则来自既有无变更保存设计，不新增接口字段。已在主契约验收清单增加对应场景。

## C03 后续候选未回链到主要阅读入口

项目主契约和模型专题仍有“协议未完成”“待字段落盘”的笼统描述。后续已经形成认证、模型保存／测试／应用、配置来源及恢复候选。开发者只读旧入口时，无法判断哪些需要新设计，哪些只待采用和实现。

本次在[主契约](../../current/first-batch-browser-api-contract.md#采用范围与后续候选)加入来源表，修正[项目专题](../../current/project-configuration-design.md)、[模型设置](../../current/model-connection-settings-design.md)和[模型应用](../../current/model-project-apply-design.md)的相关描述。完整 configuration PATCH 仍重解析两引用，专用模型应用仍是独立候选；P9 仍是内部配置绑定候选。

这些导航只指向唯一来源，不复制第二套 JSON，也不将完整模型运行路由、真实权限或高级页面标为已完成。

## C05 项目预算和时限缺少只读响应

状态：待补设计。

[项目配置 J1](../../current/project-configuration-design.md#j1项目接入与最小配置已确认)要求显示实际采用的预算和时限。[项目契约 §5](../../current/first-batch-browser-api-contract.md#5-配置引用与固定版本)只返回 budgetPolicyId／timeLimitPolicyId；configuration-profiles 只有 ID、名称和可用性。前端取得两个不透明 ID 后，不能显示上限、单位、周期或时限数值。

[来源候选](../../current/backend-first-batch-sources-draft.md)已有内部配置和账本，但明确不是浏览器响应。模型测试预览只属于单次测试，不能当作项目执行配置。

建议优先评估在现有项目 GET 的只读配置中补固定参数摘要，避免页面遍历内部策略记录。补案必须明确：

- 数据对应哪一条 configurationRevision，预算的计量单位、限额与周期，以及时限数值。
- 固定配置上限与当前额度、预留或资格观察的区别，以及各自未知时的表达。
- 当前主体对摘要的读取资格；不能用内部导入清单或前端硬编码默认值补齐。
- 默认配置更新后，旧项目仍显示原固定版本的参数；未知不显示为 0 或无限。

这是最小只读契约补齐，不要求实现完整 F06 编辑页，也不直接采用 S05 的候选次数或金额方案。具体字段及是否使用专用 GET 尚未确定，本次仅把缺口回链到主契约和交接。

## C06 应用预览缺少原模型的完整形状

状态：待补设计。

[模型候选 §5](../../current/model-settings-browser-api-draft.md#5-仅更换模型预览与原子应用)中的 before.model 只有 reference、profileId 和 snapshotId，null 仅表示原未配置。§5.1 又要求原模型不可披露时给受限标记，但未定义该标记的机器形状。

同节历史读取需要 providerId 和 providerRevision；原模型只给 snapshotId，没有 providerId，也没有已定义的固定来源解析接口。因此前端无法按已采用的[F04 呈现要求](../../current/model-project-apply-design.md)可靠展示替换前模型，只能猜字段、查最新版本或遍历供应商反查。

建议在模型浏览器候选中统一补齐可读、未配置、受限的形状。可读分支须给出能定位原供应商、固定版本及模型行的依据；受限分支不得泄露来源名称或 ID。权限未知沿当前共用 503 规则，若改变表达须在候选中明确替代关系。替换前模型受限不能单独禁止有权的配置修复，原 execution 的固定版本要求保持。

候选验收需覆盖原模型未配置、来源受限、当前权限未知、供应商后来产生新版本，以及精确保留 execution 的应用。新增字段仍须在唯一候选中编制并按具体范围采用，不能由本次检查直接加入已采用的项目 JSON。

## 已覆盖的主体规则

| 规则 | 核对结果 |
| --- | --- |
| owner、GitHub 用户读权与 App 工作能力 | 分开定义，同仓协作者不会自动取得项目资格。 |
| 创建待配置项目 | 所选范围读权须核实，App、模型或环境不足可受限保存。 |
| 项目编辑与明确增仓 | 保留原范围，只核真正新增范围；新增失败整次回滚。 |
| 创建、更新与 Issue 操作身份 | 作用域隔离；唯一约束及业务、原输入、回执同事务。 |
| 原操作恢复 | 原成功重放优先于新修订校验，404仍未知，410不复活。 |
| 固定配置与模型应用 | 资料或加仓不暗换配置，完整 PATCH 与专用模型应用不同。 |
| 列表与内容权限 | Issue、会话按完整内容范围核权，未知返回503；游标不授予权限。 |
| Issue 配置绑定与后续执行 | P9 已明确为候选前置；绑定落库和实际配置消费分别验证，G1—G5不冒称完成。 |

## 检查方法与证据边界

主检查覆盖项目浏览器契约、项目和模型页面专题、恢复与字段依赖。两个只读检查分别核对持久化与 Issue 衔接、认证与模型／来源衔接，主检查者逐条核对原文后统一修订。子代理没有编辑文件。修改后的结构检查结果见[检查结果](structural-checks.json)，与修订前工作树的对照见[任务内差异](changes.diff)。采用状态、设计版本、实现状态和JSON示例均与基线一致，见[范围检查](scope-checks.json)。非主要修订者已独立比对任务内差异、唯一契约及 CP16 原始回执，复核通过。未发现新增实质矛盾或超范围采用；C05、C06 的缺口及候选边界得到确认。

[修订前文件校验值](source-baseline.json)记录本次工作树基线，不覆盖此前审查报告或实验结果。历史记录只用于核实具体采用与技术回执，不恢复历史授权。结构检查覆盖本次修改的 Markdown 本地链接、新增锚点、JSON 示例和差异；它不能证明 HTTP、OAuth、PostgreSQL 并发或模型调用正确。

结构检查通过 11 份 Markdown、196 个本地链接、20 个新增章节锚点和 16 段 JSON 示例；本次范围的 git diff --check 通过。JSON 只检查语法，新增锚点按规范化标题核对；远程 URL 未检查。

本次没有修改业务代码、运行 Go／前端构建、启动服务、访问真实账号／模型，或重跑历史实验。根 README 的使用方式和产品完成度没有改变。

尚未收口的候选采用、C05、C06 及真实故障验收保留为后续工作；这份检查不能替代它们。
