# ADR-0016：业务记录与后台待办同事务保存

> 入口替代（2026-09-09）：按 [ADR-0019](0019-conversation-issue-separation.md)，会话与 Issue 分离，一个会话可明确建立多个独立事项。本文“正式提交”指建立某条正式 Issue，不再指整条会话转正或首次聊天。Issue、主 ChangeSet 与对应待办同事务的决定继续有效；2026-09-09 P1 已将 Issue 栏默认新会话的业务会话、来源关联及真实页面创建记录纳入原子范围，见下节补充；持续设计授权随后补齐双入口、输入快照与幂等结果范围，见“持续设计授权补充”；具体数据库实现继续设计／待验证。同一会话可以有多个独立创建操作，各操作自身仍须幂等。

RepoMesh 将需要后台继续处理的业务变更及对应持久待办，在同一个 PostgreSQL 事务中保存。后台在事务提交后领取待办、核验当前状态、执行外部操作并保存结果，避免业务已登记而后台工作因进程重启被遗漏。

本决定落实 [ADR-0010](0010-technology-stack-and-modular-monolith.md) 的 PostgreSQL 持久队列方向及 [ADR-0013](0013-web-coordinator-host-executor-processes.md) 的 Web／后台职责，不改变既定业务归属、权限与幂等规则。

## 已采用的行为

以正式提交“增加支付状态筛选”为例：

~~~text
必要配置与权限核验
        |
一个数据库事务
  +-- 保存 Issue
  +-- 保存主 ChangeSet
  +-- 保存继续处理该需求的后台待办
        |
事务提交成功，返回稳定归属及当前准备状态
        |
后台领取待办 -> 核验实际状态与约束 -> 执行 -> 保存结果
~~~

上述记录一起提交，失败则一起不生效。提交成功表示正式需求已可靠登记，实例是否 Ready、房间是否建立及实际执行进展分别展示。[ADR-0018](0018-provision-instance-after-first-draft.md) 原把实例准备提前到第一条 Draft Issue 与首条消息持久化之后；ADR-0019 分离会话与事项后，该触发曾待适配；现按 ADR-0018 的持续授权补充，首次会话消息或页面建项提交后异步准备。项目创建只保存资料、不立即启动实例，本 ADR 的正式 Issue 建立事务和持久待办原则继续有效。

待办持久保存在数据库，不依赖一次内存通知。事务提交后即使后台重启，恢复时仍可发现未完成待办；执行前核验当前有效权限、目标版本和其他适用约束，持久待办本身不代表永久执行授权。

调用 AgentTeams 等外部能力放在事务提交后，数据库事务和锁不跨越外部请求的长时间等待。如果请求已发出但尚未保存结果就超时或重启，先核查外部实际状态，按原逻辑操作标识和归属继续处理，不盲目重建房间、实例或其他资源。无法判定时保留未知结果及恢复记录，不写成成功。

## 2026-09-09 补充：Issue 栏默认新会话的原子范围（P1 已确认）

本补充适用于用户从 Issue 栏创建、默认新建业务会话的场景。在原 Issue、默认主 ChangeSet 与对应后台待办的本地短事务中，同时保存新业务会话、该会话与 Issue 的来源关联，以及标明真实页面来源的创建记录。

~~~text
同一个本地短事务
  +-- 独立 Issue
  +-- 默认主 ChangeSet
  +-- 新业务会话
  +-- 会话与 Issue 的来源关联
  +-- 真实页面创建记录
  +-- 既有后续持久待办
        |
一起提交成功，或一起不生效
~~~

成功时可可靠返回 Issue、主 ChangeSet、业务会话三种稳定身份及真实关联；不会把“事项已建、来源会话未建”当作这次本地提交的成功结果。确定事务失败时不留下半套业务记录。请求超时、断连或取消等待并不证明事务失败，仍查询原操作；提交后的运行关联恢复失败也不能成为删除已提交业务事实的理由。

该范围只包括业务会话记录，不把实际 Matrix 房间、Agent session、模型调用、实例准备或其他外部动作拉入数据库事务。新会话保存不代表 runtime Ready 或实际执行开始，不改变当前权限核验、YOLO、预算和已有幂等核查保障。

本次 P1 单项确认选择一起保存，避免分步保存带来的“事项已建、会话未建”中间状态和补齐流程；代价是扩大本地事务及关联维护。当时输入快照的具体内容、幂等存储字段与保留、会话命名、启动触发、SSE、Manager MCP 和可选已有会话能力并未同时决定，URL／HTTP schema 也没有冻结；这些后续选择另据以下持续授权落实，不倒填为 P1 的确认。

## 2026-09-09 持续设计授权补充：双入口、快照、幂等与持久事件

用户授权“之后的待决定都批准，按照建议来。”后，按[采用清单](../current/design-delegation.md)落实共同推荐。页面表单与项目 Manager 的受控创建 MCP 使用同一业务创建及结果查询逻辑；可信调用身份和来源分别绑定，不由模型自报权限。页面默认新会话，也可明确选择同项目有权的已有会话；选择失效返回错误，不静默换成新会话或其他目标。

正式创建的短事务同时保存：

- 独立 Issue、默认主 ChangeSet。
- 必要的新业务会话；选择已有会话时保留原身份与历史，只增加本次关联及记录。
- 来源会话关联、真实页面或 Manager 创建记录、允许字段的确切输入快照、规范化摘要及版本、可信操作者与来源依据。
- 逻辑创建操作的幂等结果、对应后续持久待办。
- 随本次可见业务事实变化产生的持久事件记录。

所有必要记录一起成功或一起不生效。页面来源不得伪造成用户消息，Manager 来源须引用真实用户消息和明确创建意图；不保存认证凭据、密钥或模型隐藏推理。快照与规范化的具体允许字段以[创建接口契约](../current/issue-page-create-api-contract.md)为准，不把任意请求正文当作可留存内容。

操作身份在项目保留期内不复用。删除业务正文后保留不含正文的最小幂等占位，旧请求不能重建原事项；物理删除项目后旧身份不可复活。占位不提供历史正文读取权限，也不因缺少正文就放行原键为新操作；确切数据库字段、索引和清理实现继续设计。

Issue 详情采用 SSE 失效通知与 REST 快照。业务变更或本地运行观察提交时，将对应事件一并持久记录，提交后发布；不能退化为仅一次内存广播。重连使用范围绑定游标，无法重放时要求重取快照；事件发送和读取按当前权限核验。事件记录保证可恢复的通知依据，不保证模型执行、客户端已读或跨系统 exactly-once。契约采用默认事件保留 24 小时、15 秒注释心跳，作为可调整运行参数；过期仍完整补查，实际性能及恢复待验证。

按 ADR-0018 新补充，首次会话消息或页面创建提交后自动异步接续准备；外部权限核查、实例／房间操作、模型调用仍不占用该数据库事务。事务提交不等待运行就绪，准备失败保留业务事实和原操作；当前权限、预算、计划与资源限制继续有效。

此补充减少双入口行为差异、结果丢失及短缓存过期导致的重复创建，代价是关联、输入版本、幂等占位与事件维护。采用的是设计基线，不是生产实现或已验证的运行保证。

## 原因与代价

若先保存 Issue，再仅靠一次进程内调用唤醒后台，两步之间的崩溃可能留下没有后续处理记录的需求。同事务保存把业务事实与继续处理的责任一起登记，关闭这一遗漏窗口。

代价是需要维护待办的领取、执行结果、重试和恢复核查。该事务只保证本地业务记录与待办的一致提交，不让数据库与 AgentTeams、GitHub 或容器操作成为跨系统原子事务，也不承诺外部动作只执行一次或需求最终一定完成。

## 待细化边界

队列库、直接事务入队或事务内待发送记录的具体方式、表与字段、领取机制、重试次数及退避、超时和人工运维恢复入口尚未确定。若队列库不能加入业务事务，仍须用同事务持久记录承接待办，再可靠转交；不能退化为提交后仅发一次通知。

本决定不冻结 Worker／Attempt 与容量的原子占用算法、完整事件运行参数或整套恢复状态机。当前仅设计及本地 Markdown 记录，不编码或部署；YOLO 和 Skill 工程暂缓边界不变。
