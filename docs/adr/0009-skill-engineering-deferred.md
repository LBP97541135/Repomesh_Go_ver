# ADR-0009：Skill 工程预留设计与暂缓开发

**模块状态：待定／占位，暂不开发。** 用户已同意 H1—H15 的设计方向，并明确要求先记入新 ADR、为 Skill 工程保留位置。`accepted` 表示这些设计方向已获同意；`implementation: deferred` 表示模块尚未进入开发，后续何时启动及实施范围仍待另行确定。

当前只保留设计文档、术语和关联入口。不因本 ADR 启动 Skill 管理、发布评估、分发加载、版本隔离、运行时适配或相关页面的开发，也不安装或部署组件。H1—H15 是后续恢复该模块设计和实施时的依据，不是当前已经可用的产品能力。

## 背景与取舍

RepoMesh 使用长期 Manager、Leader 和可复用 Worker，同时要求各 Issue 的执行依据独立、可追溯。AgentTeams 已有成员 Skill 分配、对象存储分发及 QwenPaw 刷新机制，但这些主要作用于成员工作区，不能据此证明按 Issue 固定版本已实现。

采用“独立维护可复用 Skill、按角色组合能力、每条 Issue 引用确定版本并附本次工作说明”，接受版本管理、场景评估和实际加载核对的额外成本，以避免一次性任务修改长期公共流程，或公共 Skill 更新静默改变其他 Issue 的执行依据。平台／项目维护归属与角色使用组合分别表达。

沿用 [ADR-0006](0006-manager-entry-modes-and-skill-driven-execution.md) 的 Skill、计划和 RepoMesh 执行职责，[ADR-0003](0003-plan-change-authorization-and-activation.md) 的计划许可与生效，以及 [CS4](../current/changeset-design.md) 的验证上下文变化规则。术语仅在 [CONTEXT.md](../../CONTEXT.md) 定义；场景和锁定源码依据见 [Skill 工程专题](../current/skill-engineering-design.md)。

## H1—H15：已同意、待实施的设计

下表整体处于上述待定／占位状态，当前不开发。

| 编号 | 主题 | 已同意的设计方向 |
| --- | --- | --- |
| H1 | 工程组织 | 独立维护可复用 Skill，按角色组合能力，每条 Issue 引用确定版本并附本次工作说明。Manager 将说明落实到具体计划；一次性要求不直接改写长期公共 Skill。 |
| H2 | 编写、维护与发布职责 | Agent 可以起草、改进和验证；项目管理员或获得 Skill 发布权限的人发布项目版本。长期 Skill 发布不阻塞当前 YOLO Issue，不因此增加逐项人工执行门禁。 |
| H3 | 平台、项目与仓库归属 | 平台提供通用版本，项目明确选用；项目可维护自己的派生版本并保留来源。仓库专用内容归属项目，标明适用仓库，由对应 Leader 提供改进。 |
| H4 | 临时能力补充 | Agent 可以在本次授权、预算及执行范围内编写工作说明和辅助脚本，保留来源与结果；沉淀为长期 Skill 时走发布流程。需要新权限或环境能力时按既有受限规则处理。 |
| H5 | Skill 内容 | 至少说明用途、适用条件、输入、步骤、输出、证据要求、工具及环境依赖、失败处理。脚本和参考资料随同版本保存；具体字段及文件格式后续确定。 |
| H6 | 发布前评估 | 检查内容完整性、依赖和脚本，在隔离环境执行代表性场景，覆盖成功、业务失败和前提缺失并保存评估结果。格式正确或安装成功不能单独作为可用依据。 |
| H7 | 依赖、同名及冲突 | 明确记录来源和依赖版本；同名内容不静默覆盖。出现冲突时先明确适用范围和采用依据，不能用后加载者优先改变职责、权限或验收边界。 |
| H8 | 能力组合与分配 | Manager 统筹，Leader／验证负责人按任务提出能力需求，RepoMesh 核验并实际分配。上游 `assign_when` 作为匹配提示，记录最终选择的 Skill 及版本。 |
| H9 | Issue 变体与长期复用 | 本次参数、业务解释和特殊步骤留在事项工作说明；形成可重复使用的方法后提出长期 Skill 改进。出现多次只是改进线索，不自动触发发布。 |
| H10 | 新版本选用与在途升级 | 发布先使版本可选，项目另行决定是否作为后续 Issue 的默认版本。已有 Issue 继续引用原版；升级时说明差异与影响，按现行计划许可、生效和证据规则处理。 |
| H11 | 同成员的多 Issue 版本使用 | 按 Issue 保存确定版本引用及可取得的内容，避免覆盖公共同名目录来切换流程。运行时须验证实际使用版本；不能保证并存时，在受影响工作收敛前不切换，不因此复制新的 Manager 身份。 |
| H12 | 分发、加载或升级失败 | 分别记录配置、文件分发和实际加载结果。只有旧版仍符合当前计划且内容已核实时才继续使用；否则暂停依赖该能力的新工作并报告原因，不把已上传显示成已生效。 |
| H13 | 第三方 Skill | 可以导入为待评估内容，记录来源、确定版本及完整内容，经过项目发布流程后选用。Agent 不自行安装未知依赖或扩大权限；首期不把 Nacos 或某个外部市场设为必需组件。 |
| H14 | 缺陷版本停用与回退 | 标记该版本不再供新工作选用，定位受影响 Issue，由 Manager 判断影响并处理；已有使用记录保留。回退也属于明确的版本调整，不静默替换在途依据。 |
| H15 | 效果、历史与清理 | 记录各版本被哪些 Issue／Attempt 使用、评估结果及失败反馈。被执行或验收引用的版本内容保持可追溯；临时材料可按策略清理，不因一次任务失败就直接判 Skill 有缺陷。 |

## 与既有执行规则的关系

- Skill、角色能力组合及事项工作说明不替代有效计划、授权、预算、独立验证和证据门槛；RepoMesh 实际控制执行。
- 人控制长期项目版本发布，不意味着当前 YOLO Issue 需要等待该发布。当前工作仍只能在实际具备的能力、授权和计划内推进；不具备必要能力时如实返回受限或未完成结果。
- 发布为可选版本、设为后续 Issue 的默认版本、在途 Issue 采用新版本和运行时实际加载分别处理。发布或加载成功不自动使计划生效，也不表示业务验证通过。
- H11、H12 涉及计划应用和派工暂停时，仍遵守 ADR-0003 的受影响上游 Project 收敛边界；不将业务依赖范围误写成上游已支持局部暂停。
- 同一代码组合采用新 Skill 等验证上下文时，按 CS4 新增相应验证记录并重新判断证据适用性；历史版本、结果和更正保留关联。
- 本 ADR 的工程暂缓不撤销既有职责、权限和验收要求，也不把尚未实现的 Skill 能力写成其他模块已经具备的运行前提。

## 支付状态筛选示例

某 Issue 使用页面验证 Skill v1.3，当前计划约定筛选、清除条件及分页检查。验证 Worker 发现可复用的分页检查方法需要改进，可以在本次有效范围内补充辅助脚本和证据，并提出长期 Skill 修订。

本条 Issue 继续按其有效计划和确定依据处理，长期版本发布另记。v1.4 经评估并由有发布权限的人发布后，先成为项目可选版本；后续默认版本和在途升级按 H10 分别决定。若同一长期 Leader 还服务另一条使用 v1.3 的 Issue，不能通过覆盖公共同名 Skill 使其静默切换。

以上是模块恢复实施后的目标场景，不代表目前已存在这些页面、记录接口或运行能力。

## 决定来源

用户先确认 H1。随后要求集中列出 Skill 工程剩余问题，在收到 H2—H15 及建议后回复：“同意，你先把决策写写入新的adr文档，但是skill这一块标记为待定（就是先不开发，但是占位置）”。因此本 ADR 保存全部设计方向，同时明确整个 Skill 工程暂缓开发；后续启动时间和实施范围另行确定。
