# ADR-0003：计划变更的自动化档位、许可与生效

RepoMesh 的跨仓 issue 需要根据执行证据调整计划，同时保留人工控制、执行归属和可追溯性。用户确认：Manager 随时可以提出计划变更，RepoMesh 判断是否获准，并在执行条件满足后应用；批准成功与计划生效分别记录。

本决定沿用 [ADR-0001](0001-agentteams-issue-concurrency-and-isolation.md) 的长期团队、issue 会话、独立 Attempt、容量约束和暂停语义，以及 [ADR-0002](0002-github-app-authorization-and-draft-pr-delivery.md) 的 Git 授权与人工合并边界。`accepted` 表示以下产品规则已经确认，不表示接口接入、审批强制约束或部署验证已经完成。

Manager 统一交互和 YOLO 无人工门禁采用 [ADR-0006](0006-manager-entry-modes-and-skill-driven-execution.md)；2026-09-08 用户确定当前阶段统一全自动，首次计划及后续调整均不等待人工批准，审批能力后续开发。用户随后确认后续审批模式的首版计划、审批人、项目默认及 Issue 覆盖、运行中切换和允许模式范围变化的规则，见第 1.7—1.11 节；这不改变当前 YOLO 范围或启动开发。计划版本、许可与生效规则继续有效。

## 1. 已确认的计划规则

### 1.1 审批对象是明确的计划版本

- 计划变更展示新增、删除和修改的工作、原因、依赖变化、仓库范围、预算及循环上限。
- 已批准的业务计划版本保持不变，修改目标、范围或约束等产生新版本；保留变更与其所依据版本的关系。按 [ADR-0015](0015-round-scoped-upstream-dags.md)，已有获准范围与上限内推进下一轮属于执行进展，上游任务安排的更新另记，不因此新建业务 Plan Version。
- Manager 提出变更不自动使新版本成为当前执行依据。

### 1.2 两个自动化档位共用执行规则

| 档位 | 计划变更如何获准 | 执行边界 |
| --- | --- | --- |
| 全自动（YOLO） | 按当前授权、预算和策略自动判断，不弹审批、不等待人同意。 | 获准后仍需满足应用条件；触及权限、预算或已明确验收条件边界时返回受限或未完成结果。 |
| 需要审批 | Manager 在当前会话展示具体版本、变更及影响，由有权用户决定。 | 获准后采用同一套应用与执行规则；Agent 内部检查不逐项请求用户批准。 |

YOLO 不自行扩大权限、提高预算上限或放宽已明确验收条件，触及这些边界时返回受限或未完成结果，不新增人工等待节点。审批模式下，这些变化由 Manager 提出并由人决定；人的决定仍受有效授权及仓库规则约束。合并继续由人和仓库规则控制。

缺失业务规则在 YOLO 下由 Manager 选择并记录解释，审批模式通过 Manager 请人决定，详见 ADR-0004。这与降低已明确验收标准分别处理。

自动化档位规定编排决定如何获得许可，不授予额外 Git 权限，也不等同于某个 coding CLI 的跳过权限检查参数。

### 1.3 已批准的 Loop 可以自动运行

- 已明确范围和上限的循环可以在许可内自动推进，无须每轮重复审批。
- [ADR-0007](0007-graph-loop-plugin.md) 已确认默认修复 Loop 最多 3 轮、诊断补证最多 2 轮、环境自动恢复最多 2 次；实际约束写入具体计划，预算或时限先到则先停止。
- 循环内产生新候选时，重新判断验证证据是否适用于新的固定交付组合；许可仍适用不代表旧证据仍有效。
- 超出原循环范围或上限时，形成版本化变更并按模式判断，不无限重试。YOLO 只能在现有授权及总体预算等约束内自动判断；触及不得自行改变的边界时返回受限结果。审批模式的待决定变更统一由 Manager 呈现。

### 1.4 变更获准后才进入应用流程

- 审批模式等待人决定时，旧计划仍是有效版本；已经发现不能继续的工作明确标记为阻塞，不能因旧版本仍有效而继续不适用的工作。
- 变更获准后进入“已获准，待应用”，此时新版本尚未生效。
- 第一版在应用变更时，按受影响的上游 Project 暂停新派工，等待在途任务及已提交结果处理到可重规划状态。暂停派工不自动终止在途执行。
- 核对最新状态，应用新版本并读回确认成功后，才以新版本继续派工。一份计划涉及多个上游目标时按 ADR-0012 逐目标核对，全部必要目标一致才整体生效；部分应用范围保持停止新派工，不能盲目继续已被改写的旧安排。处理已提交结果不能冒充业务验收通过。
- 同一上游 Project 内只暂停某个分支的能力留待技术验证，不作为首期承诺；[ADR-0012](0012-issue-scoped-upstream-projects.md) 已确定按 Issue 与仓库委派范围分开上游 Project，具体标识与任务映射仍需细化。

### 1.5 失败与冲突不覆盖历史

- 审批被拒绝时保留变更和拒绝原因。
- 应用遇到冲突时读取最新计划，重新判断原变更及其许可是否仍适用，不直接覆盖最新状态。
- 写入结果不确定时先核查；只有读回确认成功，页面才显示新版本已生效。
- 保留旧版本、执行记录和验证证据。候选或计划变化后的证据适用性与许可适用性分别判断。

### 1.6 RepoMesh 实际控制执行许可

- Manager 生成和提出计划变更；RepoMesh 保存许可记录，并控制变更应用和任务启动。
- 审批状态必须与实际执行约束一致，不能只靠页面按钮、Matrix 消息或提示词保证等待审批。
- Controller、MCP 和存储写入路径如何受控、如何防止绕过，以及与上游计划及派工机制如何衔接，均须后续技术验证。

### 1.7 审批模式的首版计划统一批准一次

本节为后续审批模式的已确认设计，当前阶段仍统一 YOLO，审批能力尚不开发。

1. Manager 在已有权限和预算等约束内读取仓库、分析及澄清需求，整理首版计划；这些准备工作不要求先批准一份尚未形成的计划。
2. Manager 在当前 Issue 主会话统一展示明确的计划版本，包含涉及仓库、主要改动、验收条件、预算和循环上限，由符合第 1.8 节资格的人一次确认。
3. 批准后，RepoMesh 记录许可，应用计划并读回核对生效，再启动对应业务执行。批准本身不等于计划已生效；尚未批准时，不提前执行计划中的开发、正式验证或修复工作。
4. 在已获准范围和上限内，开发、验证及修复循环自动推进，不逐个批准 Worker、验证节点或每轮修复。变更仍按本 ADR 的版本、许可和生效规则处理。

首版计划批准绑定具体版本。计划在获准前后发生修改时，保留版本与决定关联，不能将对原版本的同意自动套用于不同内容；拒绝、修改和应用失败保留历史。首版尚未生效时没有可据以执行该条 Issue 业务工作的旧计划，不能套用计划变更时的“旧有效计划继续执行”。

该审批点位于计划准备与业务执行之间，不作为 Issue 登记或实例准备的前置条件。按 ADR-0016 原子登记正式 Issue 与主 ChangeSet 等；按 ADR-0018，实例及主房间可在首次会话消息后已准备，页面建项则在提交后异步准备或复用。会话本身不转正成 Issue，首次计划许可和应用仍明确绑定该正式 Issue。

支付筛选示例：Manager 先分析 frontend 与 backend，展示本次范围、验收及上限；人批准首版计划后，由 RepoMesh 应用并核对，各 Team 才按有效计划启动执行。各轮自测、独立验证和限额内修复不重复等待人工确认。

### 1.8 计划审批人资格与单人审批

后续审批模式的计划审批采用以下规则，审批能力仍留待后续开发：

- Issue 发起人默认可以审批自己的计划，前提是仍具备相应项目权限。
- 该项目的管理员，或获授该项目计划审批权限的人，可以代为审批。
- 采用单人审批：一名符合资格的人批准即可。审批人必须有权查看完整的待审批计划，RepoMesh 核验其当前资格，并记录审批人、决定和具体计划版本。
- 审批许可不扩大 Git 权限。即使由权限更高的人代审，Agent 仍受原发起人的有效 Git 权限，以及 App、项目和本次任务范围约束，不借用代审者的 Git 权限执行。

例如，发起人提出“支付状态筛选”，可以在资格有效时自行批准，项目管理员也可以代审；决定绑定该计划版本。发起人没有 backend 相应操作权限时，管理员批准不使该操作获得权限，受限处理继续按 J3。

审批资格与决定内容校验由 RepoMesh 实际执行；资格配置、身份映射及实际接口后续细化。重复决定、并发冲突及恢复沿用既有逻辑操作幂等与目标版本校验规则，不将多份重复批准累计为多级审批。

### 1.9 项目默认模式与 Issue 创建时的覆盖

后续支持两种模式时，采用“项目设默认与可选范围，Issue 创建时可覆盖”。当前阶段仍统一 YOLO，相关配置和审批能力后续开发。

- 项目管理员或有项目配置权限的人，设置该项目的默认模式和允许使用的模式；默认模式属于允许范围。
- 新 Issue 继承项目默认值，发起人可以在项目允许的模式中另选；记录该 Issue 最终采用的模式。
- 项目只允许审批模式时，单条 Issue 不能选择 YOLO。实际选择范围由 RepoMesh 核验，页面选项不代替执行约束。
- 修改项目默认值只影响之后创建的 Issue；已有 Issue 保留原模式，运行中切换单独处理。

例如，订单项目默认审批模式，同时允许 YOLO。发起人创建“支付状态筛选”时可以为该 Issue 选择 YOLO；其他未另选的新 Issue 继承审批模式。项目随后调整默认值，不自动改变这些已有 Issue 的模式、许可历史或有效计划。

本条确定配置层级及创建时选用规则，不重新指定后续版本的产品初始默认值，也不扩大仓库权限或预算。运行中主动切换按第 1.10 节处理；项目允许模式范围变化按第 1.11 节处理。

### 1.10 运行中切换模式

后续支持运行中切换模式，由符合该 Issue 计划审批资格的人发起，目标模式必须在项目允许范围内。切换资格沿用第 1.8 节，当前阶段仍统一 YOLO，相关能力后续开发。

```text
请求切换并核验资格、目标模式
    |
停止受影响上游 Project 的新派工
    |
在途任务按有效授权收尾，核对已提交结果
    |
切换生效，保留原模式与切换记录
    |
按新模式处理剩余计划，核对生效后继续执行
```

| 切换方向 | 剩余工作如何处理 |
| --- | --- |
| YOLO → 审批 | Manager 展示当前剩余计划，由人统一批准后继续；RepoMesh 仍先应用并核对计划生效，再恢复对应派工。 |
| 审批 → YOLO | 原待审批事项保留记录，按 YOLO 的有效权限、预算和策略重新判断许可，再按既有应用规则推进；不将模式切换或自动许可记录为人已批准。 |

切换保留已完成工作、已有审批决定和累计消耗，不重新开始整条 Issue，也不把已经完成的任务重新派发。已获准不等于当前仍适用，剩余工作依据实际结果及当前约束重新核对。已有明确要求和拒绝决定不会因切换而被覆盖，切换不扩大 Git 权限、预算或循环上限。

在途任务及 submitted 结果仍按实际归属收尾和核对，不因切换显示成功就当作任务停止或验收通过。权限失效时继续优先遵守 J3 的实际操作限制；模式切换不允许以收尾为名继续无权操作。切换失败或结果不确定时保留记录并先核查，不假设新模式或新计划已生效。

例如，“支付状态筛选”以 YOLO 运行，发起人请求切为审批。RepoMesh 停止新增派工，已有前端自测收尾并保存结果，Manager 汇总后端剩余修改及验证计划；切为审批后，由符合资格的人统一批准剩余计划，再应用并继续执行。先前结果和已经消耗的预算保留。

实际暂停范围仍按受影响的上游 Project 处理；此产品流程不证明 AgentTeams 原生支持仅暂停单条分支或直接切换 RepoMesh 模式，接口、并发及恢复仍需实现验证。

### 1.11 项目允许模式范围变化

采用“新策略约束后续派工，已有 Issue 明确切换”。本节与第 1.9 节的修改默认值分开：默认值变化只影响后续新 Issue 的默认选择；允许范围收紧则约束不再符合策略的已有 Issue 的后续派工。相关能力仍后续开发。

| 对象或变化 | 已确认处理 |
| --- | --- |
| 新 Issue | 按新的允许范围选择模式。 |
| 已有 Issue 的模式不再被允许 | 停止新派工，在途工作按既定规则收尾，Manager 报告受限原因。 |
| 受限 Issue 继续工作 | 保留原模式和历史，由符合该 Issue 计划审批资格的人明确发起切换，按第 1.10 节核验目标、完成切换并处理剩余工作。 |
| 放宽允许范围 | 只增加可选项，已有 Issue 不自动切换模式。 |

例如，项目从允许 YOLO 和审批改为只允许审批，运行中的 YOLO Issue 停止新增派工。在途结果保存后，由有资格的人明确将其切为审批，批准剩余计划，再应用并继续执行。此前成果、审批决定及累计消耗保留；修改项目策略本身不表示已经完成模式切换或批准了剩余计划。

实际停止新派工、在途收敛及 submitted 核对继续按受影响上游 Project 处理。Git 权限失效时仍按 J3 限制具体操作，不以收尾为理由继续无权操作。处于 YOLO 的受限结果不转换为隐含的人工审批等待；人后续明确发起模式切换时，才进入对应的新模式处理流程。

配置生效、派工约束及切换结果均由 RepoMesh 核验和记录，不依赖 Manager 记住一条通知。检测、并发、恢复及具体接口继续技术细化，不能把上游已有 pause 当作这些规则已获运行验证。

## 2. 场景与流程

frontend F1 与 backend B1 正在联调。Manager 发现还需检查导出功能，提出计划 V2；当前有效计划为 V1。

```text
[Current plan V1: frontend F1 + backend B1]
                         |
                         v
[Manager proposes V2: add export verification + reason]
                         |
               +---------+----------+
               |                    |
               v                    v
     [YOLO: policy decision]   [Manager -> Human decision]
               |                    |
               +---------+----------+
                         |
                         v
             [Authorized, awaiting application]
                         |
                         v
      [Pause new dispatch for affected upstream Project]
      [Wait for in-flight work and submitted results to settle]
                         |
                         v
        [Recheck current state -> Apply V2 -> Read back]
                         |
             +-----------+-------------+
             |                         |
             v                         v
      [V2 active]              [Conflict / Failure / Uncertain]
      [Continue dispatch]      [Keep history; inspect and reassess]
```

图中自动判断或人工决定获准后才汇入应用流程；受限或拒绝的请求保留原因，不进入应用。YOLO 也可能处于“已获准，待应用”，例如等待在途任务收敛，但不进入等待人同意的状态。

## 3. 页面状态与职责

| 页面状态 | 含义及展示内容 |
| --- | --- |
| 待审批 | 仅审批模式使用；Manager 在当前会话等待人决定，展示计划版本、变更、原因、范围及约束。 |
| 已获准，待应用 | 许可已获得，显示尚未满足的执行条件。 |
| 应用中 | 正在写入并核对新计划。 |
| 已生效 | 新版本成为当前执行依据。 |
| 已拒绝 | 保留审批拒绝原因和变更记录。 |
| 受限 | YOLO 请求触及不得自行改变的边界，展示原因和未完成工作，不建立人工审批等待。 |
| 需重新判断 | 计划、候选或应用条件发生变化，原变更或许可的适用性需要重判。 |
| 应用失败 | 展示失败原因与下一步，保留旧版本及证据；结果不确定时先核查。 |

这些是计划变更的产品状态，不直接替换 issue、Worker、Attempt 或上游 Project 的状态。

- Manager：说明为什么改、改什么，以及依赖、范围、预算和循环的变化，统一对人展示结果或需要决定的事项。
- 人：在审批档通过 Manager 会话决定是否批准；YOLO 执行过程不逐项等待人。
- RepoMesh：保存有效版本和许可，协调应用时机，核对结果并控制派工。
- 仓库 Team 与验证执行者：在当前有效计划及已有授权内执行；业务修复仍归对应仓库 Team，验证环境不向业务仓库推送修复。

### 3.1 首期仅通过自然语言调整编排

- 用户通过自然语言提出编排调整，例如“增加旧客户端兼容性检查，完成后再汇总验收证据”。
- Manager 将要求转化为明确的计划变更提案，展示差异及原因，继续按本 ADR 的自动化档位、许可和应用规则处理。自然语言请求不直接改写当前有效计划，也不额外要求 YOLO 档逐次人工审批。
- 首期不提供直接编辑节点、属性、依赖连线或拖拽编排的入口；这些能力进入后续待办设计。
- 这项范围决定不改变既有获准与生效的区分，也不证明上游已经支持运行中局部改图。
