# ADR-0018：先保存项目，明确提交后异步准备实例

> 部分替代及现行补充（2026-09-09）：[ADR-0019](0019-conversation-issue-separation.md) 已分离会话与事项，原 Draft Issue 触发对象及“草稿会话转正”不再直接适用。用户持续设计授权后，已采用首次会话及首条消息提交后、或 Issue 栏建项提交后自动异步准备／恢复，见下方“持续设计授权补充”。项目先保存、不立即启动，消息与待办先持久化、实际就绪后投递及权限／容量／预算保障保持。下文原时序保留历史范围，不代表原用户当时已确认新触发。

现行规则：RepoMesh 先由用户明确选择仓库并建立长期多仓项目，项目创建只保存业务资料及必要核查工作；首次会话消息或页面 Issue 创建持久提交后，再异步准备或恢复项目实例及对应主房间。原 Draft Issue 启动方案保留在下一节，后续采用范围及依据见“持续设计授权补充”。

本 ADR 原决定替代 [ADR-0001](0001-agentteams-issue-concurrency-and-isolation.md) D18 的“第一条正式 Issue 持久化后才准备实例”时序，随后按 ADR-0019 和本页补充采用新的触发对象。项目独立实例、长期 Manager／Team、Issue 工作归属隔离及 [ADR-0016](0016-transactional-background-work.md) 的业务与对应待办同事务原则继续有效。原决定依据为[项目入口](../archive/2026-09-12-development-preparation/docs/current/project-first-entry-design.md)与[草稿入口](../archive/2026-09-12-development-preparation/docs/current/draft-issue-and-room-entry-design.md)的用户明确修正。

## 原已采用时序：Draft Issue 模型（历史，现行触发见补充）

~~~text
用户选仓，建立长期多仓项目
        |
保存项目资料；尚无草稿、正式 Issue 或 ChangeSet，不启动实例
        |
项目内首次发送需求
        |
保存 Draft Issue、首条消息及对应对话准备待办
        |
异步核验条件、准备／恢复该项目实例
        |
核验 Manager 与实际主房间就绪 -> 投递消息 -> 草稿讨论
        |
用户与 Manager 明确创建
        |
同事务建立正式 Issue、主 ChangeSet 及后续待办
        |
按有效计划、权限与预算推进正式执行
~~~

项目创建、草稿保存、实际对话就绪及正式转正分别表达。页面可在草稿保存后进入主房间准备视图，但不能把消息已保存写成 Manager 已接收，或把进程已启动写成房间已就绪。草稿阶段不产生正式业务计划、Worker 业务执行、分支或 PR；准备实例不授予执行权限。

后续草稿复用或恢复本项目原实例，每条需求分别保持独立主房间和 Manager 上下文。重复事件及准备失败沿用原项目、草稿和相关操作归属，核查后继续，不重新制造项目或草稿。权限、必要配置或容量不足时保存真实限制和准备状态，不假定持久待办必然可以启动。

## 原决定的理由与代价

项目先保存让用户明确长期仓库范围，首次实际发送需求再准备实例可减少空项目的资源占用。草稿对话由本项目真实 Manager 承接，避免另设临时聊天角色后再迁移的额外体系。

代价是首次对话可能等待实例启动；用户最终不转正也可能已产生实例资源及模型消耗。相关消耗必须有真实归属并遵守适用限制，不能以草稿为由绕过预算。草稿预算分配、费用关联及闲置回收的具体规则留待后续细化。

## 2026-09-09 持续设计授权补充：明确提交后自动接续准备

依据[持续授权及采用清单](../current/design-delegation.md)，采用以下触发规则：

| 已持久提交的动作 | 后续准备 |
| --- | --- |
| 首次保存业务会话及首条消息；已有空会话首次保存消息也适用 | 对应持久待办异步核验条件，准备／恢复项目实例和本条主房间，实际 Manager 与房间就绪后投递已保存消息。 |
| Issue 栏创建提交成功，默认新会话或明确选择已有会话 | 使用同事务待办异步准备／恢复项目实例及该来源会话对应主房间，实际就绪后由 Manager 接手已登记 Issue，不重复建项。 |
| 已有实例或对应房间 | 核查并复用有效资源；需要恢复时沿原关联恢复，不为每条 Issue 另造项目实例或复制现有房间。 |
| 仅建立项目、空会话或只读访问 | 本身不触发运行准备。 |

~~~text
会话首条消息提交，或 Issue 栏创建提交成功
    -> 本地业务事实和对应持久待办已保存
    -> 后台核验当前权限、配置、预算与资源
    -> 复用／恢复项目实例及对应主房间
    -> 核验实际 Manager 与房间就绪
    -> 投递真实消息，或接手已登记的页面 Issue
    -> 正式执行另按有效目标、计划及当前约束推进
~~~

页面创建记录有真实表单来源，不伪装成用户首条聊天消息或 Manager 回复。待办已保存、准备已请求、runtime Ready、消息传输、Manager 接收／处理和 Worker 派工分别取证；创建成功只证明业务已登记。主房间按业务会话关联复用，仍保留 ADR-0012 的各 Issue 执行隔离；Leader 房间和多事项角色上下文的具体映射继续设计／待验证。

准备发生在本地事务之后，不等待外部就绪才返回创建成功。当前条件不满足时保留受限原因和业务事实，不让持久待办绕过权限、预算或资源约束；结果未知核查原操作，不盲目重复创建实例／房间。并发触发汇合到原项目实例准备及各自会话关联，确切领取、代次和失效恢复算法继续设计。

采用自动接续使明确发送或建项后无需再补一次启动动作；相较等后续聊天才启动，可能更早产生实例与模型消耗。该成本依持续授权接受，消耗仍记录真实归属；无 Issue 讨论不得伪记到未来事项，后续建项不清零历史用量。资源准备不等于“仅启动 Manager”模式已经可用，隐藏上下文连续仍待实际验证。

本次确定触发条件，不执行安装、启动或部署。先保存项目的原决定、YOLO、人工 Git 合并及 Skill 工程暂缓范围不变。
