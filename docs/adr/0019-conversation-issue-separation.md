# ADR-0019：会话与 Issue 分离，一个会话关联多条独立事项

> 后续细化（2026-09-09）：本 ADR 的领域与导航关系继续有效。首次消息／页面建项后的准备已按 [ADR-0018 现行补充](0018-provision-instance-after-first-draft.md)采用，创建及来源原子范围见 [ADR-0016](0016-transactional-background-work.md)，双入口与 REST／Issue SSE 见[创建接口契约](../current/issue-page-create-api-contract.md)。这些来自后续确认和持续设计授权，不倒填为本 ADR 原第 3／3 轮的确认。

RepoMesh 将项目下的会话与正式 Issue 分开：会话承载持续讨论，可以没有正式事项，也可以先后创建、关联多条独立 Issue。Issue 有独立页面，组织内部仓库事项并保留整体目标、计划和验收，默认关联一个主 ChangeSet；用户可以从 Issue 导航到实际关联的主房间与 Leader 房间。

该决定替代旧“侧栏聊天条目从草稿转为正式 Issue”以及“一条正式 Issue 必须独占一个用户主会话入口”的绑定，使聊天连续性与交付边界分别表达。代价是维护会话与工作事项的关联，明确消息、操作、结果和导航的实际目标；不能再用当前打开的会话推断执行归属。

## 已确认的关系与职责

- 项目下侧栏的长期聊天对象是会话；会话标题与 Issue 标题分别表达，会话本身不转正成 Issue。建立正式事项是在会话内创建并关联独立业务对象。
- 一个会话可以先后创建、关联多条独立 Issue。该方向不同时决定一个 Issue 能否关联多个主会话，也不代表允许任意多对多关联。
- Issue 是独立整体工作目标，组织 RepoMesh 内部仓库事项；仓库事项可以关联 GitHub Issue。外部 Issue 是可选来源／跟踪，不成为建立内部事项的前提，首期不默认开启外部创建、评论、同步或关闭。
- 每条正式 Issue 保留独立范围、Plan Version、验收与状态，由项目 Manager 总协调；默认一个主 ChangeSet，正式 Issue、主 ChangeSet 与对应后台待办同事务登记。ChangeSet 可以暂时没有候选、组合或 PR。
- Issue 有独立列表／详情入口，可以导航到实际关联的主房间与 Leader 房间。共用主会话入口不合并各 Issue 的计划、执行状态、交付记录或权限。
- 业务持久会话、实际协作 room 和角色 runtime session 分层关联。共同可见的聊天不表示角色共享隐藏上下文，也不证明底层房间复用、上下文隔离或恢复已运行验证。

## 导航、状态与权限边界

房间入口必须基于持久关联、当前可读权限与实际就绪依据，不以房间标题、URL 参数或聊天文本猜测关系。暂不可进入的房间如实表达受阻状态；不可披露的信息按当前权限处理。页面按钮可见性不代替服务端在查询、进入、发送、投递和执行时核验。

从 Issue 进入主会话应保留来源 Issue 的可识别上下文，返回或切换不能悄悄改变在途工作的目标。来源提示和页面当前选项均不是执行授权；后续[消息目标设计](../current/conversation-message-target-design.md) 已采用自然语言明确目标、有歧义先澄清，具体识别、更正及路由协议仍需细化。Leader 房间沿用当前只读观察方向，不因新增导航授予用户直接派工权限；导航所需关联不决定 Leader 房间按何种粒度共享或创建。

会话通信状态、Issue 工作状态、仓库事项进展和房间运行状态分别表达。Issue 创建成功不代表计划已生效、Worker 已派工、房间 Ready、验证通过或交付完成。会话结束也不是 Issue 完成依据。

## 原确认范围与现行未决项

以下区分后续已经采用的设计和仍未写完的细节；历史确认范围保持不变。

- 一个 Issue 能否关联多个主会话，仓库事项每仓数量、共享、创建／关闭和生命周期，Leader 房间共享粒度。
- Draft Issue 是否保留为会话内的事项草案仍未确定。正式创建的双入口、明确创建意图、允许输入快照与幂等结果已由[双入口机制](../current/manager-create-issue-tool-design.md)和创建契约采用；完整 MCP Schema、来源句段与操作承接协议仍需编制。
- 新会话首条消息或页面建项提交后异步准备已按 ADR-0018 采用。无 Issue 讨论的消耗保留真实归属、不伪记到未来事项；费用分配、工具范围、预算计算及运行核查细节仍需细化。
- 会话关联多项时实际模型上下文怎样隔离、恢复及汇总；room/session 的复用和完整隐藏上下文恢复不作保证。
- 创建、原操作查询、Issue 详情／房间查询及 Issue SSE 已有采用的具体契约，见[创建接口契约](../current/issue-page-create-api-contract.md)。内部仓库事项、会话通信和其他未编制模块的协议、分页与运行恢复仍需设计；不能将已采用的 Issue SSE 扩大为所有通信契约。

本决定原确认仅涵盖列明的领域与导航方向，不把后端专项稿、页面原型或接口示例整体标为 accepted；后续采用以各自记录为准。当前设计与本地原型进展不代表后端实现或上游运行验收。
