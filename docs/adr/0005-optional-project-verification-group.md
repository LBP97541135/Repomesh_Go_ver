# ADR-0005：项目级验证小组、职责与动态执行

项目可配置专用跨仓验证小组，并在设置中选择“启用跨仓验证小组”，默认不启用。关闭后，Manager 仍组织验证；启用与否不改变验证范围、证据要求和通过门槛。团队按 Skill 组织工作，相关统一交互和模式规则见 [ADR-0006](0006-manager-entry-modes-and-skill-driven-execution.md)。

本 ADR 确认产品职责，不代表这些角色已经映射为可用的 AgentTeams 资源或通过运行验收。

## 1. 组织与人员选择

- 验证小组属于项目级，默认不启用；启用后优先承担跨仓验证节点。
- 小组开关和成员配置由项目管理员或被授予项目配置权限的人修改，记录操作者、时间和原因；普通执行 Agent 不自行改变项目级开关。
- 启用的小组设置一名固定验证负责人，负责组内安排、证据完整性核对、结果汇总，并向 Manager 回报。
- 未启用小组时，由 Manager 组织项目内具备能力及有效权限的 Worker 执行并复核；无合适执行者时显示等待原因。
- 负责人依据验证 Skill 和当前任务请求所需能力的 Worker，优先复用合适空闲成员，需要时请求创建。实际分配、创建和启动由 RepoMesh 控制。Worker 数量可在设置中调整，默认 1，沿用 A1 的团队并发上限含义，固定负责人不计入 Worker 数量。
- Worker 单活跃任务、Attempt 独立副本、全局容量和项目额度继续适用。项目设置不触发提前创建实例。
- 业务修复归对应仓库 Team；验证环境不向业务仓库推送或合并修复。

```text
Manager：协调 issue，统一对人沟通
    |
验证负责人：根据 Skill 组织验证、复核和汇总
    |
    +-- 页面验证 Worker
    +-- 接口与数据验证 Worker

实际成员依任务分配，图中数量仅为示例
```

### 调度、不可用与回收

优先完成已有候选所需验证、必要诊断和收尾，同级按等待顺序安排。Worker 失联时核查真实执行，确认旧 Attempt 已停止或失去写入能力后再由替补开新 Attempt；不确定时保留执行状态不明。

验证负责人暂不可用时由 Manager 代行协调，测试仍由独立 Worker 执行。Manager／Leader 故障优先恢复原身份和已保存上下文，停止相关新增派工，在途按已有约束收尾。保留成员身份、配置和经过整理的知识，空闲后释放执行资源，证据及必要产物保存后回收 Attempt 副本。完整 A1—A5 规则见[团队执行策略](../current/team-execution-policy.md)。

## 2. 正式验证与业务作者分离

- 业务作者可自测、提供脚本和排查资料，但不担任本轮相关业务改动的正式跨仓验证执行者。
- 独立性针对本轮被测改动，不以是否曾参与该仓库开发作为依据。
- 正式验证 Worker 可以复用已有测试，需要核对其是否符合适用验收条件，并实际执行、提交证据。
- 未启用小组时同样适用。没有合适执行者不因此省略检查或判为通过。

## 3. 必检清单、执行与复核

| 角色 | 职责 |
| --- | --- |
| 各仓 Leader | 提供契约、改动范围、已知风险和已有测试；负责本仓定位与修复安排。 |
| 验证负责人 | 根据适用验收条件编制跨仓必检清单及覆盖关系；组织执行，核对版本、证据和结论，复核后采纳为有效检查结果。 |
| 验证 Worker | 编写或复用测试，实际执行，提交证据和单项结果初判。 |
| Manager | 核对整个 issue 的覆盖、依赖和预算，将清单纳入计划版本；汇总结果，协调后续工作，统一对人沟通。 |

未启用小组时，Manager 组织被指派的验证 Worker 起草清单，并承担组织和复核职责。缺失业务规则按 ADR-0004 分模式决定，不要求 YOLO 等待人。计划调整遵守 ADR-0003。

执行者初判与复核采纳分别记录，可在 Manager 汇总及详情中查看。这是 Agent 内部职责，不新增逐项人工确认。例如报告声称四项全部通过，但缺少分页证据，复核者指出缺口，相关检查保留“暂无法判定”，节点尚未通过。

## 4. 问题归属与重新验证

- 验证 Worker 提交失败证据和初步归属；验证负责人核对后交给相关仓库 Leader 定位。
- 已证实违反验收条件时，即使尚未定位仓库，也保留“业务缺陷、归属待定位”。
- frontend/backend 对归属有分歧时，由 Manager 协调补充诊断，依据证据分派修复。缺失业务含义按 ADR-0004 处理。
- 业务 Team 修复并提交新候选；验证负责人组织独立 Worker 针对新固定组合重新验证，同时判断旧证据能否复用。
- 未启用小组时，由 Manager 承担相应组织和复核职责。
- 诊断和重验遵守当前计划及获准额度，需要调整计划时按 ADR-0003 处理；结果标签本身不授予无限派工或重试许可，具体循环行为按 [ADR-0007](0007-graph-loop-plugin.md) 处理。

## 5. 运行中停用

关闭开关后，小组停止接收新任务，页面显示“停用中”。

| 工作状态 | 处理规则 |
| --- | --- |
| 尚未开始，包括已分配但未启动 | 停止由该小组启动，交回 Manager 按既有授权安排。 |
| 正在执行 | 当前 Attempt 继续完成，保存结果和证据。 |
| 已提交、待核对 | 继续核对，提交本身不算通过。 |

以上工作处理完后显示“已停用”。新验证由 Manager 按未启用小组的规则安排，计划变化仍按 ADR-0003 处理。收尾保留真实缺陷和阻塞结果；小组状态不替代 issue、计划、Task 或 Attempt 状态，停用不等于删除成员和历史。

### 停用异常与重新启用

- 长时间未收尾时按任务已有超时规则处理，Manager 汇总卡住的 Attempt，页面显示“停用受阻”及原因。核查、停止和保存结果后再完成停用，不把超时作为成功。
- 停用中重新启用时恢复接收新任务，在途继续；已经交回 Manager 的任务不自动抢回，已经终止的 Attempt 不复活，避免重复派工。

## 6. 技术细化

A1—A5、B1—B4 已确认，成员数量设置默认 1、开关默认不启用。具体容量配置界面、故障探测和进程核查仍需细化；不将这些实现问题重新列为尚未决定的组织方向。

Skill、成员创建回收的技术契约，以及小组、固定负责人、Worker 与上游资源和房间的映射仍需验证。也需验证参与被测业务改动的记录、独立性核查、容量占用、权限和计划控制能够实际生效。

## 7. 决定来源

用户逐项确认项目级可选小组、停用收尾、固定负责人、执行者独立性、清单分工、初判与复核，以及归属与重新验证；随后采用 ADR-0006 的统一 Manager 交互及 Skill 动态执行方向。2026-09-08，用户采用 A2—A5、B2—B4，并指定 A1 数量可设置且默认 1，B1 默认不启用。详细历史确认记录见[修改前快照](../archive/2026-09-08-before-manager-skill/docs/adr/0005-optional-project-verification-group.md)。
