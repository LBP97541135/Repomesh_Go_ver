# ADR-0008：ChangeSet 归属、记录、交付与恢复

> 归属澄清（2026-09-09）：按 [ADR-0019](0019-conversation-issue-separation.md)，本文主 ChangeSet 归属独立的整体 RepoMesh Issue，不归属聊天会话，也不因新增内部仓库事项而逐个或嵌套创建。一个会话关联多条 Issue 时，各项默认主 ChangeSet、计划、候选与交付历史分别保留；CS1—CS14 的既定保障不变。

一条 issue 可以经历多轮执行、候选更新和交付动作，需要稳定的变更归属。一个 issue 默认对应一个贯穿本次交付的主 ChangeSet；修复保留同一身份和多轮历史，各交付动作独立记录并处理幂等。相比每次 Attempt 都建立完整 ChangeSet，这个边界使候选、验证和 PR 历史保持连续。

本文 Issue 指 RepoMesh 内部的一条统一需求事项，可以涉及一个或多个仓库；它与 GitHub 单仓 issue 分开，可关联零到多条外部 issue；首期只支持来源／跟踪关联，不默认启用创建、评论、状态同步或关闭操作，沿用 [ADR-0002](0002-github-app-authorization-and-draft-pr-delivery.md) 的区分。

用户明确 ChangeSet 是现有 Candidate 与 Delivery Combination 的记录整合。定义见[领域语言](../../CONTEXT.md)，本 ADR 不预先指定数据库结构或实现技术。

## 创建时机

issue 正式提交并持久化时，就建立对应的主 ChangeSet，允许暂时没有 Candidate、Delivery Combination 或 PR。后续产生的候选、组合、PR 和交付历史继续关联该记录。

例如支付状态筛选 issue 已保存，但实例准备受阻，仍有稳定变更归属可追踪相关进展；恢复后继续关联产物。重复事件及恢复处理复用同一 issue 的主 ChangeSet，不重复初始化。

此时建立的是变更记录，不决定实例启动时点。启动现按 ADR-0018 补充：首次会话消息或页面建项持久提交后异步准备／恢复。已确认本地 Issue 与主 ChangeSet 原子登记；来源会话、输入快照、幂等结果及待办等补充范围见 [ADR-0016](0016-transactional-background-work.md)，具体数据库实现与运行恢复仍待验证。

## Agent 查看与溯源

ChangeSet 同时承担面向 Agent 的变更查看与溯源入口，使 Agent 能查看相关产物、验证依据和交付历史的来源及关联，理解结果如何形成。这是用户已确认的用途，服务于 Agent 接手工作、定位问题和查阅历史。

Agent 采用“先读带来源引用的摘要，再按需查询关联的结构化记录和原始证据”的方式：

- 摘要用于了解变更目标、相关仓库和交付组合、当前进展、待解决事项及重要决定，并提供对应记录引用。
- 需要进一步了解原因时，沿 Candidate、Delivery Combination、Task／Attempt、决定或操作记录查看来源、关联版本及依据。
- 摘要中的结论能够定位到来源；证据缺失时明确显示缺失，不用推断补成已有事实。

例如追溯 B2 的产生原因，可从该候选找到对应修复任务和 Attempt，再查看触发修复的旧组合、失败检查、原始证据及当时适用的验收依据。关联必须来自实际记录。

Agent 默认读取当前 ChangeSet，并可在既有有效权限内按 RepoMesh Issue、仓库、commit、PR 查询同项目相关历史；跨项目查询首期不默认开放。返回记录标明所属组合、时间和来源。精确字段、分页、引用格式及工具契约尚待细化，不宣称接口已经存在。

## 记录关系

- ChangeSet 确定这次变更的归属，关联 issue、涉及仓库、PR、Candidate、Delivery Combination 和交付历史。
- Candidate 继续表示执行成员提交、等待检查和接受的产物；收录记录不代表任务或 issue 已通过全部验收。
- Delivery Combination 继续表示为同一 issue 的验证选定的一组仓库候选版本；组合内任一版本变化，都需重新判断原验证证据的适用性。
- 多轮版本沿用既有候选及交付组合表达，在同一 ChangeSet 中保留历史。此前讨论稿的“ChangeSet 版本”不另定义一套与交付组合重复的候选模型。
- 计划说明如何组织工作，候选和组合明确产物及验证对象，ChangeSet 串联这些记录；记录整合不合并它们的身份或验收含义。

```text
Issue：支付状态筛选
    |
    +-- ChangeSet CS-01
           +-- 仓库：frontend / backend
           +-- Candidate：F1、B1、后续 B2
           +-- 交付组合 C1：F1 + B1 -> 对应证据
           +-- 交付组合 C2：F1 + B2 -> 对应证据
           +-- frontend PR / backend PR
           +-- 各交付动作的操作记录及历史
```

图表示关联关系；Candidate 正式提交即收录，业务仓候选经 Leader 内部初审接受后，由 Manager 按验证范围、前提和有效计划选定固定组合。B2 不覆盖 B1；旧组合及证据保留，原通过结论不自动沿用到新组合。各仓单独成功也不等于整体成功。

## Candidate 收录时机

执行成员正式提交 Candidate 时，就关联到所属 ChangeSet，记录当次产物版本及来源 Task／Attempt，不等待检查接受。后续未被接受也保留检查结果、原因、证据及历史；修复产生新候选，保留新旧候选与修复过程的关联。

例如 B1 已收录但未通过 Leader 初审，B1 仍可供 Agent 查询和溯源；后续提交 B2 时新增记录，不用 B2 覆盖 B1。业务仓候选沿用 Leader 的初审职责，验证产物等其他候选沿用各自的复核职责。

收录不自动表示检查接受、入选交付组合、通过验证或达到 PR 创建条件。正式组合选定按 CS3；未修改的参与仓库固定基线，未接受候选可用于明确的诊断，新候选不替换已启动验证的组合。PR 时机仍按已确认的 E 规则执行。

## 幂等边界

幂等落实到各个逻辑操作，不只依赖 ChangeSet 身份。一次操作的重试沿用原操作标识并核查已有结果；真正的新变更保留为新候选、组合或操作，不能被当作重复请求忽略。外部结果未知时先核查，不仅凭本地请求记录宣布成功或直接重复创建外部对象。

每个逻辑操作的标识绑定目标和输入摘要，同标识不同输入拒绝。并发更新校验目标版本，对同一目标的冲突操作串行处理；重启及超时先核查本地和远端事实再恢复。具体编码、去重索引和运行适配尚待实现，不承诺跨系统只执行一次。

## 已确认交付规则与实现边界

Candidate 提交、检查接受、组合验证、推荐正式审查、人工合并和 issue 完成分别表达；ChangeSet 的存在不证明任何阶段已完成。[PR 时机](../current/draft-pr-review-design.md)继续有效，合并仍由人和仓库规则决定，ChangeSet 不增加 Agent 权限。

用户已全部采用 [CS1—CS14](../current/changeset-design.md)。除上述规则外，确认：

- 执行、验证和交付进展分开汇总，保留阻塞与部分合并事实；Agent 判断有来源，更正追加历史。
- 任一仓库版本变化建立新交付组合；同一组合下验收、Skill、环境或 mock 数据上下文变化，新增验证记录并重新判断证据。
- 代码交付完成需要约定交付物、验收和必做事项完成，所有必需 PR 已由人合并，最终实际组合证据有效；部署另记。
- 按兼容性选择人工合并顺序。基线变化或部分合并后，以实际版本形成后续组合并重新判断证据，不自动撤销成功部分。
- 未合并 PR 取消留在原 ChangeSet；已合并代码撤销由人发起关联恢复 Issue／ChangeSet，仓库 Team 产出撤销 PR，人合并。首期部署与数据恢复由相应有权限的人执行并留记录。
- 本轮修复继续原 ChangeSet，完成后新增范围使用关联的新 Issue／ChangeSet；误标完成可追加更正，首期无嵌套 ChangeSet。
- 项目存续期保留归属、版本关联、决定和操作结果，必要验收证据随交付档案保存；临时材料按策略清理，附件可用性如实标明。

[结构说明](../current/changeset-structure.md)解释记录如何关联，其中完整 ChangeSet 存储与接口尚未冻结。F／G 的合并恢复议题以本次 CS9—CS12 为准，Skill 工程 H1—H15 已另行同意并以 [ADR-0009](0009-skill-engineering-deferred.md)保留设计位置，整个模块待定、暂不开发；I 当前阶段按全自动设计，后续审批主要规则已确认（见 ADR-0003），审批能力后续开发；J1—J3 主要规则已确认。Issue 创建接口已按[现行契约](../current/issue-page-create-api-contract.md)采用，其他接口与运行适配继续细化验证。

## 决定来源

2026-09-08，用户确认一个 issue 默认一个主 ChangeSet、同一身份下多轮版本及各操作独立记录幂等的边界，并明确其用于确定变更归属，串起 issue、仓库、PR 和交付历史，整合 Candidate 与 Delivery Combination 的记录。

用户随后采用在 issue 正式提交并持久化时建立允许暂为空的主 ChangeSet，并补充其用途是方便 Agent 溯源和查看；进一步采纳“先读带引用的摘要，再按需查询关联记录和原始证据”的读取方式。

用户进一步采用“Candidate 正式提交即收录，未被接受也保留历史”，随后对 CS1—CS14 回复“都采用”。RepoMesh Issue 与 GitHub issue 的区分沿用既有术语和 ADR-0002；外部关联按 CS1，自动同步和写操作不默认启用。

这是已确认产品设计，未实施或运行验收。边界确认前的提案见[历史讨论稿](../archive/2026-09-08-changeset-initial-proposal.md)。
