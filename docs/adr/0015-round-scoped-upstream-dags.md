# ADR-0015：按获准轮次向上游下发有限任务图

RepoMesh 首期将当前获准轮次的具体工作映射为有限 DAG，即带依赖关系的有限任务图，复用 AgentTeams 原生建图、依赖校验、候选就绪计算及受控任务执行路径。后续轮次由 RepoMesh 根据有效结果、计划与约束判断并控制，不预先授予上游独立推进整个循环的权限。2026-09-09 的最新版本与复用补充见文末，详细分工统一见 [Graph／Loop 专题](../current/graph-loop-design.md)。

本决定细化 [ADR-0007](0007-graph-loop-plugin.md)、[ADR-0012](0012-issue-scoped-upstream-projects.md) 与 [ADR-0014](0014-in-process-graph-plugin.md)。选择这一映射方式，是为了统一跨仓依赖、验证结果和累计停止条件，并避免把上游原生 Loop 的存在误当成 Controller 已提供完整循环修改能力。

## 已采用的行为

- 每次落实当前获准轮次的有限执行安排。全局依赖仍由 RepoMesh 管理，各上游 Project 承载其委派范围内的工作；不把跨仓图直接当作一个上游 Project。
- Manager 根据缺陷和业务要求组织修复安排；上游计算仓内 DAG 的候选就绪节点，Graph 插件判断跨仓依赖、业务结果适用性及循环是否可继续；后台再次核验有效计划、权限、预算、时限、轮次和容量后实际派工。就绪、任务结束和验证通过分别判断。
- 已有计划范围和上限内进入下一轮，属于计划执行进展，不因轮次推进而重新创建 Issue、Manager 或业务 Plan Version。超出原范围或改变上限等仍按 ADR-0003 处理计划变更。
- 新 Attempt、候选、固定组合和结果分别留存，不覆盖上一轮历史；新组合重新判断证据适用性。累计消耗和停止条件继续按既定规则执行，重启或换计划不清零。
- 上游任务安排的更新与业务 Plan Version 分开记录。若增加下一轮任务需要 replan，必须按完整受影响上游 Project 停止新派工、等待在途收尾、核对 submitted，再应用并读回；多目标应用仍遵守 ADR-0012。

## 支付状态筛选示例

~~~text
前端修改 ─┐
          ├→ Manager 选定固定组合 → 独立验证
后端修改 ─┘                            |
                                  有效业务缺陷
                                       |
                 Manager 组织修复，上游 DAG 给出候选就绪节点
                                       |
                 Graph 核对跨仓／循环，后台核验后实际派工
                                       |
                       下发本轮修复 → 新组合 → 必要重验
~~~

例如 C1 的分页验证发现筛选条件丢失，RepoMesh 在既定修复范围内安排对应仓库修复；新候选被接受后，Manager 选定 C2，再组织适用于 C2 的必要验证。达到预算、时限、循环上限或连续相同失败的停止条件时，记录真实未完成原因，不自动再开一轮。

## 原因、代价和边界

这一方式使跨仓判断与循环约束集中在 RepoMesh，仓内当轮 DAG 能力复用 AgentTeams。上游已有原生 DAG／Loop，但 Controller replan 的 DAG 改写能力不能证明完整 Loop 可被重写；pause 不停止在途任务，replan 遇到 in-progress／submitted 会拒绝。当前基线 paused 直接 replan 的 409 还有真实 HTTP／MinIO 证据，不能直接照抄为 pause 后改图。静态依据及后续验证范围见 [Graph／Loop 专题](../current/graph-loop-design.md)。

代价是 RepoMesh 需要维护轮次与执行映射，且下一轮若需 replan，收敛和读回会增加协调成本及等待时间。不承诺上游天然支持动态追加任务，也不承诺只暂停一个图分支。

具体轮次落库与并发核验、上游 task 标识、新 Attempt 映射、上游 Project 的更新或复用方法、验证范围的承载方式、工具协议及故障恢复算法仍待细化和运行验证。本决定未选定动态追加接口或原生 Loop 调用路径，也不授权编码、安装或部署。当前仍统一 YOLO，无逐轮人工审批；Skill 工程整体暂缓不变。

## 确认来源

在解释按当前获准轮次下发有限任务图、RepoMesh 判断后续轮次、既定循环内无需新建业务 Plan Version，以及 replan 可能需要整份上游 Project 收敛的代价后，用户回复“采用”。本次确认只采用上述映射方向，不将架构 v1 的其余建议一并视为确认。

## 2026-09-09 补充：当轮 DAG 明确复用最新上游能力

用户要求按最新版本复用上游 DAG 并清理本专题文档，原话及 Graph 模块职责调整见 [ADR-0014 本日补充](0014-in-process-graph-plugin.md#2026-09-09-补充复用原生-dag收窄-graph-模块职责)。本补充确认：

- 上游每个 Project 的当轮 DAG 具有实际复用价值，不只作为 RepoMesh 自研引擎的状态镜像；不重复实现其通用仓内依赖和就绪算法。
- RepoMesh 保留全局依赖、当前业务结果采纳、固定组合、独立验证、循环上限、累计消耗及许可／生效／派工约束。原生 ready 或 completed 不能单独授权启动或宣布业务通过。
- 原生 Loop 的存在不改变首期选择：仍逐轮使用有限 DAG，RepoMesh 控制后续轮次。新轮次不自动新建业务 Plan Version，上游安排修订及新 Attempt 分别记录。
- 最新源码／release 的区别、原生能力清单、身份、应用与恢复规则和待验证项统一维护在[现行专题](../current/graph-loop-design.md)，不把“最新版”当浮动部署标签。

本补充不选择 resume 后 replan 或 paused replan 补丁中的某条实现，也不承诺动态追加、分支级暂停或 completed Project 可直接重开；这些属于接入协议验证范围。
