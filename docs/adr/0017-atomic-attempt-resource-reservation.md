# ADR-0017：Attempt、Worker 与容量统一预留，启动前再次核验

RepoMesh 在一个短数据库事务中统一登记 Attempt、Worker 占用和所需容量预留，防止并发请求分配同一个 Worker 或重复使用剩余额度。事务提交后准备独立环境，实际启动前再次核验有效约束。

本决定细化既定单 Worker 单活跃任务、团队／项目／全局额度规则，以及 [ADR-0016](0016-transactional-background-work.md) 的持久后台执行边界。它采用原子分配方向，具体锁、表、领取和恢复算法仍待细化。

## 已采用的行为

~~~text
检查任务条件及适用的计划、权限和额度
        |
短数据库事务
  +-- 登记 Attempt
  +-- 占用 Worker
  +-- 预留所需容量，核对团队／项目／全局约束
        |
事务提交 -> 准备独立环境 -> 启动前再次核验 -> 实际执行
~~~

竞争同一 Worker 或同一份容量的请求不能同时分配成功。分配记录一起提交或一起不生效；未取得资源的工作保持等待，展示实际原因。该事务不跨越环境准备和外部请求的长时间等待。

准备环境期间，相应 Worker 和预留名额已被占用。实际启动前再次核验计划、权限及占用是否仍有效，防止准备期间发生撤权、暂停或取消后继续启动。数据库预留不等于永久授权，也不替代实际执行入口的约束。

准备失败时保留失败记录，核查实际环境并释放已经可以释放的占用。超时本身不证明旧执行停止或资源已经释放；结果未知时先核查，不能仅凭超时就把 Worker 或实际容量重新分给其他工作。Attempt 历史保留。

## 场景、理由与代价

“支付状态筛选”和“订单导出”同时需要后端 Worker，团队并发为 1。若分别先查空闲再写占用，两个请求可能都读到空闲。统一事务登记后，一个请求取得 Worker 和容量，另一个等待，页面可说明“等待后端 Worker”。这只是竞争示例，不在本决定中选定新的公平性或优先级算法。

收益是让剩余额度检查和实际分配保持一致，落实既定并发约束。代价是需要维护预留、运行和释放之间的状态及核查过程；环境尚未准备完成时也会占用相应名额，可能降低即时利用率。

## 待细化与确认范围

具体容量计量、事务隔离与锁定顺序、数据库约束、占用代次、超时参数、资源释放顺序、执行端核验协议及故障恢复算法尚未冻结。外部权限的实际强制控制和运行资源状态仍须通过受控接入与运行验证落实，不宣称一个数据库事务能原子控制外部系统。新建成员、验证环境与其他执行类型的具体分配映射仍待细化。

用户在解释短事务统一占用、环境准备在事务外、启动前再核验以及失败时先核查再释放后回复“采用，然后写给下一个会话的prompt,下一个会话要做页面设计和接口设计。”据此记录上述方案，并将下一阶段切换为页面与接口设计。
