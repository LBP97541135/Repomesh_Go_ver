# ADR-0002：仓库范围、GitHub App 分层授权与 Draft PR 交付

RepoMesh 需要让 Agent 在多个授权仓库中完成代码修改并交出可审查的 PR，同时保留发起人的权限上限和仓库的合并控制。用户确认采用“选仓确定范围、App 固定权限集、运行时进一步收窄、默认交付 draft PR”的方案，避免把仓库接入做成逐仓操作权限菜单。

本决定沿用 [ADR-0001](0001-agentteams-issue-concurrency-and-isolation.md) 的一项目一实例、一仓一 Team 和独立 Attempt；启动时点以 [ADR-0018 的现行补充](0018-provision-instance-after-first-draft.md)为准。领域定义见 [CONTEXT.md](../../CONTEXT.md)。`accepted` 表示产品设计已确认，GitHub 与 AgentTeams 的具体实现及强制能力仍待验证。

## 已确认决定

| 层级 | 已确认的产品规则 |
| --- | --- |
| 仓库选择 | 添加仓库时选择允许接入的仓库范围，可选择全部或指定仓库；不逐仓勾选“只读、推送、开 PR、合并”。App 安装可访问范围与 RepoMesh 项目接入范围分别记录，安装范围不能自动成为每次任务的范围。 |
| App 权限集 | GitHub App 申请一套固定的工作权限集，覆盖读取代码、创建及推送任务分支、创建 PR、读取检查状态等主路径；向用户解释这套权限的用途。具体 GitHub 权限名称、级别和规则读取所需权限待核查，不据此承诺逐仓配置不同权限集。 |
| 运行时授权 | 实际执行使用比安装授权更窄的凭证或受控工具能力，限定当前项目、发起人、任务涉及的仓库与操作；默认支持改代码、推自己的分支及开 draft PR，不默认启用 GitHub Issues 操作、重跑 CI 或仓库管理操作。 |
| 发起人权限 | 启动 Agent 不增加用户的 Git 权限。App 能访问的仓库仍须经过 RepoMesh 的用户与项目授权核验；有效执行范围不得超出发起人对相应仓库和操作的授权。 |
| 对外交付 | Agent 默认交出可审查的 draft PR，合并留给人和 GitHub 仓库规则；主分支通过 branch protection / rulesets 禁止 Agent 直推，也不向 Agent 授予修改或绕过这些规则的能力。读取规则仅服务于状态判断。 |

- 仓库页面呈现接入范围和授权是否有效，不设置逐仓操作权限复选框。
- J1 已确认：关联 GitHub 账号后，让用户选择自己实际有权参与的仓库，包括自己的仓库及通过邀请获得访问权的仓库。账号关联、可见仓库和 App 实际工作授权分别核验；关联账号不自动授予 App 仓库权限。
- J2 已确认：可选仓库列表自动更新，项目范围由用户明确添加；“全部选择”只选中当时的仓库，不自动包含未来新增仓库。新增仓库加入项目不自动改变在途 Issue 范围，实际纳入时仍走现行计划变更规则。
- J3 已确认：部分仓库授权失效时，项目显示部分受限及具体原因；仅涉及可用仓库的新 Issue 可正常提交。停止已无授权的操作，依赖它的工作受阻，无关且仍获准的工作可继续；Manager 汇总受限及未完成结果，保留历史，不新增人工审批等待。实际重规划仍按受影响上游 Project 收敛。
- 项目接入不要求用户选择分支，由 Manager 按 Issue 和已有明确要求确定目标分支及固定基线，Team 在独立 Attempt 副本中执行。此规则不扩大写入或合并权限；配置、模型设置与具体场景见[项目配置设计](../current/project-configuration-design.md)。
- 多仓 issue 可以协调多个仓库一起修改、形成相互关联的 PR；仍沿用 ADR-0001 的 D03、D08、D09：每仓由自己的 Team 负责，每次 Attempt 使用独立副本。增加项目可接入仓库数量，不自动赋予单个 Worker 所有仓库写权。
- 产品上 Agent 负责改代码和开 PR；如何通过受控交付服务或收窄凭证完成，是技术接入问题，不要求把 App 的完整凭证交给每个 Worker。
- 仓库范围、App 授权、发起人权限和本次任务范围需要共同满足。仅持有 App 凭证不能证明已经满足发起人的权限上限；服务端必须能执行该约束。
- RepoMesh 内部的 issue 登记和讨论不等同于 GitHub Issues API 操作。按已确认 CS1 可关联零到多条外部 issue 并标明来源／跟踪关系，重复导入先查映射；首期不默认启用外部创建、评论、同步或关闭。实际读取／同步接口及额外权限仍作为接入问题确定。
- 仓库授权和上述配置检查仍在 RepoMesh 管理面完成。按 ADR-0018 现行补充，首次会话消息或页面建项持久提交后异步准备／恢复实例；仅建立项目、空会话或只读访问不触发，准备与执行仍核验当前有效授权。

待技术验证项：固定 App 权限集的最小组合；安装 token 可收窄的仓库与操作维度；如何核验发起人的有效权限及权限撤销；如何组合凭证、受控工具与仓库规则保证只推自己的分支、只开 PR，并阻止直推、合并和规则绕过。不能把“能推送、能开 PR”描述成已经证明 token 在技术上不能调用合并接口。

J1 最小配置、J2 后续新增仓库及 J3 授权部分失效的主要产品规则已确认，见[项目配置设计](../current/project-configuration-design.md)。授权检测、实际拦截和恢复触发细节仍需细化与验证；I 的执行模式与审批主要规则已确认，后续页面与创建接口进展见[现行导航](../current/README.md)。PR 创建、持续更新和正式审查时机见[审查设计](../current/draft-pr-review-design.md)；ChangeSet 的归属与记录整合见 [ADR-0008](0008-changeset-attribution-and-history.md)，合并顺序和恢复按已确认的 [CS9—CS12](../current/changeset-design.md)处理，当前授权边界保持有效。

## 最小验收场景

| 场景 | 预期结果 |
| --- | --- |
| App 能访问仓库，但发起人无相应仓库或操作权限 | RepoMesh 拒绝相应访问或操作，启动 Agent 不扩大个人权限。 |
| 多仓 issue 形成对外交付 | 各仓 Team 按分工修改，受控推送自己的任务分支，生成关联的 draft PR，不自动合并或直推主分支。 |
| 执行请求超出当前任务范围，或要求 GitHub Issues、重跑 CI、修改仓库规则 | 按运行时授权拒绝，不因 App 安装权限较宽而默认放行。 |
| 一仓授权失效，但其他仓库仍可用 | 项目显示部分受限，可用范围的新 Issue 仍可提交；停止失效操作及阻塞其依赖，无关且获准的工作继续，整体结果保留未完成原因。 |

上述为待执行的验收标准，本轮只更新设计文档，未运行这些场景。

[ADR-0006](0006-manager-entry-modes-and-skill-driven-execution.md) 的 YOLO 和统一 Manager 交互不增加 Git 权限，也不授权 Agent 自动合并；授权受限结果由 Manager 汇总反馈。
