# ADR-0006：Manager 统一交互、自动化档位与 Skill 驱动执行

用户希望通过一个 Manager 会话推进工作，减少逐节点人工介入，并让团队根据仓库和任务动态组织执行。采用 Manager 统一对人沟通、团队和验证流程由 Skill 指导、RepoMesh 实际控制执行的设计；YOLO 不触发人工审批，缺失业务规则由 Manager 选择并记录解释后继续。

本 ADR 调整 [ADR-0001](0001-agentteams-issue-concurrency-and-isolation.md) 的用户交互入口、[ADR-0003](0003-plan-change-authorization-and-activation.md) 的 YOLO 人工等待语义，以及 [ADR-0004](0004-acceptance-rule-clarification.md) 的业务解释决定权。后续 [ADR-0019](0019-conversation-issue-separation.md) 替代每 Issue 独占用户主房间的绑定，启动按 [ADR-0018 的现行补充](0018-provision-instance-after-first-draft.md)，本节据此维护。产品设计已确认，MCP、动态资源分配和上游适配未实现或运行验收。

## 1. 用户通过 Manager 推进事项

- 主界面以项目下的业务会话承载与 Manager 的讨论；会话可无正式 Issue，也可关联多个独立 Issue。用户通过它提出需求、查看汇总、反馈和作出需要人的决定。
- 仓库 Leader、验证负责人和 Worker 在内部协作；需要用户决定的事项统一交给 Manager，不要求用户逐个进入这些角色的窗口。
- Manager 汇总进度、结果、证据和需要决定的事项。检查详情可以展开查看，具体布局、图交互和刷新方式仍待设计。
- 验证负责人的复核、仓库 Leader 的定位和 Manager 的汇总是 Agent 内部工作，不设置逐项人工确认。
- 页面与 Manager 受控工具创建的正式 Issue 均由项目 Manager 接手协调，包括明确单仓需求；复用现有 Manager 身份，各项计划、验收与执行记录分别归属，用户主房间按业务会话关联复用。
- Manager 从接收到结果汇总始终担任 issue 总负责人，再按范围委派一个或多个 Leader；Leader 负责被委派的仓库工作，不承接整条 issue 的总责。
- 工作消息绑定明确目标，有歧义先澄清；追加消息、重试及重复事件保留原操作与事项归属。准备失败保留业务事实，核查原实例／房间操作后恢复。具体入口见 ADR-0001，消息目标见[专题](../current/conversation-message-target-design.md)。
- 首次会话消息或页面建项持久提交后，按 ADR-0018 异步准备／恢复实例及对应主房间；仅建立项目、空会话或只读访问不触发。Issue 详情可导航实际关联的主房间及只读 Leader 房间，不增加用户直接派工权。

## 2. 人工门禁按模式处理

### 当前阶段：全自动运行，审批能力后续开发

2026-09-08 用户确定 I 当前先按全自动、无人工执行卡点推进。当前阶段项目及 Issue 统一按 YOLO 设计，首次计划与后续计划变更均在现有授权、预算和策略内自动判断、记录许可并应用，不等待人批准。计划版本、获准、生效及实际执行核对继续分开。

后续审批模式的主要设计已确认，完整规则见 [ADR-0003 第 1.7—1.11 节](0003-plan-change-authorization-and-activation.md)。当前仍统一 YOLO，审批能力后续开发；此前“新建项目默认审批模式”的建议未采用。

| 主题 | 已确认规则 |
| --- | --- |
| 首版计划 | Manager 在已有权限及预算内分析仓库并展示范围、改动、验收和上限；统一批准一次，由 RepoMesh 应用核对生效后启动执行，范围与上限内不逐项或逐轮审批。 |
| 审批人 | 发起人在仍具备相应项目权限时可审批自己的计划；项目管理员或获授计划审批权限的人可代审。一名有权查看完整计划且符合资格的人批准即可，记录审批人及版本，代审不扩大原发起人的 Git 权限。 |
| 默认与覆盖 | 项目管理员或有配置权限的人设置默认模式及允许范围；新 Issue 继承默认，发起人可在允许范围内另选。修改默认值只影响后续新 Issue。 |
| 运行中切换 | 符合该 Issue 计划审批资格的人可在允许范围内发起；先停止新派工，在途收尾并核对 submitted 后切换。YOLO 转审批时统一批准剩余计划，反向切换保留原待审批记录并重新判断许可，不冒充人工批准。 |
| 允许范围变化 | 不再符合新策略的已有 Issue 停止新派工、在途收尾并报告受限；保留原模式与历史，由有资格的人明确切换后继续。放宽范围只增加选项，不自动切换已有 Issue。 |

切换和策略变化保留成果、既有明确要求、拒绝决定及累计消耗；实际暂停仍按受影响上游 Project，RepoMesh 控制派工与生效。

全自动继续保留独立验证、证据要求、循环上限、有效权限及预算约束；前提不满足时如实返回受限或未完成结果。GitHub draft 转正式 PR、合并及恢复仍按既有人工职责处理；本次决定未改变交付与恢复边界，也不授权当前会话开始编码。

人工门禁指执行过程中等待用户同意的决定点。它与资源不足、缺失证据或权限不足造成的受限结果分别表达。

| 事项 | 全自动（YOLO） | 需要审批 |
| --- | --- | --- |
| 首版计划 | 在当前授权、预算和策略内自动判断许可，不等待人工批准。 | Manager 整理并展示首版计划，统一批准一次；RepoMesh 应用并核对生效后启动执行。 |
| 计划变更 | 在当前授权、预算和策略内自动判断，不弹审批或等待人同意。 | Manager 在当前会话展示具体版本、差异、理由和影响，由有权用户决定。 |
| 缺失业务规则 | Manager 选择并记录解释，继续执行和验证；不能覆盖已有明确要求。 | Manager 提出解释及影响，经人决定后用于受影响检查。 |
| 已获准范围和上限内的 Loop | 自动运行。 | 自动运行，不逐轮重复审批。 |
| 需要扩大权限、增加预算上限或放宽已明确验收条件 | 返回受限或未完成结果，不自行扩大，也不新增等待人批准的节点。 | 由 Manager 提出具体变更，必须由人决定；实际权限仍受发起人及仓库规则约束。 |
| 环境、容量或证据不足 | 保留真实原因；无人工门禁不代表条件已满足或验证已通过。 | 同样保留真实原因，不将普通执行检查一概变为人工审批。 |

两个模式都遵守固定组合证据、独立 Attempt、Worker 单活跃任务、全局容量与项目额度、有效 Git 权限，以及计划获准与生效的区分。GitHub 合并仍由人和仓库规则控制；YOLO 不授予 Agent 合并权。PR 时机及正式审查按已确认的[审查设计](../current/draft-pr-review-design.md)处理；ChangeSet 的归属与记录整合见 [ADR-0008](0008-changeset-attribution-and-history.md)，合并与恢复按已确认的 [ChangeSet 设计](../current/changeset-design.md)执行，不增设统一的交付前审批节点。

受阻分支及其他工作的处理见 ADR-0007；运行中切换模式的产品规则已确认，能力后续开发，跨交付恢复按已确认 CS12 处理，具体调用接口与执行适配待细化。

## 3. Manager 的决定工具

Manager 可通过 MCP 或工具提交需要决定的事项，包含问题、建议、影响和对应事项及版本。RepoMesh 根据模式记录决定并控制执行；需要审批时，在同一 Manager 会话呈现问题，用户回复关联到具体事项和版本。

工具入口与后台执行约束共同工作。审批状态、计划应用和任务启动不能只依靠 Manager 记得调用工具、提示词或消息约定。本文其他决定工具的形态、参数、权限校验及并发恢复仍待技术设计；后继[双入口创建机制](../current/manager-create-issue-tool-design.md) 已选定 Manager 创建／查询 MCP（`repomesh_create_issue`、`repomesh_get_issue_creation`），完整可执行 Schema 与可信传输接入尚待编制和验证，不能将已采用的工具方向重新列为未决。

用户回复表示作出对应决定，不表示计划已生效或测试已通过。应用和读回继续按 ADR-0003 处理。

## 4. Skill、计划和执行各自承担什么

| 部分 | 已确认职责 |
| --- | --- |
| 团队／验证 Skill | 描述团队职责、所需能力、执行步骤、测试方法、证据要求和上报条件，指导团队按仓库及任务组织工作。 |
| Leader／验证负责人 | 根据 Skill、仓库和当前任务，请求所需能力的 Worker，组织执行和 Agent 内部复核。 |
| 本次计划 | 将流程落实为具体工作、必检项、依赖和上限，保留版本与实际执行依据。 |
| RepoMesh | 实际分配或创建 Worker，控制容量、权限、隔离和任务启动，保存计划、决定和证据。 |

- 长期 Team 和 Leader 继续保留，执行成员和具体流程按任务动态安排。
- 优先复用合适的空闲 Worker，需要时再请求创建；请求不表示已经分配、创建成功或可以立即启动。
- 已确认的业务作者与正式验证执行者分离规则仍适用，详见 ADR-0005。
- 记录并核验本次执行使用的确定 Skill 版本，是 ADR-0009 保留的设计，随 Skill 工程恢复后细化和实施，不代表版本加载与隔离已经具备。Skill 变化影响在途计划时，相关调整继续留下版本记录并遵循 ADR-0003；不能通过改写 Skill 静默替换有效计划或验收要求。
- Worker 数量设置默认 1，调度及故障处理、身份与运行资源回收见[团队执行策略](../current/team-execution-policy.md)。Skill 工程 H1—H15 的方向已同意并记录在 [ADR-0009](0009-skill-engineering-deferred.md)，包括独立 Skill、角色组合、Issue 版本引用、维护发布和升级等规则。整个 Skill 工程按用户要求待定占位、暂不开发，实际目录及加载保证待模块恢复后细化验证；场景与静态依据见 [Skill 工程专题](../current/skill-engineering-design.md)。

## 5. 支付状态筛选场景

```text
用户 <--> Manager / 当前 issue 会话
                   |
           当前计划 + Skill 版本
                   |
          各仓 Leader / 验证负责人
                   |
           请求所需能力的 Worker
                   |
       RepoMesh 核验 -> 分配或创建 -> 启动
                   |
          执行 -> 证据 -> Agent 内部复核
                   |
               Manager 汇总
```

frontend F1 + backend B1 需要验证支付状态筛选。各仓 Team 完成业务改动，验证侧安排独立 Worker 对固定组合执行检查；定位、修复和复核在 Agent 内部按分工进行。

若需求未说明“退款订单是否仍算已支付”，审批模式由 Manager 在当前会话给出解释、建议及影响，用户决定后继续相关检查。YOLO 由 Manager 选择并记录解释后继续，记录注明决定来自 Manager，不能写成人已确认。解释明确后，仍须用实际执行证据判断通过、缺陷或阻塞；解释本身不是通过证据。

## 6. 取舍与待验证项

统一入口减少用户切换角色窗口，Skill 使执行过程能够按仓库变化；代价是 Manager 汇总、决策记录和具体执行之间必须保持准确关联。YOLO 将缺失业务规则的解释权交给 Manager，接受其可能选择不符合用户隐含预期的解释，因此保留决定来源、依据及受影响检查，便于后续追溯。

A—E、CS1—CS14、I 的主要产品规则及 J1—J3 已分别确认。当前统一 YOLO，审批能力后续开发；Skill 工程 H1—H15 方向已同意，但模块整体暂缓，见 ADR-0009。页面、创建接口及后续架构进展以[现行交接](../current/HANDOFF.md)为准；各专题保留自己的具体未决项与实现边界，本 ADR 不重复列全局“下一阶段”。

尚未验证：多事项会话的主房间、Leader 房间与原生资源/session 的映射、MCP 或工具的受控写入、动态 Worker 分配和创建、暂停后的计划应用、模式控制与资源权限约束。不能将上游原生 DAG/Loop、Manager 权限或 Dashboard HITL 当作上述要求已经得到满足的证据。

## 7. 决定来源

用户主动提出 Manager 单一交互窗口、按模式触发人工门禁和 Skill 驱动动态执行；在完整建议及 YOLO 缺失业务规则解释权说明后回复“采用，现在整理并更新文档们”，随后要求去掉废弃设计、归档过时文字和文档。原讨论稿及修改前文档见[归档索引](../archive/README.md)。

随后用户进一步确认所有新 issue 先进入独立 Manager 主房间，并由 Manager 始终承担 issue 总责；本文第 1 节与 ADR-0001 同步，旧的单仓主责例外已归档。

2026-09-08：结合锁定 AgentTeams 源码讨论后，用户确认 H1 的“独立 Skill、角色能力组合、事项工作说明”组织方式。该次只确认组织方式。用户随后同意 H2—H15，并要求将整个 Skill 模块标记待定、先不开发、保留位置；现由 ADR-0009 记录全部方向和暂缓状态，第 4 节及专题同步。

2026-09-08：讨论 I 的模式默认值时，用户回复“这个一块目前先按照全自动无卡点的来然后再开发,现在下一大步”。因此当前阶段采用 YOLO，审批能力及配置细节延后，继续 J；未采用此前默认审批模式的建议。

2026-09-08：用户随后明确继续 I 的设计讨论，并采用后续审批模式的首版计划统一批准一次规则。当前 YOLO 与审批能力后续开发的安排保留。随后用户采用发起人可自审、项目管理员或获授资格者可代审的单人审批规则；随后采用项目设默认与允许范围、Issue 创建时可覆盖的规则；随后采用运行中切换及允许模式范围变化规则，I 本轮主要规则已收口。K 页面布局和曾提出的项目私有／邀请成员建议均未确认，不作为已采用设计。
