# ADR-0010：RepoMesh 技术栈与模块化单体

RepoMesh 需要在首期单服务器范围内承载 Manager 工作区、多个 Issue 的持续协调、可追溯的交付记录和受控执行。用户已确认以下技术选型，以及按领域划分模块的 Go 单体后端、后台任务可独立运行的组织方向。本轮选型收口，下一阶段讨论具体架构；本决定不表示已经实现或通过运行验收。

## 已确认选型

| 层次 | 采用方案 | 职责及范围 |
| --- | --- | --- |
| 前端 | React＋TypeScript＋Vite | 独立前端，承载 Manager 会话、摘要、详情和图。 |
| 图展示 | React Flow | 展示节点、依赖及查看交互；具体布局算法另行细化。首期自然语言调整计划的规则保持有效。 |
| 自有后端 | Go | 承载 RepoMesh 服务端业务与控制逻辑；不要求改写 AgentTeams 或其他执行工具的运行时。 |
| 业务状态存储 | PostgreSQL | 保存 RepoMesh 归属、版本、操作及相关状态；原子登记、并发控制和恢复按既有规则实现。 |
| 后台任务 | PostgreSQL 持久队列 | 支撑工作的可靠触发与重试；具体队列库、领取和恢复机制在架构及实现中细化。 |
| 前后端通信 | REST 查询／操作＋SSE 推送 | 用户查询及提交走 HTTP，后台变化向页面推送；SSE 的采用不证明上游已提供实时事件源，也不单独保证补发和恢复。 |
| 证据与产物 | 对象存储，数据库保存索引 | 保存截图、报告、日志及构建产物等文件；保留归属、来源和可用性。具体存储产品尚未指定。 |
| 后端组织 | 模块化单体，后台任务可独立运行 | 一个 Go 后端工程按业务领域划分模块；具体模块依赖、进程拆分和启动方式在架构阶段确定。 |
| 协作及执行基础 | 沿用 AgentTeams 与首期单机容器方向 | 每个多仓项目独立实例，复用长期 Manager／Team／Leader，Worker 单活跃任务及独立 Attempt 等边界不变。 |

## 取舍及架构约束

**后续局部扩展：** 用户指定创建 Issue 时的仓库分析使用 Python 插件，见 [ADR-0020](0020-python-repository-analysis-plugin.md)。Go 继续承载业务和控制逻辑，额外允许受控 Python 分析进程；不把本条改写为原技术选型当时已包含 Python，也不替换其他技术栈选择。

采用上述组合，目的是让交互界面、长期后台协调和业务记录各有清晰职责，并控制首期部署及跨服务协调成本。Go 单体按领域组织，后台任务可以独立运行；这不合并各项目的 AgentTeams 实例、数据或权限边界。

PostgreSQL 持久队列负责可靠触发工作。按 ADR-0014／0015 的 2026-09-09 补充，仓内当轮 DAG 的建图、依赖校验和候选就绪计算复用上游，Graph／Loop 模块负责跨仓依赖、业务结果适用性与循环策略；RepoMesh 控制许可、应用和任务启动。队列任务完成不表示业务验证通过，上游任务结束也不直接表示 RepoMesh Issue 完成。具体分工见 [Graph／Loop 专题](../current/graph-loop-design.md)，本补充不改变整组技术选型。

语言和组件不会自动提供幂等、授权强制、固定组合证据或故障恢复。需在后续架构中明确模块状态归属、实际执行入口、外部结果核查及重启行为；原选型基于锁定提交的静态调研，09-09 的版本复核与后续组件／有限真实服务证据按 [Graph／Loop 专题](../current/graph-loop-design.md)分范围使用，不等同 RepoMesh 全链路验收。

软件版本、HTTP 框架、数据访问工具、UI 组件库、图布局算法、队列库和对象存储产品未在本次建议中明确选定。它们保留为后续实现细化，不据此恢复已经收口的技术方向讨论，也不默认采用未提出的库或产品。

## 决定来源

用户先回复“就用Go吧”，确认自有后端语言。随后在其余技术栈与模块化单体建议后回复：“OK其他选型我也认，你记录。选型做完了。我觉得现在要讨论的是架构设计。”因此记录整组方案已采用，当前转入架构讨论。

当前仍只授权设计与本地 Markdown 整理；`grill-with-docs` 暂停使用。Skill 工程整体占位、当前 YOLO 和后续审批开发安排继续有效。
