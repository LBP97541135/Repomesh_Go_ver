# 未来规划（比赛后）

> 定位：**当前阶段以"比赛能真实跑通"为唯一目标**。本文只记录比赛后再做的东西，
> 不参与当前排期。每条都写清"现状是什么、缺什么、为什么现在不做"。

---

## 一、部署模式：公有 / 私有

**现状**：`internal/access/deployment.go` 的部署配置里已有 `mode` 字段
（`public` | `private`，留空 = `public`），分叉点只有一处 ——
`internal/access/callback.go` 的 `organizationFor()`：

| 模式 | 新账号归属 | 语义 |
|---|---|---|
| `public`（默认，= 当前服务器） | 当场开一个自己的空间 | 谁都能登录；**每个账号各看各的**，互相看不到对方的项目/仓库/中转站 |
| `private` | 并进部署唯一空间 | 只有该组织的成员能登录；**全组织共享**项目与智能体配置 |

**缺什么（私有模式）**：
1. **登录闸**：`private` 下必须在回调里校验"这个人属于本组织"——用他的
   user token 调 `GET /user/orgs`（或 `GET /user/installations`），不在名单里
   就不建号、直接拒绝。**当前 `private` 分支只做了归属，没有闸**，
   所以现在把 mode 改成 private 等于"所有人共享同一空间"，不可上线。
2. 组织成员表 `memberships(account_id, organization_id, role, ...)` + 邀请流
   （一个账号可属多个组织时还需要"当前组织"切换与会话内的 active org）
3. 前端：组织管理页（成员、角色、邀请）

**为什么现在不做**：比赛要的是"公有部署真实可用"；私有版是另一个产品形态。

## 二、管理员体系

**现状**：`repomesh_access.accounts.is_admin` 列存在，但全仓只在一处
`SELECT count(*)` 里用过（平台就绪度统计）。没有管理员操作面。

**缺什么**：
- 账号列表 + 启停（`disabled` 列现在只能改 SQL——41 个 e2e 假账号就是这么停的）
- 踢会话（作废 `identity_generation` 即可实现）
- 审批注册（配合私有模式的登录闸）
- 平台级开关（模型供应商白名单、并发上限、feature flag）

---

## 三、会话与账号安全

**现状**：会话模型已经很完整 —— `bindings`（浏览器槽位，7 天）→
`sessions`（12 小时，`generation` 递增即作废旧会话）→ `accounts`；
令牌以 `secrets.Store` 封存（root key 在 `/etc/repomesh/root-1.key`），
孤儿版本 15 分钟后自动回收。

**缺什么**：
| # | 缺口 | 说明 |
|---|---|---|
| 1 | **会话列表 / 强制下线** | 用户看不到自己的登录设备；`sessions` 表里躺着 20+ 行历史会话 |
| 2 | **审计日志** | 谁在何时登录/切换/登出、失败原因，只存在于 `attempts` 且会过期（10 分钟）。需要一张只增不改的 `access_audit` |
| 3 | **登录限速** | `POST /api/auth/github/*` 目前没有频次限制 |
| 4 | **2FA / Passkey** | 依赖 GitHub 侧 2FA（合理）；但**改模型供应商密钥**这类关键操作值得二次确认 |
| 5 | 会话固定防护不变量 | 已有 `generation` 机制缓解，建议补一条"登录成功必换 session cookie"的回归测试 |

## 四、算力与配额

**现状**：**代码里没有任何 per-account 配额**（只有 GitHub 客户端的
rate-limit 处理 + 项目级 budget policy）。公有部署 = 谁都能登录 = 谁都能烧
MiniMax / codex 额度。

**缺什么**：每账号并发 run 上限 + 每日 run 上限（建在
`repomesh_execution.agent_runs` / `attempts` 的计数上）。

**为什么现在不做**（2026-09-19 用户裁定）：先不管，比赛优先。

---

## 五、账号生命周期

**现状**：只有 `disabled` 布尔列，没有面向用户的注销流程。

**缺什么**：
- "删除我的账号与数据"（连带销毁 `secrets` 里的令牌版本、清 discovery 批次）
- 数据导出
- 账号合并（同一个人的多个 GitHub 账号）

---

## 六、其他已知缺口（与账号相关但独立）

| # | 缺口 | 备注 |
|---|---|---|
| 1 | **账号隔离逐路径核对** | 迁移 0037 已让每账号一个空间（分家），但 31 处 `organization_id` + 79 处 `ActorID()` 尚未逐条核对；`internal/assembly/roster.go` 里还留着"未归属就退化为全部"的假守卫 |
| 2 | **技能库没有账号维度** | `public.skills` 是全局一份（`skills_name_key` 全局唯一），公有部署下别人能看到/覆盖你的技能 |
| 3 | **扫描器的令牌来源** | `reposcan` 目前读环境变量 `REPOMESH_REPOSITORY_SCAN_GITHUB_TOKEN`，未配置时匿名访问（60 次/小时）；公有部署下更合理的做法是**用登录用户自己的 OAuth 令牌**扫描他自己的仓库 |
| 4 | 仓库目录 | `repomesh_projects.repositories` 是共享目录（host+github_id），参与关系在 `project_repositories`；读接口需确认只返回本空间引用到的仓库 |

---

## 七、建议顺序（比赛后）

1. **账号隔离逐路径核对**（公有部署的核心承诺，最该先补）
2. 技能库账号维度
3. 私有部署的登录闸 + `memberships` 成员表
4. 管理员体系（账号启停 / 踢会话 / 审计）
5. 会话列表 + 登录限速
6. 算力配额
7. 账号注销 / 2FA / 数据导出
