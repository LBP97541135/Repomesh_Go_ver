## 安排顺序与投入重点

1. B04 的已授权实现已结束；后续按明确授权推进 B05、B06 采用与 B07 设计，再交实现。B05 与 B06 可共同检查配置应用和建项的并发契约；这不改变施工表中的实现依赖。
2. 提前研究 B09 的 G1／G2 与 B10 的 G3／G4。G1 对 B04—B06 做定向兼容审查，避免配置持久化后无法按 Issue 消费；不要求先完成全部 B09 才交付管理功能。B10 的源码与资源归属研究可先行，接口定稿时与 B09 对齐。
3. B11 先做方案和故障推演，等 B10 明确谁能写正式状态、怎样确认停止及撤销写能力，再定稿换图与恢复接口。B08 的验收方案随管理批次设计同步补齐。

B09—B11 最依赖跨进程、上游和恢复方面的架构判断；B04、B06 最影响近期数据与事务正确性；B05 的可能收费外发及未知恢复也应由 Astra 重点设计。B07 以契约复核为主。常规页面、已定契约的 HTTP handler、存储实现和验证执行可由 Sol 承担；新增架构问题回到对应设计责任，不在实现中擅自冻结。

### 文件与操作边界

- 开始某项设计前，列出该项可编辑文件：本项设计交付文件、上表对应唯一专题，以及必要的计划／交接链接。跨批共享专题只修改该项明确涉及的章节；架构变化时定点维护相应 ADR，保留原采用与历史证据。
- Go／TS 声明先写入设计附件，例如 `.go.txt`／`.ts.txt`，注明候选或已采用范围。纯设计任务不修改 `cmd/`、`internal/`、`web/src/`、产品迁移、依赖锁文件、构建脚本或运行配置；确需产品骨架时作为明确的后续实现工作另列。
- 默认仅做源码、文档与已有证据核对，以及文档链接／声明一致性检查。不启动服务、数据库、浏览器或容器，不发送真实模型／GitHub 请求，不读取秘密，不修改上游 checkout，不重跑历史实验，不提交或推送。
- 需要实测才能选择的协议，交付限定验证对象、方法、预期证据与资源清理范围的实验方案；在当前任务没有相应授权时保留“待运行验证”。静态推断不写成已通过。
- 达到本项交付终点后交回结果和未决依赖，不自动开始下一项、实现、外部验收或部署。若当前用户另外明确授权范围内的动作，以当前授权为准；候选仍须有明确的采用记录，不能由排期推导采用。

## 每组设计交付与实现交接

- 列明采用范围、候选、替代关系、依赖和不包含的工作，链接唯一专题；新的业务决定写回原专题，架构决定变化时维护对应 ADR，本文不复制第二套 HTTP 或存储契约。
- 说明模块职责和依赖方向、核心类型、数据关系及不可变约束。按具体用例确定事务边界、锁顺序、操作身份、版本检查和资源归属。
- 在填函数体前给出必要 Go／TS 类型及函数声明，并说明调用者、输入输出、错误、提交结果未知和恢复语义。架构性私有 helper 同样先说明职责与签名；实现中新发现的必要接口先补充并复核，不事后补签名冒充前置设计。
- 声明可先保存在明确标记状态的设计稿中。尚未选定的远期协议不放入产品包，不预铺空业务包、通用框架、占位接口或功能开关。
- 提供成功、并发、失权、超时、丢响应、重启和迟到结果的验收场景；每项写清观察依据、预期结果及未验证假设。源码存在、替身测试、真实上游实验与产品验收分别记录。
- 交接时绑定实际源码基线；工作区有未提交修改时，明确涉及文件及其内容版本，不能只写 HEAD。记录明确采用的接口版本、文件编辑归属、验证入口和未决项，由非主要实现者承担独立复核。

设计推进不自动采用候选，不启动真实付费模型请求或外部环境操作，也不解除 B02 外部暂停。Graph 仍复用上游仓内 DAG，Skill 工程继续暂缓；现有三进程和受控 Python 分析的采用边界保持。
