# 测试与验证节点设计

文档修订：2026-09-09；2026-09-12 补充 Skill 暂缓阶段的适用说明。以下原确认来源和证据边界保留。

本文记录已确认的验证节点设计，并按 [ADR-0006](../adr/0006-manager-entry-modes-and-skill-driven-execution.md) 更新 Manager 统一交互、YOLO 和 Skill 执行方式。验证范围、固定组合、证据及检查结论继续有效；这是产品设计，未完成运行验收。当前入口见 [handoff](HANDOFF.md)。

## 已确认

### 缺失业务规则按模式决定

- 审批模式由 Manager 在当前会话提出解释、建议及影响，经人决定后用于受影响检查。
- YOLO 由 Manager 选择并记录解释，继续执行和验证，不等待人工同意；记录注明决定来自 Manager，不能覆盖已有明确要求。
- 解释、决定来源和受影响检查关联相关验收及计划版本。解释明确不表示检查通过，仍需要固定组合下的有效执行证据。
- 具体边界见 [ADR-0004](../adr/0004-acceptance-rule-clarification.md)；授权、预算或已有验收条件的边界按 ADR-0003 和 ADR-0006 处理。

### Manager 展示与 Skill 执行

Manager 在关联会话中汇总目标 Issue 的验证进度、结论、缺失证据及按适用模式需要用户决定的事项，用户可由 Issue 专页查看详情。按 [ADR-0019](../adr/0019-conversation-issue-separation.md)，同一会话可关联多项，汇总必须保留各 Issue 及组合归属，不把当前打开的会话当作唯一工作目标。负责人复核和仓库定位是 Agent 内部工作，不需要人逐项确认。

验证使用 Leader 提供的 mock 数据及使用说明，记录其版本和适用检查范围；环境准备见联调环境设计。

验证流程根据当前仓库、任务及适用验收条件落实必检清单。实际使用 Skill 时，记录其来源、版本及可核对的内容；未使用 Skill 时，按下述首期适用规则记录实际工作说明和脚本。验证负责人按需请求具备能力且满足独立性要求的 Worker，RepoMesh 实际控制分配、创建和启动。Skill 不替代本次计划、固定组合或证据记录；人员职责见 ADR-0005。

**Skill 暂缓阶段适用说明：** 按 [ADR-0009](../adr/0009-skill-engineering-deferred.md) 的暂缓边界及 H4，当前可以使用授权范围内的工作说明和辅助脚本。记录实际采用的说明内容或可取得的固定引用、编写／提供来源，以及脚本对应 commit、内容版本或摘要和执行结果；没有脚本的人工操作记录实际步骤与来源。版本标识须能核对到当时内容，单写名称或“最新版”不足以复现。未使用 Skill 就如实标明未使用，不为满足表格伪造 `SkillVersion`，也不要求该引用非空。

若实际宣称使用了某个 Skill，则仍应核对真实使用内容及版本，不能将无法核对的使用过程改记为“未使用”以绕过证据要求。缺失必要执行依据时，按本页证据与结果规则说明缺口。此补充只落实已有暂缓决定，不恢复 Skill 管理、发布、分发、加载或版本隔离工程，也不把这些能力设为其他验证工作的统一前置条件。

### 证据不足时保留“暂无法判定”

- 对证据不足、尚不能确定检查结论的单项检查，保留“暂无法判定”这一结果，并列出缺失证据。仅未定位具体仓库或代码位置的情况见下一节。
- 该结果描述单项检查，不直接决定整个 issue 的状态。
- 缺少证据本身不能证明业务存在缺陷，也不能证明一定是环境或数据问题；分类原则与附件要求见下文。

示例：规则明确要求“已支付”筛选显示测试订单 P01，但 frontend F1 + backend B1 的页面为空。目前只有截图，尚未核实 P01 是否成功写入、是否处于当前账号可见范围，以及接口实际返回了什么。该检查可记录为“暂无法判定”，并列明缺失的证据。

以下仅为说明已确认含义的页面文字示例，完整布局、字段和交互尚未定稿：

```text
检查：支付状态筛选应显示 P01
验证组合：frontend F1 + backend B1
检查结果：暂无法判定
缺失证据：P01 写入与可见范围检查、接口请求及响应记录
```

### 业务缺陷判定不等待具体定位

- 当证据足以证明实际行为违反已明确的业务规则时，可以判定该项存在业务缺陷，无须等待定位到具体仓库或代码位置。
- “检查结果：业务缺陷”与“问题归属：待定位”可以同时成立。
- “暂无法判定”表示证据尚不足以确定检查结论；已经证实存在业务缺陷，仅未定位具体仓库或代码位置，不因此改记为“暂无法判定”。
- 缺陷判定与归属定位分别表达，不因结果标签自动触发派工；归属与重验职责见 ADR-0005。后续工作、循环上限、汇合与迟到结果已由 [ADR-0007](../adr/0007-graph-loop-plugin.md) 确认；插件具体协议和实现继续细化。

示例：已核实实际运行 F1 + B1，规则明确要求当前账号筛选“已支付”时看到订单 P01，相关数据与环境前提成立，操作记录却证明结果为空。即使尚未定位是前端参数、后端查询还是接口衔接的问题，也可以记录业务缺陷。该示例说明判定与定位的关系，不将示例证据清单设为所有检查的统一门槛。

```text
检查结果：业务缺陷
问题归属：待定位
依据：明确的预期、相关前提检查记录、实际结果
```

### 环境阻塞按证据证明的原因判定

- 分类依据是证据证明的原因，不仅是错误发生在启动、构建、数据准备还是页面操作阶段。
- 已证实验证前提缺失、导致无法检查时，判为环境阻塞，并指出未满足的前提及支持证据。
- 已证实候选违反约定要求时，判为业务缺陷；即使错误发生在服务启动或数据准备阶段，也适用这一边界。
- 证据不足以区分上述情况时，保留“暂无法判定”，列出待补证据。

| 场景示例 | 结果及依据 |
| --- | --- |
| 测试环境应提供的数据库没有启动，导致无法继续检查 | 环境阻塞；记录缺失的验证前提及证据。 |
| 数据库符合约定，但 B1 的迁移代码存在已证实的错误，导致启动失败 | 业务缺陷；记录候选违反约定要求的证据。 |
| 只有“连接失败”日志，尚未查明数据库、配置或候选代码的问题 | 暂无法判定；列出待补证据。 |

此处确认分类原则；通用最小证据记录和按检查类型保留的附件见下文。环境与测试数据准备职责、固定组合及清理规则见[联调环境设计](integration-environment-design.md)，结果后的流程见 ADR-0007；具体实现继续细化。

### 验证节点的通过门槛

- 约定的必检项全部具有适用于当前固定组合的有效通过证据，验证节点才判为通过。
- 逐项保留检查结果；跳过、受阻、需求待澄清或暂无法判定的必检项不能计为通过。
- 必检项尚未全部达到上述条件时，节点尚未通过；汇总保留各项结果和所有未通过原因，见下文。
- 沿用固定组合原则：组合变化后重新判断原证据是否有效。节点通过不直接表示整个 issue 完成。

示例：F1 + B1 的节点约定四项必检：已支付订单展示、未支付订单排除、清除筛选、分页保持筛选条件。前三项通过，第四项因测试数据未准备好受阻。保留前三项的通过结果，同时显示第四项的阻塞原因，节点尚未通过。这四项只用于说明通过门槛，不是全产品默认检查清单。

### 单项检查的最小证据记录

每项检查保留以下五组信息，具体附件要求按检查类型确定：

| 信息 | 必须保留的内容 |
| --- | --- |
| 检查归属 | issue、节点、检查项、Attempt、执行者和执行时间。 |
| 验证对象 | 实际运行的各仓 commit，以及环境、配置和测试数据的版本或可追溯记录。 |
| 判定依据 | 对应计划及验收条件版本、本项预期结果、实际采用的工作说明及可核对来源／内容版本；实际使用 Skill 时另记其来源和版本，未使用则如实注明。补充业务解释时保留解释和决定来源的关联。 |
| 执行证据 | 相关前提核查、操作步骤或测试脚本版本、实际结果，以及支持结论的附件。 |
| 检查结论 | 结果分类、判断理由、缺失证据；问题归属已知则记录，未知则保留待定位。 |

以“筛选已支付后应显示 P01”为例，记录需关联实际运行的 F1/B1 commit、该项预期的依据和本次执行事实，使其他验证者能够复核结论。

Manager 会话先汇总结论和预期／实际差异，详情中查看证据，并分别显示“执行者初判”和“复核状态”。验证 Worker 提交初判，验证负责人复核后采纳为节点的有效检查结果；未启用小组时由 Manager 复核。职责和例子见 [ADR-0005](../adr/0005-optional-project-verification-group.md)。按检查类型保留的附件要求见下文；完整字段结构、存储方式及交互细节仍待细化。

### 专项验证节点与验收覆盖范围

- 允许一个跨仓 issue 按验收范围拆成多个专项验证节点。
- 每个节点明确关联自己负责的验收条件和必检项，并按该范围判定通过。
- issue 层汇总各节点的覆盖情况，显式呈现尚未覆盖的验收条件；单个节点通过仅证明其负责范围达到约定要求。

示例：假设 issue 已明确要求页面支持支付状态筛选，导出结果也遵循同样的筛选条件。页面验证节点检查展示、筛选、分页及清除筛选；导出验证节点检查导出请求及文件内容。页面节点通过时，若导出尚未安排检查，issue 层仍显示这一覆盖缺口。本例不将导出功能纳入所有筛选需求的默认范围，也不决定节点间的具体 Graph/Loop 行为。

### 节点输入与必检清单

每个节点执行前，应能够明确查看以下节点说明：

| 输入 | 内容 |
| --- | --- |
| 检查范围 | 负责的验收条件，以及对应必检项、操作条件和预期结果。 |
| 判定依据 | 当前生效计划版本、验收条件版本、实际工作说明及来源／内容版本；实际使用 Skill 时另记其来源和版本，未使用则如实注明。未明确业务规则及已采用解释和决定来源分别记录。 |
| 固定组合 | 涉及仓库的完整 commit，以及实际运行版本的核对要求。 |
| 验证前提 | 环境入口、配置、测试账号及可见范围、测试数据要求和准备记录。 |
| 执行约束 | 当前授权范围、预算和时间限制，以及本节点需要提交的证据。 |

必检清单及其验收条件映射随计划版本保存，调整沿用 [ADR-0003](../adr/0003-plan-change-authorization-and-activation.md)。具体工作说明、测试脚本和实际使用的 Skill 按上述适用规则分别记录来源与可核对版本，以便复现执行依据。缺失输入明确指出，按事实判断为环境阻塞、需求待澄清或暂无法判定。缺失业务解释按模式补充，不能把 YOLO 下的解释工作固定为等待人工确认。清单由验证负责人编制、各仓 Leader 提供依据，Manager 核对并纳入计划版本；测试由验证 Worker 编写或复用并执行，结果按复核采纳规则处理，详见 [ADR-0005](../adr/0005-optional-project-verification-group.md)。未启用小组时，Manager 组织被指派的验证 Worker 起草清单并核对；本节不新增首次计划审批人或审批入口的决定。

### 按检查类型保留证据附件

通用五组最小证据信息继续适用，并按检查类型保留以下必要附件：

| 检查类型 | 附件要求 |
| --- | --- |
| 页面交互 | 操作步骤、断言结果、关键页面截图；涉及跨仓链路时关联相关请求和响应。 |
| 接口与数据 | 请求条件、响应、预期与实际差异，以及相关测试数据的前提核查。 |
| 构建、启动与集成 | 命令或脚本版本、执行结果、相关日志，以及实际运行版本记录。 |
| 环境阻塞 | 未满足的前提、核查结果及其如何阻止检查。 |
| 需求待澄清 | 存在歧义的原始要求、不同解释、受影响检查项；解释明确后记录采用内容及由人或 Manager 决定的来源。 |
| 暂无法判定 | 已获得的证据，以及还缺什么才能判断。 |

附件应足以支持对应结论。例如证明订单筛选正确，需要订单与筛选条件的检查结果，仅有 HTTP 200 不足以证明这一点。具体文件格式、存储结构与采集实现仍待细化。

### 单项结果、执行进度与节点汇总

单项检查采用以下五类结果：

| 结果 | 含义 |
| --- | --- |
| 通过 | 有适用于当前固定组合的有效证据，证明该项符合明确预期。 |
| 业务缺陷 | 已证实候选违反约定要求；具体仓库或代码位置可以待定位。 |
| 环境阻塞 | 验证前提缺失导致无法检查；原因可细分为服务、配置、测试数据或验证工具等。候选自身违反约定仍归业务缺陷。 |
| 需求待澄清 | 尚无适用的业务解释；审批模式由 Manager 请人决定，YOLO 由 Manager 选择并记录解释后继续。 |
| 暂无法判定 | 现有证据不足以确定结论。 |

测试数据阻塞归入“环境阻塞”的原因分类，Manager 汇总及详情可显示“环境阻塞：测试数据未准备好”。解释明确后依据实际检查证据形成结果，不能直接把“需求待澄清”改为通过。

执行进度与验收结论分别显示。待执行、执行中、跳过等属于执行状态，不能充当通过证据。节点保留所有未通过原因及数量，不以一个原因覆盖其他检查结果；节点只有满足已确认的全部必检项通过门槛，才判为通过。

```text
节点：支付状态筛选验证
组合：F1 + B1
执行状态：本次执行已结束
验收结论：尚未通过

必检项：4
  通过：2
  业务缺陷：1（归属待定位）
  环境阻塞：1（测试数据未准备好）
```

issue 层继续汇总各专项节点的验收覆盖情况，显示遗漏和未通过项。以上状态示例不定义完整的执行生命周期，也不代表上游接口已实现这些产品状态。

## 后续主题与实现细化

第 1 项验证输入、证据和结果原则继续有效；用户进一步确认 A—E：

- 团队成员配置、调度和故障处理见[团队执行策略](team-execution-policy.md)；Worker 数量可设置，默认 1。
- 验证小组默认不启用，修改权限和启停异常见 ADR-0005。
- 固定基线、Attempt 独立环境、Leader 提供 mock 数据、实际版本核对和清理见[联调环境设计](integration-environment-design.md)。
- 五类结果的后续工作、循环默认上限、提前停止、汇合及迟到结果见 [ADR-0007](../adr/0007-graph-loop-plugin.md)，Graph／Loop 采用插件形式。
- draft PR 创建和更新、审查门槛及反馈见[PR 审查设计](draft-pr-review-design.md)。

ChangeSet 对既有 Candidate、Delivery Combination 及交付历史的记录整合已确认，见 [ADR-0008](../adr/0008-changeset-attribution-and-history.md)；不改变检查门槛及证据适用性。创建时机、Agent 摘要及按需查证、Candidate 提交即收录且保留未接受记录的规则已确认；组合选定、状态、幂等并发、合并恢复及查询保留的 CS1—CS14 已全部确认，见 [ChangeSet 设计](changeset-design.md)；记录关联与字段示例见[结构说明](changeset-structure.md)。Skill、审批、项目配置和页面／接口的阶段状态统一见 [HANDOFF](HANDOFF.md)。验证字段、证据存储、完整执行状态机、插件接口及实现仍待细化；结果标签本身不授予新工作权限。
