# 团队成员、调度与故障处理

状态：已确认产品设计；2026-09-08 根据用户对 A1—A5 的确认记录。尚未实施或运行验收。

## A1：数量设置与动态成员

- 团队按能力要求和任务需要动态申请 Worker，优先复用合适空闲成员，需要时申请创建。
- 设置中提供 Worker 数量，默认 1。沿用 A1 建议中“并发上限”的语义，表示每个团队可同时运行的 Worker 数量，Manager、Leader 和验证负责人不计入 Worker 数量。
- 数量设置不要求预先创建等量常驻进程；空闲时可没有运行中的 Worker。它与全局容量、项目额度共同约束执行。
- 项目验证小组启用时适用同样的 Worker 数量设置；未启用时由 Manager 按已有能力、权限及独立性要求安排验证。
- 正式验证仍需由未参与本轮被测业务改动的 Worker 执行，不能因默认数量为 1 而让业务作者代替正式验证者。

## A2：容量不足时的调度

优先完成已有候选所需验证、必要诊断和收尾，再启动新 issue 的重任务；同级按等待顺序安排。所有任务受全局容量和项目额度约束，不因成员请求已经提交而跳过资源检查。

## A3：Worker 失联或卡住

先核查真实执行状态。确认旧 Attempt 已停止或失去写入能力后，再由替补 Worker 开新 Attempt。无法确认时显示执行状态不明，保留原记录，避免重复执行；替补后的迟到结果按计划和证据适用性处理。

## A4：协调角色不可用

- 验证负责人暂不可用时，由 Manager 代行协调，实际测试仍由独立 Worker 完成。
- Manager 或 Leader 故障时优先恢复原身份和已保存上下文，期间停止相关新增派工，在途工作按已有约束收尾。
- 具体暂停范围遵守 ADR-0003；不承诺上游已经支持仅暂停单个 issue 分支，也不为故障恢复创建第二个 Manager 争抢工作。

## A5：成员与运行资源的回收

成员身份、配置和经过整理的知识可以保留；空闲后释放执行资源。Attempt 副本在证据和必要产物保存完成后回收，停止进程、释放副本和删除历史记录分别处理。

资源配置界面、角色故障探测、旧 Attempt 写入能力的核查、回收时机及恢复实现仍需技术细化。这里的数量默认值不代表服务器容量已完成测量。项目配置规则见[专题](project-configuration-design.md)；Skill、审批及页面／接口的阶段状态由 [HANDOFF](HANDOFF.md)统一维护（导航修订：2026-09-09）。
