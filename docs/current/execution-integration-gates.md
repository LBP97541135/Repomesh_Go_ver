# 真实执行接入前的协议门槛

本文接续[设计审查修订](design-readiness-revisions.md)，集中列出架构和 Graph 专题已承认、尚未收口的运行协议。本文规定后续设计需要交付什么，不新增服务、通用调度器或产品状态枚举，不代表任一候选补丁已采用。

证据基础为 [09-07 调研](../agentteams-survey-2026-09-07/agentteams-api-cli-survey-2026-09-07.md)锁定的 `eeaab64391ccaec9118e84977f538aefd40720d6`，以及[当前来源记录](../../third_party/agentteams-source.json)中的 `517caff9280242a00a4d4c06365352b9e41659c6`。新增读取接口和模型配置清空语义已有后续证据；不能据此认定旧版写入旁路、取消和消息恢复问题已消失。逐项区别见[独立上游对照](../reviews/2026-09-12-design-readiness/upstream-crosscheck.md)。本轮没有更新上游或重跑实验。

## 必须形成的协议与证据

| 门槛 | 必须明确的协议 | 最小验证场景 | 当前状态 |
| --- | --- | --- | --- |
| G1：配置实际消费 | 从 Issue 固定配置引用解析到每次模型调用；明确普通讨论和目标解释前使用的配置、调用绑定时点、重启回读、秘密吊销后的处理。共享 Manager 的会话身份与模型配置选择分开。 | C1 下创建 A，应用 C2 后创建 B；交错处理 A/B 并重启，实际出站请求仍能分别证明所用配置。旧 Key 吊销时 A 阻塞，不能静默改用 C2。 | Issue 记录绑定已有候选修订；实际消费者未设计完成。 |
| G2：可信消息和工具上下文 | 首条消息创建与投递、稳定外部操作身份、输入／输出关联、可信 runtime/source/actor 授权绑定、完整 MCP Schema、能力撤销和原结果查询；普通聊天输出不能写正式控制事实。 | 请求响应丢失、重复／乱序投递、错会话回复、伪造 actor、过期 Manager 代次回写；每次只产生允许的本地结果和可核查外部责任。 | 已有本地消息／澄清五端点与控制动作设计；完整传输和工具适配仍缺。 |
| G3：正式状态写入责任 | 列清 plan_dag、delegate、submit、accept、cancel、文件同步及直接存储写入的唯一管理者、凭据和校验点；选择唯一正式写方或所有写方共同遵守的条件写机制。 | Worker 直连 REST、原生 MCP 的角色参数、shared 写入、陈旧上传覆盖 pause；受限路径必须拒绝，不能只在页面隐藏操作。 | 写入策略及必要上游补丁待选；不开放默认原生写工具。 |
| G4：运行与 Attempt 生命周期 | Controller runtime、Attempt 执行进程／容器、clone、网络／卷分别由谁创建、观察、停止和回收；稳定操作身份、领取代次、实际资源限制以及停止后写能力撤销。 | 启动已发生但响应丢失、协调器重启、租约到期旧进程仍活、取消元数据后进程继续写、停止证据丢失；未知状态不得启动替补或释放实际仍占用的资源。 | 三进程权限和原子预留方向已采用；具体执行协议和所有权矩阵未完成。 |
| G5：第二轮及多目标换图 | 选择受控 resume 后 replan，或支持 paused replan 的窄补丁；明确 submitted 成功／失败／缺证据的合法收尾、上游 Project 最终 complete 时点、跨目标部分应用记录与恢复。 | 两仓仅一仓应用成功、回执丢失、读回不符、恢复中重启、旧 Attempt 迟到、仍需下一轮却已 complete；全部必要目标核实前不恢复受影响范围派工。 | Graph 已规定业务顺序；两条上游接法未选，状态映射和恢复协议未完成。 |

G1 的存储前置见[Issue 配置绑定](issue-configuration-binding-design.md)。[Manager 配置实测 CFG-05](../../validation/agentteams-2026-09-10/reports/manager-config-live.md)证明修改共享 Manager 配置会重建运行容器；直接修改它不能实现按 Issue 固定配置。以上“最小验证场景”均为待执行要求，不是本轮测试结果。

G2 沿[消息内部设计](backend-message-clarification-design.md)和[Manager 创建工具](manager-create-issue-tool-design.md)继续细化。G3—G5 沿[Graph 的换图与恢复](graph-loop-design.md)及[架构的资源边界](architecture-design-v1.md)继续细化，不另外建立第二套正式状态协议。正式运行协议应在各唯一专题落盘后回链更新本表。

## 放行顺序

1. 先落实 Issue 配置关联记录，再验证一个有可信身份、固定调用配置和可恢复关联的真实会话往返。记录保存成功、传输成功、模型接收和控制动作生效分别有证据。
2. 收口 G3、G4 后验证单仓单轮的受控派工、结果提交、实际停止与资源回收。复用原生 DAG，并覆盖真实旁路入口。
3. 收口 G5 后验证单仓两轮及双仓部分失败恢复，再接完整执行页面和业务完成判断。

实现者不能用“先在本地成功一次”跳过该阶段已有的未知／重启分支，也不必等待高级页面全部设计完成才开发管理切片。未接入处理器保留真实待办及未接入原因，不伪造 ready、派工成功或 Issue 完成。
