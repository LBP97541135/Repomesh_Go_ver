## 2. 总体结构与进程职责

后续采用 [ADR-0020](../adr/0020-python-repository-analysis-plugin.md)：保留以下三类 Go 进程，并增加可选的受控 Python 仓库分析进程。分析作业在建项前由后台协调管理，受限主机执行入口负责运行和回收；无须先准备 AgentTeams。详见[创建 Issue 仓库分析](issue-creation-repository-analysis.md)。图中增加的是分析调用，Go 业务归属和 Graph 进程内运行保持。

三类进程的职责和同工程、配套发布方向已确认，见 ADR-0013。下图中的具体监听入口、内部调用和凭据分配仍需细化。

~~~text

       |
       | REST 命令与查询 / SSE 变化通知
       v
RepoMesh Go 后端工程：统一领域规则、同一发布版本
  |
  +-- Web 进程：用户入口、查询、Agent 内部工具入口、SSE
  |
  +-- 后台进程：持久任务、短轮协调、调度、采集与结果核查
  |       |
  |       +-- PostgreSQL：业务记录 / 待处理工作 / 事件与操作历史
  |       +-- RepoMesh 证据对象存储：正文 / 报告 / 归档
  |       +-- GitHub 受控读写：任务分支、draft PR、外部状态观察
  |       |
  |       +-- 项目 A 的 AgentTeams Adapter
  |       |      Controller A / Matrix A / Storage A / Gateway A
  |       |      Manager A / 每仓 Team 与 Leader / Worker
  |       |

  |              Controller B / Matrix B / Storage B / Gateway B
  |              Manager B / 每仓 Team 与 Leader / Worker
  |
  +-- 主机执行模块的受限进程：实例环境、Attempt 环境、停止与回收
          |
          +-- 受校验的容器、挂载、网络、资源配置
          +-- 各 Attempt 独立 clone、构建目录及验证环境
          +-- 受控 Python 仓库分析进程：只读固定材料 -> 建议与证据
~~~

首期将 Web 与后台协调分别运行，属于同一 Go 工程、配套版本一起发布。后台进程可包含多个有限并发的任务处理循环，不按业务模块再拆出一组网络服务。实例准备和构建等待以持久状态推进，不占住一个 HTTP 请求。具体数据库迁移及启动停止顺序待细化。

主机执行模块因接触容器引擎，采用额外的最小受限进程。它只接受已登记且核验过的实例／Attempt 操作，以及 ADR-0020 的分析作业操作；不提供任意宿主命令或任意挂载入口。公开 Web 进程和 Agent 均不持有 Docker socket。Controller 继续管理其负责的 Agent runtime；主机执行模块处理明确分配给它的环境操作，同一容器只能有一个生命周期管理者，具体资源明细仍需核查。

**原因与代价：** Web 单独重启时后台可继续推进已持久登记的工作，主机权限集中管理；代价是维护多个进程及内部调用权限。整机故障仍会影响同机进程，后台重启后需要核查真实状态，进程划分不自动提供高可用或防重复执行。它们仍一起开发和发布，不要求首期承担独立微服务版本协调。

RepoMesh 的证据存储和各实例的协作存储分工不同。AgentTeams Storage A／B 仍分别保存各实例的共享工作材料；正式提交的必要证据由 RepoMesh 核验并归档。不能以采用一个对象存储产品为由，把既定的独立实例存储悄悄合并。

## 3. 建议的领域模块与状态归属

表中模块是代码和规则的组织方式，不意味着每行一个进程，也不是数据库表设计。

| 模块 | 负责的规则与正式记录 | 主要交互 | 为什么这样划分 |
| --- | --- | --- | --- |
| 项目与访问 | 项目配置、仓库集合、账号和授权关联、有效操作范围、额度及模型配置引用。 | 所有命令和读取核验当前访问范围；实例和调度读取有效配置。 | J1—J3 的权限规则集中维护，避免页面、Agent 工具和后台各算一套。 |
| Issue 与会话 | 独立会话、消息及投递记录；Issue 与内部仓库事项、来源关联、主／Leader 房间关联及协调轮次。 | Manager 受控 MCP／页面明确创建时同事务建立 Issue、主 ChangeSet、来源、幂等结果及待办；实例与房间实际就绪后投递或接手。 | 会话可先后关联多项，来源会话不替代各 Issue 的计划、执行目标和工作归属；仓库事项粒度继续设计。 |
| 计划与编排 | Plan Version、许可、应用进度、逻辑 Task、跨仓依赖、循环累计状态、验收覆盖。 | Manager／Leader 提交工作安排；结合上游候选就绪观察调用 Graph 模块；向调度提出执行请求。 | 仓内 DAG 复用上游，业务计划、结果采纳及执行约束留在 RepoMesh；获准、生效及执行分别核查。 |
| 调度与 Attempt | 排队、Worker 占用、全局容量、项目与团队额度、Attempt、启动／停止／替补过程。 | 使用计划、授权和实例就绪信息；通过执行 Adapter 准备并启动；回报执行事实。 | 单 Worker 单任务、独立副本与重复启动是同一组需要原子约束的问题。 |
| 验证与证据 | 必检项、实际组合与环境清单、作者独立性核对、五类检查结果、初判与复核、证据适用性及文件索引。 | 使用交付模块选定的组合；请求独立验证 Attempt；将有效结果交给编排和交付。 | 执行结束不等于检查通过；证据是否适用需要明确的业务规则。 |
| ChangeSet 与交付 | 主 ChangeSet、Candidate、初审关联、固定 Delivery Combination、PR 关联、检查与合并观察、完成条件和恢复关系。 | 接收正式候选、Manager 组合选择及验证结论；通过受控 GitHub Adapter 执行动作或核查状态。 | 稳定变更归属和远端交付连续存在，多次修复不会生成互不关联的结果。 |
| 实例与运行接入 | 每项目实例映射、资源身份、服务就绪、上游 Project／Task 映射、通信及生命周期适配。 | 向调度提供运行能力；执行已获准的基础设施动作；采集上游观察交还记录所属模块。 | 把上游字段差异、就绪过程和版本兼容集中起来，不让业务代码到处依赖 Controller DTO。 |

持久队列、操作记录、事件收件记录、数据库事务和对象存储访问是共享基础设施。读取摘要是面向页面和 Agent 的查询组织方式；它读取上述模块的记录，不成为另一个能直接改业务结果的模块。

建议由应用层组织跨模块用例：同进程通过明确的函数调用复用规则；需要可靠后续处理时写持久工作记录。一个模块不直接更新另一个模块拥有的业务记录。创建用例共享数据库事务，原子保存必要会话、Issue、主 ChangeSet、来源、输入快照、幂等结果及相应待办／事件；具体范围以创建契约为准，不因为模块分开就拆成多次提交。

## 4. 正式状态、上游事实与读取视图

建议 PostgreSQL 保存 RepoMesh 的正式业务状态；同时保存带来源和观察时间的上游事实。以下三个层次分开：

| 层次 | 例子 | 写入规则 |
| --- | --- | --- |
| RepoMesh 业务决定及版本 | Plan V2 获准、尚未生效；C2 由 Manager 选定；某项初判经复核采纳。 | 通过所属模块校验角色、目标版本和适用范围后记录。 |
| 外部及运行事实 | Worker 实际 phase；某 Attempt 进程仍运行；GitHub PR 当前 head 或合并结果。 | 保存来源、时间和关联对象；外部事实改变时追加观察，不让本地期望覆盖现实。 |
| 摘要和图 | 执行结束、验证未通过、backend 已合并；计划图及阻塞原因。 | 从记录汇总，携带修订信息和来源；Manager 的自然语言解释另注明其判断来源。 |

建议采用普通业务记录加追加历史的方式。查询可以使用同一 PostgreSQL 中的关联查询和可重建摘要；无需为了保存历史先建立完整的事件溯源框架。必要审计记录长期保留，面向 SSE 的短期重放记录可有不同保留策略。

上游 Project 保留自身执行状态和协作材料。对 RepoMesh 而言，它是执行映射及观察来源；不能凭它的 complete 或一条聊天中的“完成了”，更新 Issue 的交付完成状态。观察冲突、材料缺失或采集间断都明确记录。

## 5. Issue 到 AgentTeams 的映射（方向已确认）

已采用按“每条 Issue 的仓库委派范围”建立上游 Project，验证工作有明确执行范围与归属。不同 Issue 不共用一个长期上游 Project；跨仓依赖保存在 RepoMesh 整体计划中。正式决定及理由见 ADR-0012。不同 Issue 仍共享团队 Worker 并发额度、项目额度和全局容量，不因记录分开各获一份额度。

~~~text
RepoMesh Project：订单系统
  +-- AgentTeams Instance：订单系统实例
  +-- 长期 Manager M
  +-- frontend Team / Leader
  +-- backend Team / Leader
  |
  +-- Issue RM-42 / 主 ChangeSet CS-42 / Plan V1
        |
        +-- 来源会话 -> 该会话实际关联的主房间
        |               可同时关联其他独立 Issue
        |
        +-- frontend 委派范围及实际 Leader 房间关联
        |     +-- frontend Leader / Worker 的执行上下文关联
        |     +-- 上游 Project（frontend Team，RM-42 前端委派范围）
        |
        +-- backend 委派范围及实际 Leader 房间关联
        |     +-- backend Leader / Worker 的执行上下文关联
        |     +-- 上游 Project（backend Team，RM-42 后端委派范围）
        |
        +-- 验证执行范围
              +-- 固定 C1 = frontend F1 + backend B1
              +-- 上游 Project（实际承载团队，RM-42 验证范围）
              +-- 独立验证 Attempt 和必要的专用验证房间
~~~

每个上游引用至少能确定实例、team、project_id，以及对应 Issue 和委派范围；Task／Attempt 进一步关联真实上游 task 身份。这里不冻结编码格式，也不新增独立的 IssueRun 产品实体。

以下保留具体落地建议；验证范围挂到哪个上游 Team／Project、版本复用和 Task／Attempt 映射仍待细化。图不要求每条 Issue 独占主房间或一个 runtime session；Leader 房间共享粒度及各角色上下文隔离、恢复仍待适配验证：

- Manager 主房间不强制再制造一个跨仓上游根 Project。RepoMesh 计划已保存全局依赖，避免两个根计划各自推进。
- 上游 Project 与对应 Issue／仓库委派范围及实际 Leader 房间显式关联，以便 Leader 收到本仓通知；归属不从房间标题猜测，也不把仓库事项自动等同于上游 Project。
- Plan Version 更新通常复用同一委派范围的上游 Project，保留每次应用与读回记录；不为每个版本或重试复制完整团队。
- 普通 Task／Attempt 使用已核验的执行上下文和房间关联；具体房间复用粒度继续设计。必要的验证专用房间登记所属 Issue 和结果回流目标。
- 验证小组启用时，可映射到一个专用的上游技术 Team，固定负责人承担其协调角色；它在产品上仍是验证小组，不拥有业务仓。关闭时由 Manager 组织，验证任务挂到实际承载执行者的团队及独立验证范围，不偷偷启动常驻验证小组。具体团队成员兼容性待契约验证。
- 逻辑 Task、循环轮次、Attempt 与上游 Task 的映射显式保存。新 Attempt 不覆盖旧执行；上游是否需要新 task_id 及各状态迁移须按 taskflow 契约落实，不能假定原任务复位就是一次独立尝试。

**原因与代价：** 一个上游 Project 只承载一条 Issue 的明确范围，减少重规划影响其他 Issue 的机会；代价是一个跨仓 Issue 需要协调多个上游对象。它不意味着上游具备任意分支暂停能力：某范围发生 replan 时，仍暂停该完整上游 Project；若技术映射实际产生共享范围，按真实影响扩大暂停，不能按页面图上的分支推断隔离。

## 6. 实际执行入口：需要补齐的核心模块

本节受控适配的方向已由用户采用，见 ADR-0011；下述三条接入路径、身份传递、启动授权和防护的具体实现仍需细化与验证。

### 6.1 三条接入路径

| 路径 | 复用能力 | RepoMesh 新增的职责 |
| --- | --- | --- |
| Controller REST Adapter | 资源创建和读取、ensure-ready/status/wake/sleep、Project 观察及 pause/replan 等有限干预。 | 选择正确实例、窄字段转换、独立操作标识、超时核查、409 后重判、写后读回。 |
| Matrix 通信 Adapter | 建房、邀请、消息发送、同步接收。 | 持久化房间和 Agent session 归属、消息去重、投递状态、结果路由及授权过滤。 |
| 运行时工具桥接 | TeamHarness 本地 MCP 的计划和 taskflow 语义、提交及协作机制。 | 把 Agent 提议转换为 RepoMesh 业务命令；实际委派和执行前校验已登记的许可与占用，收集结构化结果。 |

运行时工具的受控接入方向已采用，桥接的具体形式是本稿提出的实现建议，不是 AgentTeams 已有的远程 HTTP 任务服务。Agent 侧可以使用本地 MCP 工具接入 RepoMesh；后台触发的已授权委派由受控执行端落实。需要核对具体 runtime 的扩展点，必要时维护小范围 TeamHarness／runtime 补丁。不能把自然语言“请启动任务”作为可靠执行协议。

### 6.2 业务判断与实际动作

~~~text
Manager / Leader：提出明确计划、任务或资源需求
        |
受控工具桥接：带来源身份、房间上下文、操作标识
        |
RepoMesh：校验归属 + 当前权限 + 有效计划 + 预算与依赖
        |
调度模块：原子占用 Worker 和所需容量，登记 Attempt
        |
运行接入：确认 Ready，准备独立环境，核验本次启动授权
        |
实际启动 -> 记录回执 -> 采集执行事实 -> 提交候选与证据
~~~

建议每次启动绑定 Issue、Task、Attempt、有效 Plan Version、Worker、允许操作范围和本次占用的代次。代次用于让旧执行的授权失效：后台换负责人或旧 Attempt 被隔离后，受控执行端拒绝旧代次的新动作。它不是由 Agent 自己填写就能生效的字段，也不代替实际停止进程。

Manager／Leader 仍负责业务拆解和判断；后台对普通可靠性事件可直接核查和重试，不必每次调用模型。业务结果到达后再触发对应 Issue 的短轮协调。同一 Agent 在同一 Issue 的协调轮次顺序处理，不同 Issue 分开排队；首期可保守串行调用同一长期协调者，而让不同 Worker 的业务执行并行。

### 6.3 防止旁路的实施要求

仅新增一层工具包装，而保留 Agent 直连高权限 Controller、任意改共享计划文件或持有完整 Git 凭据，不能满足本方案。

建议将实际防护落在以下位置：

- Controller 管理凭据只供可信接入路径使用；Agent 必需的自身状态上报和通信能力通过有限路径保留，禁止借上游 Manager 角色直接创建、重规划或绕开派工。
- TeamHarness 的控制状态写入由受控路径执行。Agent 不持有可任意覆盖正式计划／任务记录的共享存储凭据或可写挂载；提交材料区与已接受记录分开授权。
- Git 通过受控操作执行，只允许当前任务拥有的分支和允许动作。App 私钥和宽权限安装凭据不进入 Agent 工作区；产品上的“Agent 推分支和开 draft PR”仍成立，实际请求由校验过的路径完成。
- 容器、工作副本与验证网络由可信运行模块准备。Agent 不可通过宿主 socket、任意挂载或其他成员工作目录绕过 Attempt 隔离。
- 工具调用者身份、房间和有效执行上下文由可信接入路径核验。长期 Manager 的凭据不因为能访问多个 Issue，就允许仅凭模型填入的 Issue ID 执行任何动作。

这些要求可能涉及上游工具、启动配置、网络及存储授权的配合修改，必须通过旁路测试验证。REST DTO 没有暴露全部挂载、环境和权限字段，不能声称只靠现有 Worker POST/PUT 就能完成。

**原因与代价：** 已确认的权限上限、Worker 单活跃任务和计划许可必须在动作发生处执行；代价是维护受控适配，并验证不破坏 AgentTeams 的心跳、唤醒和协作机制。若某运行路径无法约束，先标记该能力不可用于正式执行，不把提示词遵守率当作保证。

## 7. Graph／Loop 插件与计划应用

### 7.1 复用上游 DAG 与进程内协调（已确认）

2026-09-09 用户采用“按最新版本复用上游 DAG，不重写全部能力”。详细能力分工、版本和证据统一见 [Graph／Loop 专题](graph-loop-design.md)，决定见 ADR-0014／0015 本日补充。TeamHarness 提供仓内当轮 DAG 的建图、依赖／环校验、候选就绪计算与任务状态能力；RepoMesh 不另建完整仓内 DAG 引擎。

Graph 模块仍在后台协调进程内运行、随 Go 后端发布，负责跨仓前驱、业务结果适用性及 Loop 判断。后台经上游执行 Adapter 获取带来源的原生 DAG 观察，结合有效计划、固定组合、已采纳结果和累计进展调用 Graph，再核验实际派工。计划、轮次和累计消耗持久化，重启核查后恢复。具体 Interface、观察修订、注册和兼容方式继续细化，不确定动态加载机制。

插件不持有 GitHub、Controller、Docker 凭据，不直接派 Worker，也不自行批准计划。远端调用和任务委派由后台及执行 Adapter 执行。原生 ready 仅提供候选节点，assigned 节点再次出现也不构成新派工；跨仓前驱、业务采纳、计划、权限和占用仍须核验。上游观察陈旧或模块异常时先核查并停止受影响的新推进，不以本地替代引擎静默继续。

前端 React Flow 消费后端汇总的业务节点、依赖、版本和状态，可展开上游任务及 Attempt，负责查看交互和布局。workflow 的压缩状态不能直接作为完整业务状态。页面拖动位置不改变依赖；自然语言修改仍由 Manager 形成相应安排或计划变更，直接编辑图延后，图查询与推送契约继续细化。

**原因与代价：** 独立模块保留测试和替换位置，进程内调用减少一个独立服务及通信维护成本；代价是插件版本随后端发布，严重故障可能影响后台，缺少独立进程的故障隔离。需要处理异常、兼容性与恢复，不能声称所有插件故障都被隔离。具体方法、格式和兼容策略尚未冻结。

### 7.2 上游工作流的使用方式（轮次映射方向已确认）

按 [ADR-0015](../adr/0015-round-scoped-upstream-dags.md)，上游 Project 承载本团队当轮 DAG 并提供原生候选就绪计算；RepoMesh 管理全局依赖、业务采纳与 Loop，后台核验后实际派工。不能删除跨仓边后让上游直接放行，也不能以原生 completed 替代当前组合的有效验证结果。上游不获准自主启动下一轮。

首期已采用把当前获准轮次映射为有限 DAG 工作，暂不依赖 Controller replan 能重写原生 Loop。授权范围内的下一轮属于既有计划的执行进展，无需新建 Issue、Manager 或业务 Plan Version；改变目标、范围或上限等仍按计划变更规则处理。轮次及上游安排的更新与业务 Plan Version 分开，新 Attempt 不覆盖旧执行。具体轮次物化、上游 task 标识和镜像修订格式仍待细化。

若下一轮需要 replan，同样遵守完整受影响 Project 的停派工、在途收尾、submitted 核对和读回条件。paused 不能直接 REST replan，completed Project 也不能假定可原地重开；受控衔接方案及最终关闭时机按专题继续设计。是否可用其他已验证路径减少重写，留给契约验证，不承诺原生动态追加。

修复 3 轮、诊断 2 轮、环境恢复 2 次继续写入具体计划；预算和时限先到先停。建议对同一工作目的的循环保留连续计数和累计消耗，换计划或重命名节点不能清零。队列传输重试、业务 Attempt 重试、业务修复轮次分开记录；是否真正开始新一轮由业务事实判断，不能用反复重试绕开上限。

“相同失败且无新增有效证据”的判断保留失败依据和证据引用，由负责协调／复核的角色提供可追溯判断，系统执行连续两轮停止的规则。不能仅把两段日志字符串相同当作完整业务判定。

### 7.3 计划变更应用流程

按受影响上游 Project 收敛、保留各目标实际应用结果、全部必要目标一致后才宣布整体新版本生效的行为已在 ADR-0003、ADR-0012 确认。下面的操作记录、事务与恢复实现继续细化。

~~~text
Manager 提出 V2，注明依据 V1、变化和原因
  |
保存不可变提案 -> YOLO 核验许可 -> 已获准，待应用
  |
确定受影响的上游 Project 集合
  |
RepoMesh 持久关闭该集合的新派工入口，必要时配合上游 pause
  |
核查在途执行与 submitted，按真实结果收尾
  |
通过已验证的受控衔接更新各目标，不能直接 pause 后 replan
  |
逐目标读取最新状态 -> 应用安排 -> 权威读回核验
  |
全部必要目标一致 -> 原子记录 V2 生效 -> 恢复允许的派工
~~~

候选衔接仍是门禁持续关闭时 resume 后 replan，或支持保持 paused 的受控 replan 补丁；本次复用方向不替两者作实现选择。当前轮次技术改图沿用相同核查流程，但只更新安排修订，不据此生成新业务 Plan Version。正式元数据的所有可达写路径须遵守统一写入责任或版本条件，不能只依赖 REST ETag。

建议为每次应用保留目标清单、输入摘要和各目标结果。多目标应用不具有跨系统原子性：前端成功、后端失败时，显示部分应用及原因；受影响范围保持停派，不发布 V2 已生效，也不盲目继续已被改写部分的 V1。其他未受影响且仍有效的工作按既定规则继续。

恢复时核对每个目标的实际状态，重新判断原许可和输入是否适用，再完成剩余应用或形成明确的恢复安排。409 后重新读回，不覆盖竞争写入；不通过把 submitted 强行改成通过来满足 replan 条件。上游任务的执行收尾、候选接受和业务验证通过分别记录。

**原因与代价：** 这是对上游 replan 限制和多仓写入非原子性的直接响应；代价是新计划获准后可能需要等待收敛，且需要维护应用过程记录。整体 Issue 不因技术性等待变成人工审批流程。

## 8. 持久任务、并发和故障恢复

### 8.1 业务记录与后台待办同事务保存（已确认）

按 [ADR-0016](../adr/0016-transactional-background-work.md)及[创建契约](issue-page-create-api-contract.md)，必要会话、Issue、主 ChangeSet、来源关联／创建记录、确切输入快照、幂等创建结果和相应待办／持久事件在同一个 PostgreSQL 短事务中保存。首次提交返回 201，同键同输入的已提交重试返回 200 及原身份；回执只证明已提交，当前准备情况通过详情／房间查询取得。逻辑创建身份、规范化比较及权限边界已由契约规定，表结构、锁和恢复实现继续细化。

具体实现可按队列库能力选择：支持加入业务事务则直接事务入队，否则同事务保存待发送记录，再可靠转交。具体库和实现路径尚未选定；已确认的边界是业务与待办一起持久化，不能先提交 Issue，再仅靠一次内存通知安排后台工作。

后台在事务提交后领取待办，核验目标修订和当前有效约束，执行并保存结果；外部请求超时或重启后结果未知时，先核查实际状态，复用原操作与归属。数据库事务和行锁不跨越模型、GitHub、Matrix 或容器启动的网络等待。短任务拆分、后续采集触发和具体恢复算法仍待细化；该事务不保证跨系统原子性或外部操作只执行一次。

PostgreSQL 的 SKIP LOCKED 可用于多个消费者领取队列记录，但不适合作为一般业务一致性读取；它也不自动保证业务公平性或一次执行。[PostgreSQL 锁定子句](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)。具体队列库仍未选定。

### 8.2 三种占用不能混为一谈

| 记录 | 保护什么 | 失效后怎样处理 |
| --- | --- | --- |
| 后台队列处理权 | 某个进程正在处理这条短后台任务。 | 可以重新领取，但先核查原逻辑操作结果。 |
| Worker 与 Attempt 占用 | 哪个 Worker 正在为哪个 Attempt 工作。 | 不因心跳超时就立刻当作空闲；先隔离或确认旧执行停止。 |
| 实际运行资源占用 | 正在消耗的 CPU、内存、磁盘和执行槽位。 | 只有确认进程或环境已停止、资源已释放才回收容量；授权失效不等于进程已消失。 |

按 [ADR-0017](../adr/0017-atomic-attempt-resource-reservation.md)，已采用在短事务中统一登记 Attempt、Worker 占用和所需容量预留，核对团队、项目与全局约束。竞争同一资源的请求不能同时分配成功，未取得资源的工作等待并展示原因。事务提交后准备独立环境，真正启动前再次核验有效计划、权限和占用。准备失败先核查实际环境再释放可释放的占用，超时不视为资源已释放。具体校验数据、事务隔离、占用代次、执行端协议和恢复算法仍待细化。

同一逻辑操作重试复用标识和输入；输入不一致拒绝。同一目标的冲突修改串行化，并检查预期修订；跨目标锁定顺序固定，降低死锁和不一致分配风险。首期调度可以只有一个主调度循环，但正确性仍由数据库约束保证，不能只依赖“现在只有一个后台进程”。

资源优先级沿用 A2；同级按等待顺序选择。Manager、Leader、验证负责人不计入团队 Worker 数量，但它们的模型调用、常驻内存及实例基础开销仍计入预算与全服务器容量。集成环境按实际多服务需求申请资源，不只占一个抽象 Worker 名额。

### 8.3 预算和时限需要实际执行路径

建议模型调用、Attempt 启动及环境恢复共用累计用量记录，启动前为可界定的消耗作预留，回执到达后核对实际用量；并发请求不能分别依据同一份剩余额度放行。模型出口与执行端需要执行限制，后台观察到超限后才提示不足以保证既定上限。

外部提供商的用量回报可能滞后，单次请求的成本上界、取消能力及未报告用量须验证；能力不明时保留预留和未知消耗，不承诺精确到分的实时费用控制。具体核算口径和容差需要单独设计，不能自行提高用户上限。时限到达停止新动作，并按实际可执行的停止机制处理在途工作、保存结果及核查未决调用。

### 8.4 关键异常的建议处理

| 异常 | 建议系统行为 | 理由 |
| --- | --- | --- |
| 首次会话消息或页面建项并发准备同一项目 | 复用原项目实例准备操作，分别保留逻辑操作、业务会话及实际房间关联；已有有效房间复用。 | 防止重复创建实例及 Manager，不按每条 Issue 复制会话房间。 |
| 建房请求超时 | 查已登记的外部操作、房间标记或别名并核验归属；无法确定时保留未知。 | Matrix 发送消息的事务 ID 不意味着 createRoom 自动具备同等幂等保证。 |
| Worker 创建成功但尚未 Ready | 保存已受理状态，继续观察 phase、ready、身份和必要工具。 | 避免 POST 成功后立即派活；Controller 重启后重新核验 ready。 |
| 启动请求超时或后台重启 | 按 Attempt 和运行引用查询真实执行，确认未启动才重试。 | 避免第二次请求启动另一个业务进程。 |
| Worker 失联 | 保留占用，核查进程；旧执行已停止或失去有效写入能力后才允许替补。 | 租约过期或数据库代次改变本身不能杀掉旧进程。 |
| 旧 Attempt 迟到提交 | 保存原归属的提交／观察及证据，标明已被替代；不覆盖当前结果，不直接解除依赖。 | 同时保证历史和当前执行正确。 |
| draft PR 创建超时 | 以仓库、任务分支和对应操作核查已有 PR，匹配后复用；无法判定则不盲目再建。 | 本地事务无法让 GitHub 对象创建跨系统只发生一次。 |
| backend 权限失效 | 拒绝相应新动作，撤销受控路径的许可，处理受影响运行和上下文；frontend 无关且仍获准的工作继续。 | pause 不停止在途，不能代替 J3 的实际拦截。 |
| 数据库暂不可用 | 停止新派工和需要在线许可的新外部写入；在途按已落实的有限授权与停止机制处理。 | 不能在无法核验归属和约束时凭内存无限执行。 |
| 采集出现历史缺口 | 保存当前核查状态及缺口，补查可取得的材料；不能补齐则明确不可追溯部分。 | 上游有限历史不能保证离线期间所有中间变化都可恢复。 |

权限撤销检测建议由相关外部通知、敏感操作前核验和后台定期检查共同触发。具体通知覆盖和缓存期限待验证；不承诺能即时获知 GitHub 的所有权限变化。已发出的外部请求需要核查实际结果，已读进模型上下文的数据也不能声称自动收回。受影响会话应停止继续使用无权内容，并从当前可授权的材料恢复；Manager 身份仍复用。恢复权限不自动复活已经结束的 Issue／Attempt。

## 9. 验证、证据与 GitHub 交付

### 9.1 固定对象及独立验证

Leader 初审有范围和自测记录的业务候选，形成首个符合条件的候选后即可创建 draft PR。Manager 从已接受候选和未修改仓库的固定基线中选定正式组合。验证模块核对作者独立性和必检清单，调度模块分配实际满足条件的 Worker。

每个验证 Attempt 准备自己的代码、服务、配置和数据；Leader 提供运行说明及 mock 数据使用方法。执行前保存实际运行的 commit、产物和环境清单，并与目标组合核对。验证者只获得必要读取和验证产物写入能力，业务修复交回对应 Team。

Worker 数量默认 1 指并发上限，不等于只能永久拥有一个 Worker 身份。业务作者结束后可以由另一名合适成员在同一并发上限内执行正式验证；无合适执行者时记录真实等待原因，不让作者自证替代独立验证。

### 9.2 文件正文与正式记录

建议对象存储保存正文，PostgreSQL 保存归属、摘要校验信息、版本、产生者、来源和可用性。正式提交 Candidate 时登记候选及附件引用；附件尚未确认可用时如实标注，不因为收录就判定候选接受或验证通过。

文件先进入本次 Attempt 的提交区，可信归档过程核对完整性并固定到不可被执行成员覆盖的位置，再将索引记为可用。数据库与对象存储不存在本地原子事务，上传成功但索引未完成、索引存在但文件缺失都要有核查过程。过期未引用临时文件按规则清理，必要证据保存前不回收唯一工作副本。

同一 commit 组合换了配置、mock 数据或验收依据，建立新验证记录并重判证据；代码版本变化建立新组合。初判、复核采纳、证据复用依据和之后的更正分别保留。历史报告缺失正文时不能继续展示为当前仍可复核的有效证据。

### 9.3 受控交付与真实合并观察

建议 GitHub Adapter 只暴露产品所需操作，由交付模块检查操作意图和当前授权：读取指定仓库状态、受控推送本任务分支、创建／更新关联 draft PR、读取相关检查和合并结果。是否允许取消尚未合并 PR 按已有明确取消指令和 CS12 处理；首期不提供自动合并、转正式 PR、改规则或外部 Issue 写入能力。

有效范围同时受用户、App 安装、项目接入、当前 Issue／Task 和具体操作约束。自己的分支需要由后端登记并验证，写入时核对目标引用和预期 head；仅从分支名推断归属不够。App token 的仓库权限不被当作“只允许推本分支”的技术保证，具体 Git 数据通道与权限核验需专门验证。

Manager 推荐正式审查前核对适用验证、内部复核和必需仓库检查。人转正式 PR、人按仓库规则合并；RepoMesh 读取实际 head／合并结果并保存观察。通过分支名称、PR 号或旧 head 的检查不能证明实际合入组合有效。

部分合并时保留成功部分，以实际版本推进剩余工作。完成判定由 CS9 的条件产生：交付物、验收及必做事项完成，必需 PR 已人工合并，最终实际组合证据有效。部署及数据恢复继续独立记录；已合并代码撤销由人发起关联恢复事项，不自动补偿回滚。

**原因与代价：** 验证和交付可以独立表达进度并保持连续溯源；代价是保存多轮组合、证据及远端观察，不能用一个 success 字段简化全部流程。

## 10. 前端查询、推送与 Agent 查阅

建议浏览器只调用 RepoMesh；每实例的 Controller、Matrix 地址及管理凭据不直接提供给前端。Agent 查阅摘要和证据也经过同一套范围校验，默认当前 ChangeSet，按需查同项目相关历史。

前端数据按使用目的组织：独立会话、Issue 详情、执行／验证／交付摘要、指定版本图、节点或 Attempt 详情、候选／组合／证据／PR 历史。创建条件、创建／核查、Issue 最小详情、房间查询及 Issue SSE 的路径和字段以[创建契约](issue-page-create-api-contract.md)为准；其余列表、消息和工作详情协议继续设计。A／B／C 旧布局已否定，当前页面方向见[会话与 Issue 专题](conversation-issue-separation-design.md)。

建议更新路径为：

~~~text
Agent 结构化结果 / Matrix 消息 / Controller 查询 / GitHub 观察
        |
去重并保存来源 -> 所属模块核对并更新记录
        |
同事务保存变化记录 -> 更新可重建摘要
        |
SSE 通知页面哪些快照需要重新查询
        |
页面按需查询摘要、图和明细
~~~

Matrix 建议通过服务端同步游标接收消息；先持久化事件及归属再推进游标，防止游标已前进而消息未保存。不能把所有内部房间消息自动当作 Manager 对用户的回复。

Controller 的工作流和运行状态先采用服务端按活跃对象查询、操作后读回和故障后补查。GitHub 的通知可作为加速线索，关键状态再查证。上游没有完整事件源不妨碍 RepoMesh 向浏览器提供 SSE，但推送时效受实际采集路径限制。

Issue SSE 已采用不透明重连游标与失效通知，事件不携带业务修订或运行成功承诺；Issue 修订由 REST 快照提供。连接注册后先发 resync_required，游标不可重放时同样要求重查；客户端合并在途失效通知并补查，详见[创建契约 §8](issue-page-create-api-contract.md#8-sse通知快照失效读取仍以查询为准)。不能假定数据库自增编号天然按事务提交顺序可安全消费。项目列表和会话消息订阅尚未编制，不照搬为已采用协议。

SSE 标准提供重连时的 Last-Event-ID，服务端的持久记录、重放和缺口处理仍需实现。[HTML SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-last-event-id-header)。PostgreSQL LISTEN／NOTIFY 可作为低延迟唤醒优化，但正式事件仍落表，恢复不依赖通知连接一直存在。[PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)。低层实现选择仍是建议，不改变 Issue SSE 已采用而尚未实现的状态。

查询、SSE 初始订阅、重连、持续推送及证据读取都检查当前权限。部分仓库权限失效后，旧摘要也不能继续泄露受限内容；可授权的摘要需要按当前可见来源重新生成或过滤，连数量和标题也遵守范围。临时下载授权、下载代理及具体认证方式留待安全接口细化。

## 11. 支付状态筛选的完整链路

以下 F1、B1、B2 只是说明用代号，执行时使用完整 SHA；假设检查范围包含分页保持筛选，不把该例强加给所有需求。

1. 用户先选仓建立长期项目，项目创建只保存资料。会话路径中，首次发送“讨论支付状态筛选的实现方案”时保存业务会话、真实首条消息及对应待办，页面显示已保存与对话准备情况；普通讨论不自动创建 Issue。
2. 首条会话消息提交后，后台准备或恢复本项目实例，核验对话所需服务、Manager 与实际主房间后投递；区分准备、已保存、已投递和有证据的接收状态。各仓能力分别记录，讨论不授权业务 Worker 派工；具体就绪检查待验证。
3. 用户明确要建立工作且目标、范围足够清楚时，Manager 通过受控创建工具登记 Issue、主 ChangeSet、来源、快照、幂等结果及待办；会话保持原身份，还可建立其他独立 Issue。用户也可直接从 Issue 栏提交，默认新会话或明确选已有会话；先取得本地创建回执，再异步准备并让 Manager 接手同一 Issue。两入口均按现行权限、必要配置和范围核验，正式业务任务在计划应用核对后启动。
4. Manager 提交 V1，RepoMesh 按 YOLO 判断许可，建立本 Issue 的仓库上游执行映射并核对应用。调度为前后端任务分别分配空闲 Worker、独立 Attempt 和容量；无空位时记录排队原因。
5. 前后端提交 F1、B1，候选立即收录。Leader 初审接受且具备范围及自测记录后，受控交付路径建立各仓 draft PR。Manager 选定 C1＝F1＋B1，验证者在独立环境核对实际版本、mock 数据及账号范围后执行。
6. 验证发现分页丢失筛选条件。保存执行证据和“业务缺陷”初判，复核后成为有效结果；尚未定位仓库也保留缺陷事实。Manager 协调定位，按已获准的修复 Loop 安排对应 Team，系统扣减该轮额度并控制实际启动。
7. backend 提交 B2。保留 B1 与 C1 的失败历史；B2 经初审后，Manager 选定 C2＝F1＋B2。对 C2 重新判断证据适用性，组织必要重验。若需调整计划或上游 DAG，执行对应范围的收敛和应用核查。
8. 约定必检、内部复核和必需仓库检查满足后，Manager 推荐正式审查。此时可显示“执行已结束、C2 验证有效通过、PR 尚未人工合并”。人完成合并后，RepoMesh 核查最终实际组合及证据，再依据 CS9 判断完成；部署另记。

## 12. 实施前应验证什么

具体源码限制、实验和通过条件见 [AgentTeams 接入验证清单](../plan/agentteams-validation-plan.md)。其中原生 pause 将 Project 设为 paused，而 REST replan 只接受 active；上文停派工／应用流程需补齐受控衔接协议，不能直接照抄为两次原生调用。MCP 和存储写入旁路也必须一并验证；清单未选择最终适配或补丁方案；已开始组件实验与最新源码部署，见[执行状态](../../validation/agentteams-2026-09-09/reports/validation-status.md)。

本节是未来验证顺序，不授权本轮安装、编码、部署或远端操作。

| 验证顺序 | 必须证明的行为 | 为什么先做 |
| --- | --- | --- |
| 1. 执行控制闭环 | Manager／Leader 工具请求经 RepoMesh；未获准、无占用或旧代次不能启动；无法直连管理面、改控制存储或绕开 Git 路径。 | 这是既定产品规则能否落实的前提，无法靠页面设计补救。 |
| 2. 实例与执行上下文 | 首次消息／页面建项并发复用一套实例；一会话多 Issue 的操作和结果不串归属；实际房间及角色上下文映射、Ready 重报和恢复正确；两个项目不串数据。 | 业务隔离方向已确认，具体 room/session 拓扑及恢复能力尚未证明。 |
| 3. 计划与派工 | 多目标部分应用、409、submitted 收尾、下一轮物化、Worker 争抢、暂停期间新请求都正确。 | 防止两个控制路径或两个 Issue 重复驱动同一工作。 |
| 4. 恢复和权限变化 | 启动超时、后台重启、旧 Attempt 未停止、权限撤销、PR 创建结果未知均先核查。 | 正常链路跑通不足以证明长任务可靠。 |
| 5. 验证与交付 | 固定组合、作者分离、缺少附件、PR head 变化、部分合并、最终实际组合证据和历史权限。 | 防止把任务完成当作可交付。 |
| 6. 容量与读取 | 控制面资源保留、重验证峰值、跨项目额度、采集延迟、SSE 缺口及历史权限过滤。 | 之后才有依据给出并发、轮询和容量数值。 |

具体 runtime 建议先以调研中实际主路径 QwenPaw 做兼容性验证，不把未实现的通用 coding harness 当作必需已具备能力。是否正式采用该运行组合、是否另接 coding CLI、镜像版本和受控执行工具形式仍需确定；不同时搭建一套多 runtime 平台。

Skill 工程继续只有文档位置，不新增管理、发布、分发、加载或版本隔离模块／接口／开关。现有执行依据如实记录可取得的工作说明及来源；未实现的 Skill 固定版本加载保证不列为其他模块已经具备的能力。审批模块当前也不开发，YOLO 的许可校验、计划版本和生效控制照常实现。

## 13. 已确认的取舍与接续讨论

用户已确认受控适配的深度：保留 AgentTeams 的团队、通信和生命周期体系，同时允许为 RepoMesh 增加实际工具／执行接入，必要时维护范围明确的上游补丁，并用契约验证约束升级。正式记录见 [ADR-0011](../adr/0011-agentteams-controlled-integration.md)，不再重复询问是否接受该方向。

原因是现有 REST 和提示词不足以证明全部执行约束成立。若坚持完全不改上游且其默认路径又不能被有效限制，本方案的权限、预算与单 Worker 单任务就无法闭环，需要重新寻找可强制控制的运行接入方式；不能把这个缺口推给使用者手动遵守。

Graph 插件在后台协调进程内运行、随后端发布的方案已采用；09-09 补充将其职责明确为跨仓协调与循环策略，仓内 DAG 复用上游，实际派工仍由后台控制，见 [ADR-0014](../adr/0014-in-process-graph-plugin.md)。不重问该运行方式或另建完整 Go DAG 引擎。
