## 当前入口评审：登录与项目创建（RM-UI-PROJECT-ENTRY r1）

[登录与项目入口原型](../prototypes/repomesh-project-entry-prototype.html)沿现行深色界面与两步项目创建：GitHub登录入口→当前已发现仓库多选→项目名称/用途及默认配置摘要→项目保存后继续配置。后端r1技术及落盘已核对；用户在本原型评审后回复“正确”，采用“先选仓库、再填资料”的两步创建流程及授权提示。模型连接/API Key设置仍须另展原型讨论；此次确认不扩大此前详情/交付/消息控件的采用范围。

登录按钮只进入模拟等待，页面外“模拟登录完成”推进到示例账号；没有OAuth跳转、回调或真实令牌。仓库列表区分账号可读取与App工作授权，当前partial覆盖明确为已发现范围，保留完整参与仓库发现仍待接入的缺口，不承诺只有这些仓库。

搜索/加载更多保留按ID明确选择，App缺失仍可选并保存；用户读权未知时隐藏旧仓库内容、暂停继续/保存并保留仍有权的输入，返回上一步不恢复旧资格。当前原型用一个受控按钮模拟核查恢复，不能证明真实权限检测。项目名称/用途沿首批200/20000 Unicode标量，未选择分支；配置摘要中的并发1/验证关闭为明确演示值，预算时限未取得不写0或无限。模型缺失可先保存，正式Issue按其范围及必要条件核验。

保存只在内存保留一份项目示例，不新建会话/Issue、不启动实例。保存后显示待配置摘要及设置入口；设置仅说明模型/API Key管理位置，不收集密钥、不实现配置保存。新建另一个项目用于重演单项目流程，不模拟完整多项目持久化。

正常演示覆盖模拟登录、选仓/加载更多、资料填写、权限未知/恢复及保存后摘要；尚未覆盖真实OAuth、安装授权、模型表单、仓库失权自动检测、项目配置编辑、提交未知/404/410/多操作或刷新存储。后者仍沿现行首批契约，不因本原型演示完成。仅原型/文档，机器协议和真实实现/验证分别推进。

## J1：项目接入与最小配置（已确认）

采用最小必填、其余继承可用默认配置的方式。用户关联 GitHub 账号，从自己可以参与的仓库中选择项目范围；项目配置不要求选择分支。模型 API Key 在设置中配置，项目使用相应模型配置。

| 内容 | 已确认规则 |
| --- | --- |
| 项目名称与用途 | 用户填写，帮助 Manager 理解项目目标和各仓关系。 |
| GitHub 账号与仓库 | 关联 GitHub 账号后，列出用户实际有访问权限的仓库供选择，包括自己的仓库和通过协作邀请或组织成员身份获得访问权的仓库。邀请尚未生效不视为已获得权限。 |
| 分支 | 用户无需在项目接入时选择。Manager 按 Issue 目标、仓库情况及用户已有明确要求确定目标分支，并组织对应 Team 在各自 Attempt 副本中执行；首次计划记录固定基线。 |
| 模型 | 设置中支持配置模型 API Key；项目采用可用的默认模型配置，也允许调整项目使用的配置。无需在每次提交 Issue 时重复输入密钥。 |
| 执行环境 | 继承平台可用配置，允许项目调整；配置引用与实际实例就绪分别表达。 |
| 并发、预算与时限 | 显示项目实际采用的配置值，可以继承明确的默认值；Worker 并发沿用默认 1，受全局容量、项目额度和有效权限约束。本轮不新增具体预算或时限数值。 |
| 项目验证小组 | 沿用默认关闭，启用与停用规则按 ADR-0005。 |
| 执行模式 | 当前项目及 Issue 统一 YOLO；后续模式配置与切换规则见 ADR-0003，相关能力后续开发。 |

### 账号关联、仓库选择与执行授权

账号关联用于确定用户身份和可参与仓库，GitHub App 安装授权用于 RepoMesh 的实际工作能力；二者继续分开。用户可以参与的仓库、App 能访问的仓库、项目选中的仓库和本次 Issue 的范围仍需共同核验，操作不得超过发起人的有效权限。

被别人邀请进入仓库不自动意味着有权为该仓库安装 App，也不意味着 RepoMesh 已能推送分支或创建 PR。具体账号关联方式、仓库枚举接口及完整性、App 安装与账号授权衔接仍待技术接入设计与验证；尚未满足 App 授权的仓库按 J3 标明缺失的权限及原因，不显示为已可执行。

### Manager 处理分支

Manager 负责决定本条 Issue 使用哪些目标分支与基线，Team 在独立 Attempt 副本中执行实际 Git 操作；不通过切换公共工作目录影响其他 Issue。已有明确分支要求属于执行依据，Manager 不能静默覆盖。

执行期间调整目标分支或基线时，按既有计划变更、候选与组合、证据适用性规则记录和处理，不让在途验证跟随分支最新提交。Agent 仍只推自己的任务分支并交付 draft PR，主分支与合并权限继续按 ADR-0002 限制。Manager 的具体选支策略尚未冻结。

### 模型设置与项目可提交条件

设置负责模型连接与 API Key 配置，项目使用可用配置。具体服务商、模型选择、API 地址、密钥归属与共享范围、保存与可用性核验、运行时传递方式后续细化；本轮不冻结字段或承诺 AgentTeams 已具备相应接入能力。

项目配置阶段在 RepoMesh 管理面检查账号关联、所选仓库必要授权、模型及执行配置、额度和预算等必要条件。项目可先保存并表达待配置或部分受限；正式创建 Issue 时针对本次明确范围核验必要条件。“配置完成”不要求 AgentTeams 实例已经创建或 Ready，也不把未填写分支视为配置缺失。混有不可用仓库时按 J3 表达项目部分受限，不能仅因其他仓库失效就禁止只涉及可用仓库的新 Issue。创建成功不表示计划生效或已允许派工，实际执行再次核验。

```text
关联 GitHub 账号 -> 明确选仓 -> 保存长期项目与配置引用（不启动实例）
                                  |
                 按本次操作核验权限、配置、预算等必要条件
                                  |
             +--------------------+--------------------+
             |                                         |
会话首条消息及待办持久化                    Issue 栏明确提交创建表单
  -> 异步准备，实际就绪后讨论                -> 原子建项，返回创建回执
  -> 明确建项时 Manager 受控创建             -> 异步准备，Manager 接手原 Issue
             |                                         |
             +--------------------+--------------------+
                                  |
               确定目标分支与固定基线 -> 计划生效后按当前约束执行
```

### 支付状态筛选场景

用户关联 GitHub 账号，选择自己的 frontend 仓库和受邀参与的 backend 仓库，在设置中配置模型 API Key。项目填写“订单系统”及用途，采用已有执行环境、预算与时限配置，Worker 并发为 1，验证小组关闭。

项目保存、必要配置和本次范围授权成立后，用户可在 Issue 栏提交“增加支付状态筛选”，无需先选分支。默认新会话或明确选中的已有会话，与 Issue、主 ChangeSet、来源及创建结果按创建契约一并关联；提交后异步准备实例和对应主房间。实际就绪后，Manager 接手同一 Issue、核对两仓约定并确定目标分支与固定基线，按生效计划组织各 Team 在独立副本中工作。选支依据、实际 commit 和后续变更均可追溯。

## J2：后续新增仓库与项目范围（已确认）

仓库可选列表自动更新，项目范围由用户明确添加。“全部选择”只选中当次可选的仓库，不持续把未来新增仓库加入项目。该规则适用于 RepoMesh 项目选仓；GitHub App 安装范围仍按 ADR-0002 单独核验。

| 变化 | 已确认处理 |
| --- | --- |
| 用户新建仓库或新获得协作访问权 | 更新账号下的仓库可选列表；实际可执行能力仍核验 App 授权及用户权限。 |
| 用户在项目选仓时点击“全部选择” | 采用当时明确选中的仓库集合；后续列表新增不静默扩大该项目范围。 |
| 用户把新增仓库加入项目 | 记录项目接入范围的变化，Manager 可在有效权限内将其纳入后续工作。 |
| 项目新增仓库时已有 Issue 在途 | 保留其已有范围、计划和固定组合；确需加入本条 Issue 时，由 Manager 按既有计划变更与生效规则处理。 |

例如，“订单系统”已接入 frontend 和 backend。用户后来接受 inventory 仓库的邀请，该仓库出现在可选列表中；用户明确将其加入订单项目后，Manager 才能将它纳入后续工作。正在执行的“支付状态筛选”继续按原范围推进，不因项目选仓变化自动增加库存改造或验证。

列表刷新不触发项目扩仓，项目扩仓也不自动改写在途计划。列表更新的接口、刷新频率和新增仓库 Team／Leader 的实际准备机制仍需技术细化，不据此承诺上游已具备动态接入的完整能力。

## J3：授权部分失效（已确认）

采用“项目部分可用、按影响范围受限”。仓库缺失必要授权、授权被撤销或某些操作权限收窄时，按实际失效能力及工作依赖判断影响；不将某一仓库失效直接等同于整个项目不可用。

| 对象 | 已确认处理 |
| --- | --- |
| 项目页面 | 显示“部分受限”，标明受影响仓库、失效权限及原因；保留原有接入、执行和交付记录。具体状态字段不在本轮冻结。 |
| 新 Issue | 只涉及可用仓库的需求可以正常创建；Manager 在实际关联的主房间接手，不要求每条 Issue 独占主房间。页面入口默认新会话或明确选已有会话，Manager 工具沿可信当前会话创建；仍需满足模型、执行配置、额度和预算等必要条件。 |
| 在途工作 | 停止已无授权的操作，依赖这些操作或结果的工作受阻；无关且仍获准的工作可以继续。 |
| Manager 汇总 | 说明已完成部分、受限部分及原因，不插入人工审批等待，不把未满足验收及交付条件的整体标为完成。 |

例如，支付状态筛选开发期间 backend 仓库授权被撤销，frontend 独立自测可以在仍有效的计划和权限内继续；需要 backend 访问的修复、验证或交付标明受限。已有候选、证据和 PR 保留归属与历史，整体结果如实表达未完成部分。保留历史不扩大查询权限，读取仍遵守既有有效权限范围。

RepoMesh 实际约束已失效的操作，不能只靠 Manager 提醒。无关工作能否继续按依赖和有效计划判断；需要重规划时，仍按 ADR-0003 暂停受影响的上游 Project 新派工并等待在途及 submitted 收敛。上游 pause 不停止在途任务，不能将它作为已撤销权限立即失效的技术保证，也不据此宣称原生支持只暂停某个分支。

该规则不自行扩大权限、提高预算或降低验收要求。当前 YOLO 返回真实受限或未完成结果，授权管理入口不构成当前执行流程的人工审批节点。

2026-09-08：随后讨论 J3，提出项目显示部分受限、可用仓库的新 Issue 正常提交、受影响操作及依赖受限、无关且获准工作继续、Manager 汇总真实结果且不插入人工审批等待；用户回复“采用”。J3 据此确认，下一阶段继续 K。

## 首批项目归属与可恢复配置（RM-B01-04 r2）

更新：2026-09-10。双方已确认这一首批限制；账号和浏览器具体协议另行按唯一字段契约收口。此为本轮推荐方案，不倒填旧“项目默认私有／邀请成员”建议已采用，不改变用户参与仓库的 Git 权限。

首批项目创建者为 owner，本地项目访问资格与 GitHub 仓库参与资格、App 工作能力分别判断。不会把同仓协作者自动变成项目成员，暂不提供邀请／成员管理页面。后端保留明确访问记录的扩展位置。该范围让初期项目归属可检验，代价是暂不支持产品内项目共享；owner 也不能越过所选仓库实际权限。

### 表单与保存门槛

| 内容／动作 | 可用条件 | 失败／未知及恢复 |
| --- | --- | --- |
| 填写项目名称、用途 | 已登录且可创建项目 | 校验失败保留输入，重复标题不自动合并项目。 |
| 选择项目仓库 | 账号实际参与且当前允许读取；App 能力独立展示 | 用户无资格不返回隐藏名称；核查未知不冒充无权。选择只按稳定 ID 保持，分页／刷新不自动增删。 |
| 新建项目 | 完整明确所选范围的用户读权取得有效观察 | 任何新增范围未知时不提交，返回核查未知；拒绝时整次不落项目。App／模型／环境缺失或未知可保存完整待配置项目。 |
| 修改名称／用途／配置引用 | 当前 owner 有项目配置资格 | 原有仓库失权不阻止修复配置；保留项目既有范围，不从裁剪后的列表重建范围。 |
| 明确添加仓库 | 完整新增范围当前有用户读权 | 添加部分失败时整个更新不提交；原有范围完整保留。 |
| 移除项目仓库 | 首批暂不开放 | 不提供按钮，也不允许提交完整替换集合暗中删仓。后续需先明确在途工作与历史影响。 |
| 创建可执行 Issue | 通用必要配置及本次所选仓库的当前能力满足 | 未选仓失效不阻断；创建条件可用不保证运行 Ready 或消息已接收。 |

页面显示“账号参与资格”“App 工作能力”“当前操作能否进行”三种不同观察。每种保留观察时间和实际原因；没有观察依据显示未知，不能用灰色单一“未授权”覆盖所有情况。项目 owner 在仓库失权后仍可访问项目外壳与配置，但受限仓库名称、正文及可利用入口按当前权限隐藏，仅展示允许披露的受限提示。

项目保存与配置编辑都不启动运行。保存后首屏提供进入项目与继续配置；当模型或环境引用未可用时说明缺项。有效默认配置已存在时可以继承，配置未解析时不把预算／时限显示为无限或把空额度显示为 0。已有配置引用失效应回读并重新选择，不自动更换到另一份有费用或权限影响的配置。

### 可恢复配置流程

打开设置先读取当前项目修订和配置引用；编辑在独立草稿中进行。另一客户端已更新时，旧修订提交应显示差异与冲突，保留仍有权的输入，让用户核对后明确提交新修订，不自动覆盖服务端版本。提交后响应不明应查询原更新操作；重新载入页面不能自动产生第二次写操作。

新建项目同样需要稳定操作身份和恢复入口；不能因为首次保存超时就按名称新建一套。字段和恢复路径已由[首批浏览器契约 §6—7](first-batch-browser-api-contract.md)定义，本专题不另建 JSON。

### 首批页面验收（尚未运行）

1. 有仓库读权但 App 缺失，保存后仍包含完整选择且显示待配置；没有自动建项或启动。
2. 新增仓库读权未知时不落半个项目／半次更新；已选已知有权仓库不会因分页被删除。
3. 原项目部分仓库失权时，仍可修改模型引用或项目用途；没有泄露仓库名称，也没有隐式删仓。
4. 两个客户端编辑同一修订，后者看到冲突并核对，不覆盖先前更新；响应丢失查询原更新。
5. 可用仓库单独创建 Issue 继续允许；跨仓 Issue／会话内容失权依内容范围限制，不全项目禁用。

全站账号接入、配置密钥管理、会话保存门槛和运行时凭据传递仍需分别完成具体协议；本节不把配置引用设计当作这些能力已经实现或验证。

### 首批字段来源与页面讨论边界

项目保存／查询、资料／增仓／引用配置更新及其原操作恢复、仓库候选与配置候选的唯一字段来源为[首批浏览器契约 v1／RM-API-01 r3](first-batch-browser-api-contract.md)。固定配置版本由显式配置提交重新解析；名称／用途／加仓不自动换模型。该技术基线已与后端互核，不复制另一套JSON。

项目创建的两步流程和下文 F02 列明的三项 UI 及主界面入口已有用户采用记录。其余新增呈现仍须按页面讨论范围处理；表单字段与错误恢复的技术确认不等于整页 UI 或业务验收完成。

| 场景 | 页面路径／限制 |
