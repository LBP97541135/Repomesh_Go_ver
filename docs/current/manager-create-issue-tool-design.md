# Issue 创建机制：Manager MCP 与 Issue 栏入口

用户最新“之后的待决定都批准，按照建议来。”已授权按推荐推进。本稿采用双入口统一创建机制，依据[持续设计授权](design-delegation.md)与[创建接口契约 v1](issue-page-create-api-contract.md)。DESIGN-004 历史保持 3／3；各轮完整评价、用户原话及先前批准范围保存在[页面日志](../archive/2026-09-12-development-preparation/docs/current/design-communication-page-log.md)，不倒填历史。

## 两个入口，同一个业务创建命令

页面入口后续增加可选“仓库分析”，采用[Python 插件专题](issue-creation-repository-analysis.md)与 [ADR-0020](../adr/0020-python-repository-analysis-plugin.md)。分析先于 Issue 独立受理，用户应用建议后可带 `repositoryAnalysisId` 建项，来源同创建事务保存。首期不向 Manager 新增分析工具，也不把页面专用来源字段自动加入尚未编制的 MCP Schema。

| 入口 | 可信来源 | 创建后的页面 |
| --- | --- | --- |
| 项目 Manager 的受控 MCP | 真实用户消息、明确创建意图与可信调用上下文 | 当前会话出现真实关联记录及 Issue 卡片。 |
| Issue 栏“＋ 创建 Issue” | 登录用户的实际表单提交 | 打开独立 Issue 详情，显示新建或明确选中的会话。 |

两入口统一核验身份、当前发起人权限、项目及明确仓库范围、必要配置、逻辑操作和输入。服务端登记 Issue、默认主 ChangeSet、来源与后续待办；页面创建直接调用业务命令，Manager 接手时不再建一次。正式创建不以 runtime Ready、完整计划生效或 Worker 已准备为条件。

页面默认新建会话，也可明确选择当前项目有权的已有会话。新会话初始标题使用 Issue 标题，之后独立改名；已有会话保留名称及消息。选中会话失效时报错，不静默换会话。一次创建关联一个来源会话，不据此引入一个 Issue 多个主会话。

## 原子提交、来源和恢复

必要新会话、Issue、默认主 ChangeSet、来源关联、真实创建记录、确切输入快照、幂等结果与对应持久待办同一本地短事务保存。既有会话仅增加关联及记录。所有外部建房、运行准备、模型调用均在事务外。

输入快照记录允许字段的确切内容、服务端规范化摘要与 schemaVersion、可信操作者及来源。页面来源不伪造用户发言；Manager 来源引用真实消息及相关澄清依据，不保存隐藏推理或密钥。数据库约束覆盖并发最终提交，不能只先查询再插入。

同次操作重试返回原 Issue／CS／会话；改变内容或关联不得复用已提交操作身份。同标题的明确新工作保持独立，不按相似度合并；跨入口没有可信共同操作依据就不能自动去重。超时或取消等待不证明回滚，先查原操作，查询 404 也不证明旧请求不会继续提交。

操作键随项目保留期禁止复用。删除业务正文仍保留无正文最小幂等占位，旧操作查询返回已删除结果，不能复活事项；详见接口契约。未提交取消或本地表单校验失败不创建 Issue、会话或 ChangeSet；已经明确提交的辅助仓库分析作业按其独立生命周期处理。

## Manager 工具职责与接口边界

**2026-09-10澄清链路补充：** [消息与目标澄清内部协议](backend-message-clarification-design.md)按RM-UI-MESSAGE-TARGET r3语义采用提问／确定目标／替换问题／核查结果动作及可信调用槽位，最终落盘已互核。目标确定分为未提问pending请求的root直接判断与当前唯一答复判断，有open问题不能绕过。它只覆盖既有Issue单项请求的解释，不替代本文创建工具完整Schema，也不解决一条消息包含多个新工作的来源拆分。目标结果不授予创建或派工权限，模型正文不作为工具控制命令。

采用工具名 `repomesh_create_issue`，配套 `repomesh_get_issue_creation` 核查结果。首期 Agent 创建能力仅向项目 Manager 开放，服务端仍核验真实角色、发起人有效权限和会话归属。工具不提供数据库直写，也不默认新增独立部署服务；传输与运行接入继续由后端按现有受控适配设计细化。

Manager 在用户明确要建立工作、目标及范围足够清楚时调用；普通询问／讨论不创建，有歧义先澄清。对话中已明确要求建立即可继续，不额外要求页面按钮或开工审批。可信来源校验不能证明语义理解绝对正确，沿用已采用的消息目标、更正与误判边界。

创建工具的业务输入与页面共用 `expectedCreationContextRevision`、`title`、`description`、`repositoryIds`、`acceptanceCriteria` 及同一验证限制。另接收可信适配层承接的逻辑创建操作引用和来源消息引用；项目、发起人、Manager 身份与来源会话由上下文绑定，不让模型自报 role／userId／approved 授权。来源会话固定为当前已核验业务会话，工具不能任意替换为另一会话。

逻辑操作引用由可信入口持久承接，同次恢复重用；不以 MCP 传输请求编号或模型每次生成的随机数替代。具体句子包含多个新工作时必须拆出明确且可追溯的逻辑操作，不能把一条消息永久限定为只能创建一项，也不按整个会话做唯一键。具体来源句段与操作承接协议尚需后端细化，按持续授权推进，不列作等待用户批准。

查询工具只读取同一可信作用域下的原创建结果并重新核权。创建／查询输出复用页面 committed 回执的业务字段，来源 kind 为 `manager_mcp`；links 仅返回 issue／rooms，原操作通过查询工具核查，不返回只接受页面操作的 links.operation URL；返回持久 Issue／CS／会话身份，不返回运行 Ready 保证。错误复用契约业务 code；MCP 适配层表达工具业务错误，不将 HTTP 状态码当作 MCP 传输协议。完整可执行 JSON Schema 及传输身份协议尚未编制，不能宣称工具已实现。

## 创建后的自动接续

首次保存业务会话及首条消息，或页面 Issue 创建提交后，持久待办驱动异步准备／恢复项目实例及关联主房间，复用已有准备与就绪资源。仅建立项目、打开空会话或读取历史不触发。Manager 已运行时直接接续同一工作；尚未就绪时等待真实就绪及当前权限、配置、预算核验。

页面分别显示业务已创建、运行准备／受阻、Manager 实际接手和工作进展。创建记录不伪装成待投递用户聊天，Manager 文本“创建好了”也不代替持久回执；不由创建成功推断计划生效、Worker 派工或 Leader 房间 Ready。恢复失败保留业务事实，未知外部结果先核查原操作。

## 实施进度

当前只有设计与上一版内存原型。原型已有 Issue 栏创建、默认新会话、表单校验、来源记录与详情导航；可选已有会话、页面提交后自动准备尚未补入，真实 API／MCP／数据库／SSE 均未实现。旧原型依赖当前房间 Ready 的限制不是正式创建规则。

仓库事项粒度、反向多主会话、来源句段协议、列表及消息契约等继续按推荐设计并与后端对齐；不把未编写或未验证误报成等待用户决策。代价是来源、幂等、权限与恢复维护，收益是两种入口得到一致且可追溯的结果。
