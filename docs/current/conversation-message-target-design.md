# 多 Issue 会话中的工作消息目标

## 当前实现设计：RM-UI-MESSAGE-TARGET r3

按用户“但是具体实现得和后端聊一下”，双方已确认第3／3轮最小消息与澄清协议。[浏览器五端点契约](conversation-message-clarification-api-contract.md)由页面独占，[后端实体与事务设计](backend-message-clarification-design.md)由后端独占；这两份文档为当前实现设计来源。r1控件演示保留，新控件仍待用户反馈，本轮不修改HTML或业务代码。

明确单项请求可从原消息直接解释；存在歧义则发布有身份的问题，答复沿普通消息入口携带原问题及版本。两条处理分支由可信后端上下文确定，不能解析聊天Markdown当控制命令。候选仅辅助填入，实际改写正文重新解释；应保留已有草稿。移除问题引用只形成新普通消息，仍解释正文，不是“禁止工作”开关。

一个问题至多一份有效答复；不同键并发只有赢家消息整笔保存，输家保留有权的输入并获409。已保存、目标已明确、实际计划/派工分别表达。含糊答复保留记录，以新问题接续，旧问题不重开。提交未知查询原键，原查询404仍未知，410不复活；成功重放保持原回执，不重复消费问题。

技术设计及文档落盘已由双方互核，无遗漏实质分歧，原文见当前双方日志。数据库/Manager/实际权限/重启恢复/真实传输均未测试；完整B05、多命令、更正补救、可信适配器和执行协议仍有缺口。新恢复/冲突/草稿保护控件后续须展示原型讨论。本段替代下方r1“完整消息协议均未编制”的当前状态，历史采用证据及原型演示边界保持。

## 当前控件评审：消息目标与澄清（RM-UI-MESSAGE-TARGET r1）

承接用户采用的悬浮入口与同页右栏；新[消息目标原型](../prototypes/repomesh-message-target-prototype.html)仅演示一条歧义请求及其答复。r1第1／3轮技术已获后端ACK，具体卡片、候选位置与回复方式待用户评审。本文原accepted只指下方DESIGN-003既有方向，不自动涵盖本次新控件。

用户说“这个也加上日期范围”，Manager在同一会话原消息之后询问是哪条Issue，附当前可读的两个候选。问题不弹窗、不迫使所有消息预选Issue。候选点击只把可编辑的“指的是 #2 订单导出。”填入主输入框，并带原问题引用；用户也可直接输入补充，或移除引用形成仍按正文解释的新普通消息。发送才保存答复，目标核对与计划/派工结果分别表达。

原问题和答复持续可见。目标明确后，Manager处理记录显示稳定Issue标识及查看入口；点击只在现行同页右栏查看该Issue。右侧查看范围不能覆盖消息正文的目标。仅这条歧义请求在明确前不调计划/派工，不暂停该Issue其他已经获准的工作；不新增逐条审批。

候选展示、发送和处理须核当前读权/会话关联/问题有效性，答复绑定原消息及问题；已失效问题或改写后正文冲突不能由隐藏的候选选择强行定目标。当前合法的Issue身份及模型置信度均不能证明意图无误，目标显示不授予执行权限，后续执行仍核状态、范围、计划、版本、预算和容量。目标更正、已发生工作的补救与跨多Issue命令仍另行设计。

原型只有预置脚本，无模型识别、业务请求和持久化。点候选后原样发送，页面外“模拟Manager收到答复并明确目标”才生成演示回执；用户修改候选文字或自由输入后只保留“答复已保存/等待核对”，不能根据旧候选自动确定目标。答复保存、投递、收到、计划变更和执行不是同一事实，本次快捷模拟未覆盖全部中间阶段。完整消息/澄清/幂等/更正协议和真实权限、恢复、执行验证仍未完成；创建v1与RM-API-01 r3保持。


本稿对应 DESIGN-003，第 1／3 轮双方对齐后，页面询问是否采用“自然语言明确目标，有歧义先澄清”，用户回复“是的，我建议给manager可以额外写一个创建issue的mcp让其可以调用，你觉得如何”。其中“是的”确认本方向；后半句创建工具作为 DESIGN-004 单独评估。具体算法和接口未冻结。DESIGN-002 保持 3／3 收口，通信原文见[页面日志](../archive/2026-09-12-development-preparation/docs/current/design-communication-page-log.md)。

## 已采用方向与取舍

继续自然语言沟通，用户不必在每条消息发送前手动选择 Issue。Manager 根据明确的编号、名称或无歧义的对话内容识别目标；目标有歧义或冲突时先澄清，该请求在明确前不改计划或派工。普通讨论可以不关联正式 Issue，提到某项不等于要求执行。

| 场景 | 建议行为 |
| --- | --- |
| 会话有支付状态筛选和订单导出两项，用户说“给订单导出加日期范围” | 对应订单导出，处理记录显示该 Issue 标识与动作；沿既有规则核验后处理。 |
| 用户说“这个也加上日期范围”，对话中两项均可能符合 | 在会话中澄清是哪项，保留原消息；不以最后打开的页面猜测。 |
| 从支付筛选 Issue 页面进入主房间，用户明确说调整订单导出 | 来源提示继续用于导航，不能覆盖正文明确表达的目标。 |
| 用户询问“这两种方案有什么区别” | 可以讨论，不因此修改两项工作。 |
| 已针对订单导出发出的工作稍后返回，此时用户正在看支付筛选 | 结果保持原目标与版本，不随页面切换改归属。 |

未采用的替代方案是发送前必须选择“普通讨论／某 Issue”。它让发送目标直接可见，但增加切换成本，仍需处理选项与正文冲突。本轮只确认自然语言明确目标、歧义澄清及列明保障；具体识别算法、控件与更正流程尚未冻结。

## 页面与执行边界

建议 Manager 的工作处理记录显示可跳转的 Issue 标识；必要时提供当前可见的候选供澄清。目标足够明确且满足现行权限、范围与计划规则时继续按当前 YOLO 处理，不新增每条请求的审批。确定目标本身也不授予执行权限。

模型理解与实际操作分别取证。后续具体工作请求必须绑定稳定 Issue 身份、动作及相关版本，服务端核验项目、关联及当前权限。模型的置信度不证明用户意图；无效、缺失或冲突目标不能用当前标签页、最新事项等默认值补齐。

后端能核验目标身份和执行条件，却不能单靠结构校验证明模型理解正确：一个存在且有权操作的 Issue 仍可能被语义选错。采用本方向需接受仍可能误判的代价，通过歧义澄清、目标可见、来源记录及更正处理控制影响；显示目标不等于用户已确认，也不承诺零误判。

澄清答复对应原消息及待澄清问题，记录可见的用户内容和业务结果，不记录模型隐藏推理。等待某条请求澄清不意味着暂停该 Issue 已有的获准工作；投递未知时的顺序等待与语义澄清分别处理。当前读权不等于执行权限，执行还须核验状态、计划、版本、预算与容量。

消息保存、等待澄清、目标确定、实际执行与完成事实分开表达。恢复和晚到结果保持原操作归属；用户纠正目标时不能把已经发生的工作改写成从未发生。纠正、撤销及补救的细节另行讨论。

## 本轮未包含

DESIGN-003 的原确认不包含跨多 Issue 批量命令、自动默认目标、内部仓库事项粒度、完整消息／更正协议及运行时映射；这些继续设计，不能从本方向推导为已冻结。原型未模拟语义识别，本轮浏览器接口无变化。

后续 DESIGN-004 及[持续设计授权](design-delegation.md)已采用 [Manager 受控创建工具与页面双入口](manager-create-issue-tool-design.md)、创建快照及原子范围、默认新建／可选已有会话、首次消息或页面建项提交后异步准备，以及[创建 REST／Issue SSE 契约](issue-page-create-api-contract.md)。这些来自后续决定，不追溯归入 DESIGN-003，也不再标为“尚未采用”。完整 MCP Schema、可信来源句段／逻辑操作承接和会话消息协议仍需编制，真实接口未实现。
