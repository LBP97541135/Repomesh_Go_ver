# Issue 配置绑定：创建与后续接续

本文是设计就绪审查 R04 的**推荐修订，待采用**，不是新增已确认决定，也不表示数据库、消息或运行接入已实现。当前采用的浏览器字段、错误与项目配置固定规则仍以[首批浏览器契约](first-batch-browser-api-contract.md)、[Issue 创建契约](issue-page-create-api-contract.md)和[首批持久化协议](backend-first-batch-persistence.md)为准。本稿补充的内部字段与流程在采用后才能成为实现依据；不直接增加 HTTP 或 MCP 字段。

现有规则已要求项目配置修订不可变，并要求项目换模型不改变在途 Issue；但尚未规定 Issue 持久引用哪一条修订。只保存项目当前配置、创建时间或创建条件令牌，不能在后台重启后可靠还原创建时采用的配置。

## 1. 推荐决定与实施先后

推荐在 Issue 创建事务内，将当时核验通过的不可变 `ProjectConfigRevision` 固定到该 Issue。之后接续同一 Issue 时，先沿这个可解析引用读取原配置，再核查该配置现在是否仍可使用。对 Issue 的配置选择而言，项目后来显式更新配置只影响随后创建的 Issue；普通讨论见 §6。

已定项目、列表、详情和创建事务的代码可以继续准备；**在首次持久保存可供以后接续的真实 Issue 与待办之前，应采用本规则或另一套同等可追溯的绑定方案，并完成数据库约束核对**。不能先积累未绑定的业务记录，等 B06 接运行时再按时间猜配置。B05/B06 的消费者映射、凭据取得和运行隔离可以后续完成；完成前待办保持真实 `blocked`，不进行模型调用或启动运行。

本轮不设计在途 Issue 主动换配置的完整流程。原配置失效时，不通过修改原始绑定或共享 Manager 的全局配置继续执行；修复边界见 §5。

## 2. 内部引用与保留约束

以下是推荐的内部逻辑结构，具体 DDL、Go 类型及外部展示字段仍需实现前核对。

| 位置 | 推荐保存或校验 | 约束 |
| --- | --- | --- |
| `ProjectConfigRevision` | 以 `(projectId, revision)` 唯一标识不可变配置；保存已经固定的 model/execution profile、有效参数及 secretVersion 引用。 | 与现有项目配置记录共用，不为每个 Issue 复制密钥或另造同义配置表；含未解析引用的受限修订仍可供项目保存，但不能据此通过 Issue 必要条件。 |
| `Issue.initialConfigurationRevision` | 创建时选定的 `ProjectConfigRevision.revision`。 | 新 Issue 必填且不可改写；`(projectId, initialConfigurationRevision)` 以复合外键或同等数据库约束引用同项目配置。与 `Issue.revision` 分开。 |
| `CreationOperation` 的内部成功结果 | 保存创建结果对应的 `initialConfigurationRevision`，与结果 Issue 一致。 | 与 Issue、原输入、回执、待办同事务；这是服务端选定的结果事实，不加入客户端规范化输入，不改变旧键比较规则。 |
| Issue 接续待办 | 继续保存原 `causeOperationId` 和目标 Issue；处理时必须解析目标 Issue 的固定引用。 | 不再读取项目当前配置作为该 Issue 的执行依据；若为审计冗余保存配置引用，提交时校验与 Issue 相同，不能形成第二个可独立更新的来源。 |
| 配置与秘密历史 | 保留被 Issue／操作／运行事实引用的配置版本及可追溯的秘密版本身份。 | 引用存在时不级联删除配置。秘密正文可撤销或按秘密管理规则销毁；保留版本身份和失效事实不等于永久保留可用 Key。 |

`creationContextRevision` 仍只是创建条件的等值比较令牌，覆盖范围、配置和策略等条件；它**不是** `ProjectConfigRevision` 的外键，也不能通过拆分令牌或拿它当配置 ID 来取得配置。`configurationRevision` 是已有项目有效配置修订的名字，`initialConfigurationRevision` 是 Issue 对它的首次固定引用。

本稿的配置绑定不替代 Issue 的仓库范围、内容权限范围、生效计划、固定交付组合或动态预算账本。配置中的额度与策略引用只是依据；当前权限、剩余预算及资源占用仍按实际动作核查。

## 3. 创建事务与模型应用并发

沿用现行创建协议的重放优先、项目锁和短事务，在[持久化协议](backend-first-batch-persistence.md) §2.2 的步骤 4—6 补入以下动作：

1. 锁后先查原创建操作；已经提交时按当前读权返回原结果，不重新选择配置。
2. 对新的创建操作，比较客户端创建条件令牌，在同一项目锁内读取当前 `configurationRevision`，解析其不可变记录，并核验现行必要条件及当前可用资格。
3. 将这个版本写入新 Issue 和操作内部结果。Issue、配置引用、必要会话、主 ChangeSet、来源、事件与待办全部提交或全部回滚；不允许先提交 Issue 再补引用。
4. 后续后台只沿已提交引用接续；项目当前配置是否又变化不影响原操作重放。

项目配置提交与 Issue 创建遵守同一项目锁及修订规则，不能用事务外“最后读取值”填绑定：

| 交错 | 必须得到的结果 |
| --- | --- |
| 项目从 C1 应用到 C2 先提交，创建仍携带旧条件令牌 | 按现行契约返回 `409 CREATION_CONTEXT_CHANGED`，不把旧输入静默配到 C2。 |
| Issue 创建在 C1 下先提交，项目应用随后提交 C2 | 原 Issue 固定 C1；此后经新条件创建的 Issue 可固定 C2。 |
| 创建提交后响应丢失，期间项目变为 C2 | 原键回查或重放仍指向原 Issue 和 C1；不新建、不改绑。 |
| 原版本 Key 的本地撤销与创建并发 | 纳入现有访问／凭据修订核对；撤销已观测且条件已失效时不能提交正常创建。外部服务尚未观测的撤销不由本地事务保证，动作前另核。 |

已知没有必要模型／执行配置时，项目仍可按现行契约受限保存；新的 Issue 创建按现行 `409 CREATION_REQUIREMENTS_UNMET` 返回可披露原因，不产生可供执行的半套 Issue。外部权限未知仍按创建契约处理，不能把未知当作配置可用。已提交的 Issue 后来失去配置资格则保留业务结果，并阻塞受影响的新动作，不撤销历史创建成功。

“用于项目”仅更换模型并精确保留 execution 的行为目标，还依赖[模型设置专题](model-connection-settings-design.md)所列专用应用协议。本稿解决 Issue 如何保留原版本，不宣称现行完整 PATCH 已具备该应用原子保证。

## 4. 后台重启与实际消费者边界

后台启动后从 DurableWork 找回同一工作及 Issue，沿固定引用恢复配置依据，不依赖创建进程的缓存。每次执行敏感动作前核查原 actor 当前资格、固定版本是否可取得和启用、secretVersion 是否仍有效，以及当前计划、预算和资源条件。核查通过只是可进行相应动作的条件，不证明模型往返、Manager 接收或 runtime Ready。

配置失效、缺失或无法核实时，保留原因、原版本、最后观察及重新评估条件；保持受影响工作 `blocked`。已经可能外发的动作先沿原操作核查，不因配置失效直接取消核查责任，也不自动用新 Key 重发。配置恢复仅重新评估原待办，不创建另一 Issue，不重置操作身份或预算。

绑定字段本身不能提供运行隔离。接入消费者前仍须完成以下映射及真实验证：

| 消费场景 | 接入前必须补齐的协议与证据 |
| --- | --- |
| 同一长期 Manager／Leader 处理采用不同版本的 Issue | 逻辑请求如何携带 Issue 与固定配置归属；模型／网关／runtime 实际使用哪个版本；并发或复用时如何防止其他 Issue 被切换。不能靠覆盖共享环境变量、公共配置文件或重载共享 Manager 来满足每 Issue 固定。 |
| 仓内任务、跨仓验证与后续 Loop | 将目标 Issue 的配置依据映射到实际请求、Attempt 及证据；计划或组合另有变化时分别记录，不能借任务重试重选项目最新配置。 |
| 凭据获取、撤销与已外发恢复 | 凭据边界按固定 secretVersion 取得当前仍可使用的秘密；明确撤销观察、不可取得、远端未知和停止新动作的处理。历史配置不能充当长期授权。 |

上述映射及故障恢复由 B05/B06/B07 相应专题补齐。未证明实际消费者可按固定版本执行时，相关消费者仍为 `blocked`；不因此另建一个 Manager 业务身份，也不宣称上游已支持按请求选配置。本轮仅修订产品文档，没有运行上游或验证运行隔离。

## 5. 旧 Issue、密钥撤销与修复

现有工程仍是骨架，尚无产品 Issue 数据库；以下为实现迁移、导入历史记录及未来故障修复时应遵守的候选规则。

| 已有记录或变化 | 推荐处理 |
| --- | --- |
| 已有 Issue 已带可信固定引用 | 验证同项目外键与创建操作一致，保留原值；项目应用新模型不更新它。 |
| 旧 Issue 缺少绑定，但有原提交事务日志、操作结果等能唯一证明当时版本 | 经受控迁移补写确切引用，保留证据、迁移身份和时间；不改写原创建时间及输入。普通业务更新不能开放这个补写入口。 |
| 旧 Issue 缺少绑定，只有创建时间、当时名称、相邻配置记录或当前配置 | 标为历史绑定未确认，阻塞依赖配置的新动作；不能用“时间最接近”或当前默认补填。迁移可保留明确的旧记录例外，新建路径不能借例外写空绑定。 |
| 固定版本停用，或其 Key 撤销／删除 | 保留引用、版本身份及失效事实；阻塞依赖它的新动作。项目改用新 Key／模型不修复旧 Issue，普通重试也不得自动换绑。 |
| 用户希望旧 Issue 改用可用的新配置 | 另行设计明确选择、原版本／新版本、影响范围、许可与生效、在途动作收敛及证据重新判断；采用追加变更记录，不能覆写 `initialConfigurationRevision`。相关写接口与消费者在该流程完成前不启用。 |
| 历史绑定无法确认，但希望继续原 Issue | 后续修复流程须记录“历史未知”及新选择从何时、对哪些新工作生效；不能伪造创建时已使用该版本。首次绑定修复与在途换配置均需完整协议后才能执行。 |

原固定版本重新可用时，可在当前权限等条件通过后接续原待办。若必须改用另一版本才能继续，则属于上表的显式变更流程；不把“配置已修复”解释为所有旧 Issue 自动跟随项目。

## 6. 尚未确定 Issue 目标的普通讨论

普通需求讨论可以发生在 Issue 创建之前，同一会话也可以关联多个 Issue。因此不能把会话、当前打开的页面或“最近一个 Issue”的固定配置当作全部讨论的默认执行依据。

推荐以一次**可恢复的模型处理请求**为普通讨论的配置固定单位：在该处理请求持久受理时固定当时项目配置，重试和后台重启沿原请求引用；以后独立的新请求可以选用项目后来明确提交的配置。它不创建 Issue，不给整段会话永久绑定一个模型。仅保存用户消息与受理模型处理分别表达；缺配置时不能把消息已保存当作模型已接收或即将执行。

这仍是候选方向。B05 须先定义该请求与消息／投递操作的身份、原子提交点、无配置时的保存结果、幂等恢复和预算归属，B06 须证明实际模型调用遵守固定引用，才能启用普通讨论消费者。首批持久化不能自行发明消息 Schema 或把未接入处理器写成成功。

普通讨论随后要求操作某个 Issue 时，新的受控业务动作核对该目标并使用其固定配置依据；此前讨论记录不倒填为该 Issue 的创建配置。一个请求涉及多个不同配置的 Issue 时，如何拆分处理和分摊预算需由上述协议定义，不能合并成一份共享 Manager 全局配置。

## 7. 采用与实施后的验收

以下是推荐修订的验收条件，**尚未执行**。CB01—CB05 应在首批真实 Issue 持久化前完成；CB06—CB10 在对应消费者或修复能力启用前完成。

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| CB01 | 创建成功、任一步写入失败、响应丢失 | 成功时 Issue／操作／待办可沿同一固定配置追溯；失败无半套记录；原键仍查回同一版本。 |
| CB02 | 创建与 C1→C2 项目应用交错 | 串行结果符合 §3；旧条件冲突，已创建 Issue 保持 C1，新条件创建可得 C2。 |
| CB03 | 项目更新后清空进程缓存并重启后台 | 原待办从数据库找回原 Issue 与 C1，未接处理器仍真实 blocked；不从项目当前值补配置。 |
| CB04 | 新 Issue 空引用、跨项目引用、操作引用与 Issue 不同 | 数据库约束／同事务一致性检查拒绝提交；历史例外不能被新创建路径使用。 |
| CB05 | 缺必要配置、受限项目保存、删除被引用配置 | 项目可按原规则保存；新 Issue 不绕过必要条件；被引用配置不会级联消失。 |
| CB06 | 两条分别固定 C1/C2 的 Issue 共用长期角色 | 每次实际模型／执行请求可证明使用各自版本，结果与费用不串归属；共享配置切换不能算通过。 |
| CB07 | 原 Key 撤销／删除，项目改用新 Key，原请求结果未知 | 旧 Issue 不暗换版本、不盲重发；保留原操作核查与受限事实，创建成功历史不被改成失败。 |
| CB08 | 有确证和无确证两类历史缺绑定记录 | 前者补写有证据可审计；后者维持未知并阻塞，时间相近不能作为采用依据。 |
| CB09 | 明确升级或修复旧 Issue 配置 | 完整变更协议采用后才启用；保留原始引用及新生效范围，处理在途动作和旧证据适用性。 |
| CB10 | 无 Issue 的讨论、重试、项目换配置、随后指定 Issue | 同一模型处理请求重试保持原版本；新独立请求的选择可追溯；目标 Issue 动作不继承任意会话配置。 |

文档自查只能核对这些规则是否一致，不能替代数据库并发、秘密撤销、模型调用或 runtime 隔离验收。采用本候选也只关闭 R04 的创建绑定选择缺口，不等于 B05—B08 或完整后端已经可以无条件接入。


## 8. B06 P9 约束细化候选（2026-09-13）

`P9-r2 / PROPOSED_NOT_ADOPTED`：推荐继续采用 §1 的强引用方案。与按时间寻找/复制配置相比，同项目不可变外键可复用 B03 事实源，并能由数据库拒绝空引用、跨项目和操作不一致。新 Issue 必须有 NOT NULL `(project_id, initial_configuration_revision)` 外键，引用现有 project_config_revisions 主键；历史配置删除 RESTRICT。Issue 的项目、初始引用和首次创建身份更新被数据库拒绝，正文删除只设置墓碑。

CreationOperation 保存同项目、同 Issue、同配置的内部结果，复合外键引用 Issue 的 `(project_id,id,initial_configuration_revision)` 唯一键；待办的 `(project_id,issue_id,cause_operation_id)` 引用这一操作结果。配置字段不加入 HTTP 输入或回执。主 ChangeSet、主会话、非空范围、操作完整性用[迁移设计](../development/2026-09-13-b04-b06-design-01/migration-design.md)的组合键及延迟约束实现；当前没有持久 Issue，实施不允许以 nullable 遗留例外先写新数据，也不在本轮设计历史修复工具。

创建与应用共用 project 行锁。创建先持锁读C1并提交，应用随后可写C2，旧 Issue 永留C1；应用先写C2则旧创建条件冲突，刷新后用新输入/新操作才能创建于C2。应用 no-op 保留全部修订；相同模型但从 inherit 改为 reference 是选择依据变化，会形成新修订。创建提交未知时先查旧键，不能在新条件下自动重建；原成功重放不受C2影响。

可解析闭包为 Issue → ProjectConfigRevision → 固定 ModelProfileVersion → ProviderRevision/ModelSnapshot/SecretVersion，以及固定 ExecutionProfileVersion → 模板/预算/时限政策。参数不是 latest 查找；任何闭包材料缺失/被限制时保持 blocked，禁止 fallback。秘密正文可销毁，但版本身份与当前不可用事实保留。被引用版本停用不应妨碍有权读取历史事实。

本文旧 §6 将普通讨论消费者/真实模型证明写为 B05/B06 条件，属于先前批次映射，**不适用于本轮授权**。本轮只保留普通请求与正式 Issue 可以分别固定配置的空间；普通讨论的受理身份/消息协议、运行读取与实际消费在 B09 及相应消息批次另定。本轮 CB03 只验证重启后数据库引用可追溯及 blocked，不证明模型参数已实际消费。CB06—CB10 和完整 G1/G2 未完成。
