## 当前悬浮入口与同页右栏（RM-UI-ROOM-NAV r2）

用户原话：“我觉得可以做成codex这样的常驻悬浮但可以随着窗口比例收起，并且点击里面条目可以展开右侧边栏的的感觉”。[悬浮入口与右侧内容栏原型](../prototypes/repomesh-conversation-dock-prototype.html)据此替代r1固定索引栏和离开主会话的快捷跳转；旧原型保留作演进参考。r2第2／3轮技术及落盘已核对；用户回复“正确的，进行下一项”采用已展示的悬浮入口、响应式收起和同页右栏交互。已采用的DAG图形与图下节点详情保持。

宽窗口在会话右上方常驻悬浮入口，显示图标和文字；打开右侧内容栏后入口收为图标。点击Issue/DAG/Leader在同一页面右侧显示对应内容，主会话和输入框保留；再次点击当前入口或关闭按钮只收起内容栏。支持临时扩大面板读图。窄窗口自动收成图标；跨入窄窗口时收起已打开的内容栏，仍可点击图标以覆盖方式重新打开。缩回宽窗口不自动恢复旧面板。

- 视图动作不关闭主会话/房间、不取消后台任务、不触发重试或创建，不改关联和消息目标。新右栏保持r1的实际资源关联、DAG可读性独立runtime、Leader只读及当前核权要求；隐藏后重新打开仍须重核。
- 主草稿不受展开/切换/收起右栏影响。右栏绑定当前主体、会话、所选Issue、实际资源及请求代次；切会话或Issue撤下旧内容，晚到响应不可回填新上下文。注销/失权清敏感内容，未知不得保留旧敏感正文；实际权限与订阅清理尚未演示。
- 选择Issue只变查看上下文。上下文入口展开选择器；切Issue后关闭旧面板及选择器，重新选相应资源。多个Issue无有效来源仍需明确选择；不凭上次选中直接授予读权。
- 原型断点为讨论参数：1100px以下图标入口，820px以下进入自动收起/覆盖模式；较窄的并排模式暂隐藏左项目栏以保留聊天与右侧阅读空间。具体比例未冻结成业务约束。关闭内容栏后仍保留入口。
- 本次只新增独立HTML和页面文档；复用已有SVG读图及Leader模拟消息，不改变React Flow方向。创建v1、RM-API-01 r3保持。关联/图/消息/房间API、订阅、真实核权和刷新恢复仍未实现，不因同页展示视为完成。

## 历史会话右侧导航（RM-UI-ROOM-NAV r1，呈现已被r2替代）

用户原话：“是的并且在会话房间也能也要有按钮索引到leader房间还有DAG。可以参照右侧边栏的设计如图”。“是的”确认上轮[只读DAG](../prototypes/repomesh-issue-dag-prototype.html)的布局与图下详情；本轮新[会话导航原型](../archive/2026-09-12-development-preparation/docs/prototypes/repomesh-conversation-navigation-prototype.html)参照截图的简洁图标文字行。仅在会话页新增可收起右栏，不推导全站三栏布局。r1第1／3轮已获后端技术ACK，右栏的具体宽度和排布仍待用户评审。

右栏上方为项目和“查看关联 Issue”选择，下方依次为 Issue 详情、任务 DAG、按实际关联列出的 Leader 房间（只读）。保留原左栏、聊天和输入框；窄窗口通过“导航”按钮展开右栏。

- 关联选项必须属于当前会话且按当前全部内容范围可读。有效来源或仅一条关联可提供明确查看上下文；多条且无有效来源时先选择。上次选择仅可在仍有效时恢复，禁止回退猜选另一条。
- 右栏选择仅用于查看，不确定后续消息目标、不改业务绑定、不触发计划或执行。消息仍在主会话与 Manager 沟通，具体工作目标按自然语言明确规则处理。
- DAG入口依据实际可读计划，独立于runtime Ready。点击进入该Issue的“任务图与规格”页签；没有可读计划时禁用并说明，不因Leader可进入就推断有计划。
- Leader入口按当前Issue的真实房间关联及当前canEnter展示，进入时重核Issue/仓库/房间归属、当前读权和就绪；只读。不得按选仓合成房间或地址。空列表只表示当前无可进入入口，不推断无委派；未知不展示缓存的敏感名称。
- 入口跳转保留返回会话按钮。草稿和查看上下文按主体及会话隔离；返回同一会话恢复未发送草稿、选择与滚动位置。注销/失权清理敏感上下文，读权恢复必须重新核查；保持原操作身份，不借导航重放或新建操作。当前原型只演示同页内存往返，刷新重置。
- 晚到查询继续遵循既有身份/对象/请求代次隔离；切Issue立即撤下旧目标入口，未核实时不混入旧Issue数据。关联查询需处理分页与完整性，不能仅筛一页项目Issue列表便宣称全会话关联。新接口/快照/消息协议仍未完成。

## 已确认范围

用户先更正侧栏原 Issue 本质是聊天，应改为会话，Issue 独立组织各仓库事项，ChangeSet 保留。随后明确仓库事项是 RepoMesh 内部对象，可以关联 GitHub Issue。页面询问一条会话能否先后创建、关联多条独立 Issue，各自保留计划、验收和 ChangeSet，用户回复：

> 可以的，我同意。issue在页面上可以给一个专门页面，并且可以导航到对应会话房间（主房间，leader房间）

- 会话持续承载讨论，可以没有 Issue，也可以先后关联多个独立 Issue。聊天不再整体从草稿转正为 Issue，关闭聊天不等于完成工作。
- Issue 独立表达总体目标、范围、计划、验收与状态，并组织内部仓库事项。各仓状态的简单集合不替代整体验收。
- 每个正式 Issue 沿用默认一个主 ChangeSet，候选、固定组合、证据、PR 及交付历史不因会话变化重建；不为每个仓库事项默认新建嵌套 ChangeSet。
- Issue 有专门页面，能够导航到明确关联的主房间与 Leader 房间。一个会话可关联多项，不自动确认反向一个 Issue 可挂多个主会话。

## 页面设计

后续采用：创建 Issue 表单在“本次仓库”旁增加可选“仓库分析”按钮，展示推荐仓库、关系与证据；用户应用建议后仍可调整，失败时可手动创建。Python 分析不启动 AgentTeams 实例，也不提前创建 Issue／会话。完整交互、过期处理和 API 见[仓库分析专题](issue-creation-repository-analysis.md)；当前 HTML 原型尚未加入该按钮。

左侧保留长期项目，项目下的标题列表表示会话，不显示“草稿转正式”的混合事项树。主导航新增 Issue 入口；项目切换决定所查看的项目范围，不扩大权限。

Issue 列表提供编号、标题、状态、涉及仓库及主 ChangeSet 的入口，并显示“＋ 创建 Issue”。表单明确“关联会话：新建会话”；提交成功后打开独立 Issue 详情，侧栏出现新业务会话。设计已采用默认新建、可选当前项目已有会话，新会话初始名取 Issue 标题，此后独立改名。当前原型仍只有默认新建，尚未补已有会话选择器。进入详情后先看总体目标、内部仓库事项和房间导航，再按需查看计划、验证交付和历史。排序、过滤与布局仍为原型方案。

会话中建立 Issue 后显示关联卡片，同一聊天可继续建立其他独立 Issue。页面创建的新会话记录真实业务来源及关联卡片，不伪造用户消息或 Manager 回复。Issue 详情的“进入主房间”回到对应会话；进入时展示来源 Issue 提示，便于返回详情。来源提示仅用于导航，不能自动把后续所有消息授权为对该 Issue 的指令。消息目标沿 DESIGN-003 已采用方向，具体协议与更正过程待细化。

Leader 房间入口放在对应仓库事项附近，并显示关联仓库与状态。首期继续只读；房间内显示来源 Issue，提供回到该 Issue 或主房间的入口。房间是否跨多个事项共享尚未确认，不能由这版页面推出底层拓扑。

## 状态、权限和异常

接口 P1 已获用户“确定”：Issue 栏创建的新业务会话、来源关联及真实创建记录，与 Issue、主 ChangeSet 和既有待办在同一本地短事务提交，失败不留半套记录。后续持续授权补齐快照、幂等结果、启动与接口字段，见创建契约；原型不证明数据库保障已实现。

导航依赖后端已确认的 Issue、会话、仓库及实际房间关联，不按标题拼接地址。只有当前可读且实际就绪的房间可进入；未就绪、受限或未知时说明允许披露的原因，不伪造可用链接。失去读取权限时，正文、标题等信息也按现行权限边界处理。

建立正式 Issue 不表示计划已生效、已派 Worker 或 Leader 房间 Ready；分别展示事实。多个 Issue 仍各自有计划、工具请求、Task／Attempt、上游工作流和验证交付归属，不凭当前打开的会话决定执行目标。晚到结果保留原 Issue 及版本归属。

业务会话、实际协作房间、各角色 runtime session 分别关联，不承诺隐藏模型上下文完整复用或恢复。运行恢复受阻保留已提交的业务事实；导航与历史读取不会自动重放旧操作。

## 接口影响与未决范围

旧 `draft-issues`／`formalizations` 草案不能继续表示整条聊天的生命周期，应分别设计会话通信、明确建立并关联 Issue、Issue 列表／详情／仓库事项及房间查询。旧路径仅保留历史参考，未实现；页面建项、结果核查及房间查询已有采用的具体契约；其他模块与数据库表继续设计。

会话快照表达消息与通信状态以及允许看到的关联 Issue；Issue 快照表达总体工作、仓库事项、主 ChangeSet 与房间关联。Issue 最小创建后快照及 SSE 的游标、失效通知、重放／补查已按[创建契约](issue-page-create-api-contract.md)采用；会话消息及更完整的工作聚合协议继续细化。订阅围绕已保存事实和当前权限更新，业务关联存在不等于物理连接永不断开。

继续按推荐设计：反向多主会话、仓库事项数量／拆分／生命周期、会话内候选需求、消息协议及运行恢复。创建快照、命名、幂等保留、默认新建／可选已有、Manager MCP 统一命令、首次消息及页面建项提交后异步准备、Issue SSE 已按持续授权采用；这些不再列为待用户批准。

## 首批路由、状态与创建恢复（RM-PAGE-01 r1）

更新：2026-09-10。页面与后端已确认本节行为；创建线协议继续采用[创建契约 v1](issue-page-create-api-contract.md)。这是 P02／P03 的页面设计补齐，不表示项目／账号／列表等未编制协议已完成，也不表示原型或产品已实现。

### 路由与首屏结构

| 浏览器路由 | 首屏及来源 | 主要去向／恢复 |
| --- | --- | --- |
| `/login` | 登录入口、登录错误、返回目的地 | 仅接受站内允许路由作为返回地址，认证后重新核权。 |
| `/projects` | 可读项目列表、空态“创建项目”、查询刷新状态 | 进入项目 Issue 列表；新用户不自动造项目。 |
| `/projects/new` | 名称、用途、仓库选择和配置摘要 | 保存真实项目后继续配置或进入 Issue 列表；保存不建项、不启动。 |
| `/project-creations/{projectCreationId}` | 核查原项目创建，不依赖尚未知的 projectId | 查询原项目创建API；本地索引按主体、操作种类和键隔离。 |
| `/projects/{projectId}/issues` | 编号／标题／明确仓库／主 ChangeSet 引用，筛选和创建入口 | 进入独立 Issue 详情；筛选、查询参数可恢复。 |
| `/projects/{projectId}/issues/new` | 明确标题、描述、验收、本次仓库和关联会话 | 默认新会话；显式提交后进入操作恢复页或 Issue 详情。 |
| `/projects/{projectId}/issue-creations/{creationId}` | 查询这次创建操作；不依赖提前知道 Issue ID | 已提交去原 Issue；未知继续核查；已清理停止重建。 |
| `/projects/{projectId}/conversations` | 当前可读业务会话列表 | 进入同项目会话；列表存在不证明房间就绪。 |
| `/projects/{projectId}/conversations/{conversationId}` | 业务历史与关联卡片、独立运行状态 | 同项目其他 Issue、来源 Issue、实际房间；消息功能按后续契约。 |
| `/projects/{projectId}/settings` | 项目资料、明确仓库范围、配置引用及限制原因 | 保存后回读；不从裁剪后的仓库列表推导新的完整范围。 |
| `/projects/{projectId}/updates/{updateId}` | 核查原项目更新 | 查询原更新API，输入丢失只查，回执旧修订不冒充最新状态。 |
| `/issues/{issueId}` | 目标、约束、验收、仓库范围、来源、主 ChangeSet 和实际房间 | 从响应的 projectId 定位侧栏，业务记录与运行观察分区。 |
| `/issues/{issueId}/rooms/{roomId}` | 当前真实关联房间；Leader 只读 | 返回原 Issue／主会话；URL 和旧 canEnter 都不能代替服务端再核权。 |

这些是浏览器路由，不是新增 API。保留深色会话式风格及左侧项目分组，项目下展示会话；主内容随导航切换 Issue 列表、详情或会话，不引入固定三栏布局。窄屏将项目导航收起到可打开的抽屉，选中项目／当前页仍在标题处可辨认。详情首屏优先显示业务目标和当前可用动作；计划、验证、交付等后续数据尚无契约时不伪造完成百分比、执行枚举或可用按钮。

`fromIssue` 查询参数只保存返回来源。进入主会话后仍按正文与真实上下文识别消息目标；它不是默认执行目标或授权。敏感正文、凭据不进入 URL。嵌套路径中的项目与对象归属不匹配时显示不可用目标，不能用不匹配 projectId 发跨项目写请求。详情直达通过有权快照恢复项目选中态，不能按标题找同名对象。

### 共用页面状态及请求隔离

| 状态／触发 | 可观察表现 | 允许动作与数据处理 |
| --- | --- | --- |
| 初次加载 | 占位与加载指示，不显示空列表结论 | 可离开；只读重试不创建业务对象。 |
| 已成功且列表为空 | 区分“尚无记录”和“当前筛选无结果” | 创建或清除筛选；不能拿错误响应冒充空态。 |
| 查询失败／网络中断 | 明确读取失败；已有且仍获准的快照标记“可能过期” | 手动重试；恢复在线再查询，不重发写请求。 |
| 未登录／401 | 登录入口，敏感内容清空 | 关闭当前身份订阅，清身份范围的敏感缓存／草稿；登录后按原主体核查操作。 |
| 项目可见但动作被拒绝／403 | 可披露的限制原因 | 清受影响敏感对象、派生列表和选择器；提供仍获准的配置动作。 |
| 目标不存在或不可见／404 | “该内容不可用”，不披露受限对象 | 清该对象及派生缓存；返回有权列表。创建结果的特殊 404 见创建恢复表。 |
| 切项目／会话／Issue／查询筛选 | 新目标加载，旧请求结果不回填 | 中止旧请求只是节省资源；即使取消失败也必须丢弃晚到响应。 |
| SSE 断连／游标失效 | “连接中断，状态可能过期” | 按 Issue SSE 重新连接、补读快照；不把断流写成业务失败。 |

每次认证身份改变产生新的身份代次，每次路由或筛选改变产生目标代次。结果只有身份、资源 ID、筛选／排序、目标代次和该快照请求代次均匹配时才能落地；错误也须匹配，旧目标的 401／404 不能清空新身份的新页面。每个快照最多一个在途请求；请求期间收到失效通知记 dirty，结束后再查询一次；不同快照不把各自 revision 当统一时序。刷新和深链接均重新核权，本地缓存不授予访问。

### 创建到详情的完整流程

1. 从项目 Issue 列表进入表单。并行读取创建条件及需要时的已有会话候选；仓库分页保持已选 ID 集合，不全选新页或因缺席而删选。创建条件修订变化时回读并显示变化，用户明确确认新的输入后才作为新操作提交。
2. 默认关联新会话。用户选择已有会话后显示其名称和稳定身份关联；提交失权或失效时解释实际错误，不能静默改成新会话。未发出请求可取消且不产生对象。
3. 首次发出前产生并保存 creationId 和确切输入，进入提交中。按钮锁定这次逻辑操作的输入；取消等待、切页、关闭窗口均不宣称回滚。恢复入口可以在尚未知 Issue ID 时打开。
4. 201 或同键重放的 200 取得完整业务回执，进入该 Issue，刷新会话／Issue 列表并读取当前详情与 rooms。页面来源只显示真实创建卡片，不添加假用户消息或假 Manager 回复。
5. 详情首屏显示“事项已创建”，并单独显示实际运行观察：未取得关联／就绪依据时没有“进入房间”可用动作。有本地准备事实才显示准备中；实际接入不可用时明确显示未接入，不把健康探针当 Manager Ready。
6. 成功后运行失败仍保留 Issue／会话／主 ChangeSet。首批无仓库事项时显示“尚无仓库委派记录”；不能由选仓生成 Leader 房间。业务会话历史的读取入口与实际房间可进入性分别判断。

| 创建状态／依据 | 页面文案与动作 | 恢复约束 |
| --- | --- | --- |
| 未提交，本地校验不通过 | 标记字段，保留输入 | 不生成业务记录。 |
| 已发出、未收响应 | “正在提交”，可取消等待 | 保存原键和输入；退出后可进入操作恢复页。 |
| 网络中断、5xx、结果不明 | “提交结果待确认”＋查询原操作 | 不显示失败后“重新创建”的快捷动作，不自动换键。 |
| 查询 200 committed | “已创建”，打开原结果 | 不重验新建条件以否定旧成功；结果读取仍核当前权限。 |
| 查询 404 CREATION_NOT_FOUND | “暂未查到提交结果” | 不等于未创建；继续查或原键原输入重试，时间经过不构成失败证明。 |
| 409 IDEMPOTENCY_CONFLICT | “该操作已绑定另一份输入” | 核查原操作；新工作必须显式独立操作，不能冒充原操作重试。 |
| 409 条件／会话／分析不适用 | 解释可披露原因，保留有权输入 | 先排除同键在途不明；刷新并由用户明确修改，不暗中改仓库／会话／来源。 |
| 410 CREATION_RESULT_REMOVED | “原事项创建结果已清理” | 不返回旧正文，不提供旧键再建按钮。 |
| 401／403／404 RESOURCE_NOT_FOUND | 登录或内容不可用 | 清敏感数据；无权不可解释为没创建或换身份重建。 |
| 输入丢失但原键可恢复 | 只显示操作核查 | 不按标题／会话名拼请求重放；无法确认时保留未知。 |

## 首批关系与内容读权（RM-B01-04 r2）

2026-09-10，双方第 2／3 轮确认。本节是本轮对旧未定项的具体推荐采用，不追溯为 ADR-0019 当时已决定。上文“反向多个主会话”“仓库事项数量”等待细化描述，在首批范围内以本节为准；运行房间共享和完整消息协议仍待后续收口。

| 关系／限制 | 首批采用 | 页面表现与代价 |
| --- | --- | --- |
| Conversation → Issue | 一个会话可有 0..N 个 Issue；每个 Issue 恰好一个不可改绑的主／来源业务会话 | 支持创建时选同项目已有会话；不提供迁移或多个主会话管理。收益是来源和运行承接清楚，代价是暂不支持跨会话迁移。 |
| Issue → Repository Issue | 每个 Issue × Repository 为 0..1 个稳定仓库事项；首次实际委派时建立 | 创建选仓只显示范围，不生成虚假事项。事项下可有多个 Task／轮次；终止后重试保留原身份，完成后新增工作另建 Issue。 |
| Issue → ChangeSet | 默认一个主 ChangeSet 继续保留 | 同仓多任务或重试不创建重复主 ChangeSet；内部仓库事项不是嵌套变更集。 |
| 房间与事项 | 浏览器只展示实际 rooms 查询中允许披露的关联 | 房间跨事项共享仍需 B06；同仓 0..1 事项不推出物理房间拓扑。 |

Issue 正文、标题和聚合资料要求对其内容范围的全部仓库具有当前读权；内容范围包括当前工作范围及历史实际引入材料，只增不减。不能通过删除一个仓库范围或关联来解密旧正文。项目其他独立且仍有权的 Issue 不受该项失权牵连。

会话在没有可靠逐消息权限标注前，整体历史按只增的内容仓库范围并集核权。页面创建来源卡片时，同事务加入新 Issue 范围；表单选择已有会话后说明：“本次事项将加入该会话；查看完整会话需要具备其中所有内容涉及仓库的访问权。”这条说明不是新增人工审批。已有会话中旧 Issue 或消息不被迁移、改写；失权时不能只隐藏关联卡片却继续暴露旧正文。

自由消息采用保存当时整个项目仓库范围作为保守的内容保护范围；受控回复／工具结果引入额外材料时，先登记范围再发布内容。具体消息保存和工具发布协议由 P06/B05 完成，首批不假装已有完整逐消息授权实现。该策略的代价是一个仓库失权可能使整段跨仓会话不可读；项目外壳、配置修复和仍可读的独立 Issue 可继续使用。

只读 Leader 房间仍逐次核当前关联、就绪与读权，不因为用户是项目 owner 或能看某个主会话就开放所有 Leader 历史。首批不开放由浏览器指定任意 roomId 绑定会话的写接口。
