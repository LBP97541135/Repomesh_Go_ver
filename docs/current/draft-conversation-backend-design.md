## 1. 已确认入口与当前边界

先选择仓库并保存长期多仓项目，项目创建不产生正式 Issue、主 ChangeSet 或运行就绪事实。项目下的会话承载持续讨论，可以没有正式 Issue；会话内可明确建立、关联多个独立 Issue，会话本身不转正，标题、消息身份和历史不因建立某项工作而变成另一对象。用户也可从 Issue 栏直接创建，默认建立新的业务会话，也可明确选择同项目有权的已有会话；这一路径不要求预先存在或就绪的聊天房间，详见 §4.1。

每条正式 Issue 组织 RepoMesh 内部仓库事项，保留总体目标、范围、计划、验收与状态，由项目 Manager 总协调，默认一个主 ChangeSet。内部仓库事项可关联 GitHub Issue；外部关联不是建立工作前提，也不默认授权 GitHub 写操作。

Issue 专页可以进入实际关联的主房间与 Leader 房间。同一会话可以承接多项，不代表各项共用执行计划、上游 Project、验收依据或授权。具体业务会话到实际 room／角色 session 的映射仍待细化验证。

**现行准备入口：** 按 ADR-0018 持续授权补充，首次会话及首条消息提交后，或 Issue 栏创建提交后，自动异步准备／恢复项目实例和对应主房间；项目建立、空会话与只读访问本身不启动。是否保留会话内事项草案继续设计，不为兼容旧时序强制每条聊天建立 Draft Issue。

### 1.1 项目创建的后端衔接建议

本节按持续授权继续细化，已有建议不再等待逐项批准；完整项目创建契约及外部核查实现尚未完成。

仓库查询提供当前用户实际可参与的候选，提交使用稳定仓库身份及明确选中集合；显示名称可变化，不能用名称或搜索结果位置作为归属依据。分页、筛选、“全部选择”与列表刷新都不自动扩大集合。账号侧参与／读取能力与 App 执行能力分别表达，不把 App 可见仓库直接当成用户可参与仓库。

建议项目创建分为外部核查与本地提交两步，外部访问不占用长数据库事务：

~~~text
明确选仓集合 + 名称／用途 + 配置引用 + 创建操作标识
        |
核验创建权限、仓库身份及当前账号参与能力
核查 App 能力与配置，记录观察依据和时间
        |
短事务：创建项目 + 完整所选仓库关联 + 配置引用
        + 核验观察 + 幂等操作结果 + 必要的后续核查待办
        |
返回项目身份、配置状态与逐仓限制 -> 项目内需求输入页
        |
此时尚未因项目创建建立会话、正式 Issue 或 ChangeSet
~~~

项目保存必须保留用户提交的完整范围。若某仓库已无参与／读取资格，建议本次创建整体不落项目，返回允许披露的失败原因，由用户明确修改选择；不能静默删掉该仓库后创建另一范围。若用户仍可参与但 App 授权不足，则可保存完整项目并标明受限，不能误报可执行。用户资格无法核实与已确认无权限分别表达；建议前者保留本次请求供核查但不宣布创建成功，具体受理／重试契约继续设计。

App 或配置核查暂不可得时，项目能否保存可按已明确的待配置方向设计，但必须保留“未知／待核查”，不能伪写为缺少权限或已经通过。必要配置缺失不删除已保存项目，也不自动允许会话讨论或正式执行；保存项目、对话可用、特定仓库可执行分别核验。

提交事务检查本地相关配置／权限修订；外部权限在检查后仍可能变化，保存的核验结果只是一份带时间的观察，不是持续授权保证。后续读取、讨论和实际工作按当前能力重新核验；不把外部 GitHub 状态与本地事务描述为原子一致。

同一次项目创建复用逻辑标识和规范化输入摘要；同键同输入返回原结果，同键不同输入拒绝。超时先按原操作核查，即使项目尚未 Ready 也不能另建一个项目。名称不承担去重身份，所选仓库相同也不能据此合并两个独立项目。具体摘要规则、操作查询入口及并发约束仍待接口细化。

### 1.2 项目快照建议分开表达的事实

| 维度 | 返回含义与用途 |
| --- | --- |
| 项目身份与明确范围 | 已保存项目及仓库关联，支持后续会话与事项引用；稳定项目 ID 不因配置缺失而改变。 |
| 配置 | 配置引用、实际采用值、缺失或待核查项；模型密钥正文不进入项目响应。具体默认值继承和修订契约待细化。 |
| 逐仓能力 | 账号侧参与／读取能力、App 能力及缺失或未知原因、观察时间；不能用单个“已授权”掩盖差异。 |
| 运行观察 | 实例是否已关联、正在准备或可用及观察依据；创建项目成功不能自动写 Ready。实际状态枚举未冻结。 |
| 当前可用操作 | 按当前身份与配置判断可保存／继续配置／发起对话等能力，并说明受限原因；客户端展示结果不代替服务端核权。 |

无需为了进入项目就创建草稿或会话。项目快照在无事项时也应可读；会话 SSE 只有会话存在后才有归属。项目级变化先需要可靠快照查询，是否新增项目 SSE、事件名称和刷新频率继续设计，不用创建一个空会话承载项目事件。

项目创建只保存业务资料和必要核查工作、不立即启动实例的决定继续有效。ADR-0018 原以首条 Draft Issue 为触发对象；其持续授权补充现已适配首次会话消息及页面 Issue 创建提交两类触发。项目实例失败不能撤销已保存业务项目。

## 2. 对话准备：提交后自动接续（已采用）

按[ADR-0018](../adr/0018-provision-instance-after-first-draft.md)新补充，首次持久保存业务会话及首条消息，或 Issue 栏创建提交成功后，后台自动异步准备／恢复项目实例和对应主房间。已存在的实例和有效房间复用，项目建立、空会话或只读访问本身不启动。

~~~text
首次会话消息，或页面 Issue 明确创建
    -> 核验本次保存条件
    -> 同事务保存必要业务记录与持久待办
    -> 返回已保存事实
    -> 后台核验当前权限／配置／预算／容量
    -> 准备／恢复项目实例及对应主房间
    -> 实际 Manager 与房间就绪
    -> 投递真实消息，或接手已登记的页面 Issue
~~~

项目、业务保存、准备请求、房间 Ready、传输投递、Manager 接收／处理与实际工作分别取证。页面创建记录不伪装成用户消息，Manager 接手不再次创建 Issue；有持久待办不代表永久执行授权。外部准备与模型调用在本地事务外，准备失败保留业务事实；超时或重启查原操作，不换身份盲重建。

这使明确提交后自然接续，代价是可能更早产生运行和模型消耗。纯讨论不直接建立正式计划、上游业务 Project、Worker 任务、分支或 PR；无 Issue 消耗记录真实项目／会话归属，不借以后建项清零。无 Issue 工具范围、费用具体分配继续设计。

并发触发复用项目实例原准备操作，各会话保持自己的运行关联；选择已有会话不重置其消息或其他 Issue。具体领取、代次、状态核查和资源恢复算法继续设计／待验证。房间存在、成员加入与模型可处理消息分别核查，不承诺已经具备“仅启动 Manager”的部署模式或完整隐藏上下文恢复。

### 2.1 DESIGN-001：准备期间保存补充、就绪后依序尝试投递（已确认保障）

用户于 2026-09-09 明确采用准备期间向原草稿保存补充、就绪后依序尝试投递，原话与范围见[通信日志](../archive/2026-09-12-development-preparation/docs/current/design-communication-backend-log.md)的 DESIGN-001 记录。ADR-0019 改变会话与事项关联，不撤销以下保障；原确认以同一草稿为顺序范围，新模型的会话／事项消息目标及具体顺序范围仍需细化，不能据此假定多个 Issue 共用一条执行队列。

- 消息与投递待办一起持久保存，成功后表达“已保存，待投递”；准备期间允许补充，复用原准备工作，不重复制造会话、实例或房间。
- 首条与后续补充以服务端持久保存顺序依序尝试投递，就绪前后新消息不插队；前序结果未知先核查，后续等待并说明原因。不承诺模型处理／回复顺序或外部 exactly-once。
- 保存失败保留输入，结果未知查询原逻辑操作；准备失败保留已保存消息和归属，不换键盲目重建。
- 实际 Manager 与本条房间就绪、传输成功、Manager 接收／处理各需依据；拿不到接收证据时保留未知。
- 保存、实际投递和历史读取分别核验当前权限及限制；已保存不代表永久执行授权。准备和对话状态不能授权执行某个关联 Issue 的工作。

例如等待对话准备时保存“增加支付状态筛选”和“保持历史订单兼容”，第二条已保存不证明 Manager 的工作整理已包含它。会话随后关联订单导出 Issue，也不能把先前筛选消息、操作或结果改归导出。

## 3. 会话与工作归属

### 3.1 已确认对象关系

~~~text
长期多仓项目
  +-- 会话：标题 / 消息 / 讨论历史 / 运行关联
  |     +-- 可关联 Issue A：支付状态筛选
  |     +-- 可关联 Issue B：订单导出
  |
  +-- Issue 专页
        +-- 本项整体目标 / 计划 / 验收 / 状态
        +-- 内部仓库事项，可选关联外部 GitHub Issue
        +-- 本项主 ChangeSet / 候选 / 组合 / 交付历史
        +-- 实际关联的主房间与 Leader 房间导航
~~~

图表示已确认的正向能力，不决定一个 Issue 可关联几个主会话、每仓事项数量或 Leader 房间共享粒度。仓库事项与 Task、Attempt、上游 Project 不互换身份；新增仓库事项不默认新增或嵌套 ChangeSet。

ADR-0012 的正式 Issue × 仓库委派范围继续作为上游工作隔离依据。同一会话谈 A、B 时，A 的计划应用、Worker 结果和验收不能按页面当前选择误记到 B。两项共享团队额度，不各自多获一份 Worker 或预算。实际模型上下文怎样承接多事项且保持执行隔离仍待验证，业务 ID 不构成已实现隔离的证明。

### 3.2 DESIGN-003：自然语言明确目标，歧义先澄清（已确认方向）

2026-09-09，页面在解释误判可能、后端校验边界及手选目标的备选后，询问是否采用本方向，用户回答“是的”，并提出另行评估 Manager 创建 Issue 的 MCP 工具。前半句确认 DESIGN-003，第 1／3 轮收口；后半句当时属于 DESIGN-004 新提议；后续持续授权才采用受控创建机制，不倒填为该句已批准全部方案。准确原话与时间见[后端通信日志](../archive/2026-09-12-development-preparation/docs/current/design-communication-backend-log.md)。

用户继续用自然语言交流，无须在每条消息发送前手动选择 Issue。Manager 根据明确编号、名称或无歧义的对话内容识别目标和动作；普通询问／讨论可以不关联正式事项，提到某项不自动表示要求执行。

- “给订单导出加日期范围”可明确针对对应 Issue；“导出支持日期范围吗”是询问，不能因此修改工作。“这个也加上”若无法唯一指向，应先澄清，保留原消息，未明确前不据此改计划或派工。
- 从其他 Issue 页面进入房间只提供导航来源，不能覆盖明确的正文目标。名称歧义、编号与正文冲突、目标缺失或无效时，不用当前标签页、最近事项或模型置信度兜底。
- 具体工作操作落到稳定 Issue、动作及相关版本，后端核验当前项目／关联、权限、业务状态、计划、预算和容量等既定条件；目标足够明确且条件满足时按现行 YOLO 继续，不新增逐条确认或开工审批。
- 处理记录显示可辨识的工作目标与动作；澄清仅提供当前可读的候选，可读不等于可执行。保留用户原消息、相关公开上下文／澄清答复及业务结果，不要求记录模型隐藏推理。澄清答复必须对应原消息与问题，不能因后来的页面或问题改绑。
- 消息保存、等待澄清、目标确定、操作受理与实际执行结果分别取证。等待某条消息澄清不等于暂停已有获准工作，也不取消 DESIGN-001 的前序投递未知等待保障。
- 恢复、重试和晚到结果沿原 Issue、逻辑操作和适用版本核查；切换页面不能重新计算归属。用户纠正目标时追加更正，不改写原消息或已发生事实，不把原操作身份改绑到另一目标重放。

后端的结构和权限校验不能证明模型语义一定正确；一个存在且有权的 Issue 仍可能被选错。显示目标或模型高置信度不等于用户已确认，也不承诺零误判。采用该方向保持自然交流，代价是维护来源、目标展示、澄清和更正过程；强制每条消息手选目标不作为本轮方案。

具体识别算法、控件、澄清协议、操作字段、批量跨 Issue 命令、自动默认目标、在途更正及补救流程按持续授权继续设计。创建工具、输入快照和启动触发的现行选择来自后续采用清单，不追溯归入 DESIGN-003。

### 3.3 历史、运行恢复与执行归属

业务会话及原消息身份保持稳定，建立 Issue 不把历史复制成新消息或重新当作新操作执行。读取历史、恢复上下文、重新执行工作是不同动作；旧工具请求不能借新建 Issue 自动补获执行许可。

已提交的 Issue、主 ChangeSet 或消息事实不能因 runtime 恢复失败而撤销或重新建一套；恢复失败保留原关联和实际受阻情况。用有权读取的历史恢复上下文不等于保证原模型隐藏上下文完整保留。各次查询、发送、投递、工具执行分别核验当前业务目标及权限，不再对整条会话使用单一“已正式”状态授予所有操作。实际运行映射和恢复算法未冻结。

## 4. 正式 Issue 建立：双入口与原子保存（已采用）

### 4.1 创建入口与来源会话

页面表单和项目 Manager 受控 MCP 共用同一业务创建命令、当前条件校验、持久化和结果查询逻辑。Agent 创建能力首期仅向项目 Manager 开放；身份、发起人权限、项目与会话来源由可信上下文绑定，不相信模型自报角色或“用户已批准”。工具只接入业务入口，不授予数据库直写权。

- 页面默认新业务会话，也可明确选择当前项目有权的已有会话。提交时重验选择资格；失效时返回错误，不静默换成新会话或其他已有会话。本次只指定一个来源，不预先定义该 Issue 将来的多主会话关系。
- Manager 依据真实用户消息及明确创建意图调用；普通讨论不创建，有歧义先澄清。页面来源保留真实表单提交，不能伪造用户聊天或 Manager 回复；页面已建 Issue 不再由 Manager 重建。
- 新会话初始标题取 Issue 标题，此后独立改名。已有会话保留原名、历史和其他关联事项；不把会话整体转正或复制旧消息。
- 正式保存不要求 runtime Ready、已生效完整计划或 Worker 已启动。成功返回稳定 Issue、主 ChangeSet、来源业务会话身份；页面进入详情，再按真实状态提供主／Leader 房间入口。
- 创建提交后的运行准备按 §2 自动接续；创建、接手、计划生效与派工分别取证，来源和当前页面选择不授权后续执行。

原“默认新建会话”（2026-09-09T12:42:29.811Z）只确认默认值；P1“确定”（13:03:30.896Z）只扩展当时列明原子范围。可选已有会话、双入口及后续细节依据 13:12:51.158Z 的持续授权采用，完整原话见[后端日志](../archive/2026-09-12-development-preparation/docs/current/design-communication-backend-log.md)。

### 4.2 本地事务、输入与幂等

按[ADR-0016](../adr/0016-transactional-background-work.md)持续授权补充，同一本地短事务登记：

~~~text
Issue + 默认主 ChangeSet
  + 必要的新业务会话，或对既有会话增加本次关联
  + 来源关联 + 真实创建记录
  + 允许字段的确切输入快照 + 规范化摘要及版本 + 可信来源
  + 幂等创建结果 + 后续持久待办 + 相应持久事件
    -> 一起成功，或一起不生效
~~~

快照只保存允许字段、已明确的目标／范围／验收内容及可信操作者／来源；Manager 入口引用真实消息，不把推断写成用户确认，不保存密钥、凭据或隐藏推理。文本保留确切提交，规范化规则用于稳定比较而不改写意图；字段与限制以[创建接口契约](issue-page-create-api-contract.md)为准。新建仓库事项的数量和生命周期不由仓库集合自动推导。

同一逻辑操作重试返回原 Issue／CS／会话，不同输入冲突；明确新工作使用新的操作身份，相同标题不自动合并。双入口使用同一业务幂等机制，但各自可信身份及来源不能混用，MCP 传输调用号不直接当持久创建意图身份。规范化输入与原键绑定，切页不改归属，不能将重试从新会话改为已有会话。

操作键在项目保留期内不复用。删除正文仍保留最小无正文占位以阻止旧请求重建；核当前权限后返回 410 CREATION_RESULT_REMOVED，不进入正文比较或新建分支，不向已失权调用者泄露旧内容。物理删除项目后旧身份不能复活。实际索引、锁、数据库隔离、占位字段和清理执行继续设计／待验证。

未提交前取消或本地表单验证失败不建项；请求发出后的超时、断连、取消等待不证明回滚。结果未知查询原操作；查询暂未找到不证明旧请求不会提交。已提交结果仍按当前读权提供，不因新的创建条件变化将历史成功写成失败。后续运行关联恢复失败不能删除已提交业务事实。

外部权限核查、实例／房间准备、模型调用都在事务外。接受输入、关联、幂等占位和事件维护成本，换取完整提交、来源追溯与可靠恢复；不承诺跨系统原子事务或 exactly-once。

### 4.3 创建协议的当前完成度

后续采用的[建项前仓库分析](issue-creation-repository-analysis.md)由 Go 持久作业调用受控 Python 插件，独立于业务建项和 AgentTeams 准备。分析可以先返回 202；Issue 创建仍须本地提交后返回 201／200。可选 `repositoryAnalysisId` 的输入、核权、失效及同事务来源记录由创建契约统一维护；分析失败允许手动建项，不能把旧 DiscoveryChain 的计划或审批前置条件迁入此入口。

[页面创建契约](issue-page-create-api-contract.md)作为当前 REST 设计基线：创建条件、可关联已有会话候选、POST 创建、原 creationId 查询、Issue 详情、实际房间和 Issue 级 SSE。候选分页和请求限制按该契约。首次本地提交返回 201，已提交同输入重试返回 200；不等待运行就绪，不采用未完成持久化的 202 成功表达。具体 schema 由该文件维护，后端不复制另一套字段。

Manager MCP 采用 repomesh_create_issue 与 repomesh_get_issue_creation，共用业务创建及查询；输入沿用页面业务字段和限制，来源会话固定为可信当前会话，逻辑操作及真实消息引用由适配层承接。输出复用持久回执业务字段，source.kind 为 manager_mcp，原操作通过查询工具核查，不返回仅接受页面操作的 links.operation。名称及业务职责已采用；transport、可信上下文签发／绑定、来源句段与完整可执行 JSON Schema 继续设计，工具未实现。会话通信协议、仓库事项、列表与聚合工作状态尚需完成，依持续授权推进，无须等待逐项批准。

### 7.1 B01：真实身份与逐操作授权

首批保存项目时创建者为 owner，项目外壳只向该 owner 开放；不根据GitHub组织成员、同仓协作者或知道projectId自动授予RepoMesh项目访问。暂不开放邀请、成员管理、账号合并或所有权转移。该选择减少首批共享权限模型的歧义，代价是暂不支持多人协作入口；后续新增角色必须显式定义。

服务端稳定 userId 绑定 provider＋host＋外部账号ID；login／email／展示名变化不改变主体。登录凭据、当前本地会话、GitHub账号侧权限、App安装能力和项目访问分别建模。浏览器只发送业务输入；userId、role、owner或“用户已同意”均不接受为权限证明。

| 路径／控制者 | 真实主体和可用证据 | 允许传递的内容 | 禁止依赖的输入 |
| --- | --- | --- | --- |
| Web认证入口 | 已核验回调绑定的本地会话、userId、账号连接版本、当前本地访问状态 | 应用层 TrustedActorContext；审计仅稳定ID／请求ID | 请求体userId、email匹配、客户端角色或URL中的账号。 |

### 7.2 会话认证与凭据边界

后端建议浏览器采用同源、服务端保存的不可预测会话标识；生产Cookie使用Secure、HttpOnly、SameSite=Lax、Path=/及__Host-前缀，不设Domain。服务端只存会话标识的验证摘要、稳定userId、会话代次、到期／停用时间。初始建议绝对有效期12小时、空闲30分钟；部署可收紧，实际参数与认证接入协议收口后统一。登录成功／提权／更换凭据后轮换会话身份，注销先本地失效，后台不能借旧会话继续发起新的用户写操作。

写请求同时校验Origin和会话绑定CSRF值，GET不修改业务。CSRF值不是用户身份或长期密钥；不进URL、恢复索引、审计正文。认证回跳必须绑定服务端保存的一次性state、发起会话和允许的站内returnTo，使用PKCE S256，拒绝重复／过期／串浏览器回调；token换取和当前用户身份查询均在服务端。真实登录／账号连接路由、会话丢失恢复及供应商错误映射仍需与页面认证协议对齐，不能把本节当已完成登录接口。

| 凭据 | 保存与使用者 | 轮换／失效处理 |
| --- | --- | --- |
| GitHub用户访问／刷新令牌 | 按userId＋外部账号ID保存加密正文、版本、到期和授予能力；限认证／授权适配器解密 | 轮换使用版本CAS防并发覆盖；刷新结果未知先核原凭据状态，不打印token或当作新账号连接。 |
| GitHub App私钥 | 部署秘密存储，业务表只引用；仅安装身份凭据签发路径可读 | 本地停用版本立即阻止新签发；旧已发令牌仍按其实际到期／撤销证据处理。 |
| 安装访问令牌 | 后端受控调用路径按本次仓库和操作收窄，短期内存或加密缓存 | 安装权限／范围变化失效缓存；不能拿持有token证明用户仍有权。 |
| 模型API Key | SecretVersion归属用户，项目引用有权的model profile；设置端只能写新版本／停用，不回读正文 | 禁止审计、来源快照、队列、SSE和导出包含密钥；停用阻止新调用，已发调用的费用／结果单独核查。 |
| 内部运行能力 | B05/B06定义项目、角色、会话、目标、操作和代次的有限授权 | 不与浏览器会话或用户凭据共用；实际撤销／围栏能力待验证。 |

数据库加密使用应用层认证加密与独立部署密钥／密钥服务引用，记录keyVersion与nonce；加密上下文绑定secretId、owner和用途，禁止通过改引用挪用他人密钥。数据库备份不能携带同份解密根密钥；日志使用结构化白名单脱敏。具体秘密存储产品、首次设置流程和密钥恢复责任尚未选定，B01不据此标全完成。首批项目引用契约可以完成，但从全新部署配置Key到成功建项仍有明确接入缺口。

浏览器注销／会话到期不会撤销已提交业务事实，也不自动取消已登记待办。后台以原操作的稳定actor及当前账号／项目／仓库资格核权，不要求原浏览器Cookie续期；本地停用账号、撤销项目访问或相关凭据失效则阻止新的受影响动作。两种失效不能混为同一个生命周期。

配置固定规则按RM-API-01 r3：仅显式提交configuration时重新解析profile／secret版本；后台发现失效只更新观察与创建条件，不切换配置。管理面creationReadiness和configurationRevision均不能作为运行就绪证据。字段以[首批浏览器契约](first-batch-browser-api-contract.md)为准。

### 7.3 权限观察与失权

每份后端观察绑定actor、账号／凭据版本、仓库稳定ID、操作能力、结果allowed／denied／unknown、reason、observedAt和本地accessEpoch。账号参与／读权、App能力、项目范围、本次Issue范围、内容范围及操作约束取交集；任何项unknown都不能作为allowed。外部API失败、限流、组织授权待处理或网络中断不直接写denied。

建议查询允许最多60秒的成功权限观察；新业务写要求本次重新核查且观察距本地提交不超过15秒。值是初始保守策略参数，不是GitHub撤权发现SLA；核查失败后不得使用失效或被本地撤销的旧allow兜底。列表每页、详情每次、订阅发送和后台动作都重验本地accessEpoch与观察时效；过期先重新核查，未得到有效结果则unknown。

| 操作 | 本地／外部核验 | 已知不足／未知／恢复 |
| --- | --- | --- |
| 读取项目外壳、修复名称／用途／配置引用 | 当前owner和本地有效账号；引用可见可用范围 | 旧仓库失权仍能修配置；不回显旧仓名。配置引用不可见隐藏404，已知不可用可保存受限。 |
| 保存新项目／明确加仓 | 所有新加入仓库的当前用户参与／读权；整体有效集合 | 任一无权整体拒绝；任一未知503；App不足／未知不妨碍保存完整项目。 |
| 项目范围查询／候选仓库 | 当前主体对可披露仓库的有效读权；分别观察App能力 | 未核实身份／名称不回传；覆盖不足显示partial／unknown，不声称全量。 |
| 创建Issue | owner、明确Issue仓库集、配置引用／额度／预算、用户与App必要工作能力、所选会话完整读权 | 已知门槛不足用创建契约409；未知503；不等待runtime或计划／Worker就绪。 |
| 查询原创建结果 | 原作用域actor＋项目资格＋结果的全部内容读权 | 不再核新创建条件；失权隐藏结果，unknown不谎称不存在，removed按有权410。 |
| 读Issue／会话／历史／SSE | 对象内容范围所有仓库的有效当前读权；本地资格／版本 | 不能只过滤卡片后泄露正文；受限关闭订阅，其他可读Issue不受牵连。 |
| 后台接续／Manager工具 | 原actor当前权、来源／目标、配置、适用预算等；每次动作重核 | 失权停止新的无权动作，待办blocked并保留事实；不换系统actor继续。 |
| Git／Worker真实执行 | 另需计划许可及生效、Attempt预留、资源与目标分支限制 | 本批不启用；只推任务分支／draft PR及人工合并边界维持。 |

外部变化通过主动核查和未来经签名验证／去重的webhook进入观察；webhook只使对应观察失效并触发核查，不凭未核事件授予权限。各更新路径增加本地accessEpoch，正在提交的命令锁后重验。SSE每次发送／心跳核本地访问；需要外部刷新但尚未确认时暂停内容发送或结束连接，客户端回REST核查。不承诺15秒内发现外部撤权。

检测到失权时：先阻止新的受影响操作；标记并暂停待办推进；保持已提交Issue／CS／来源；触发原操作核查。已经发出的请求或旧进程可能仍有副作用，停止请求、实际停止、身份失效和资源释放分别取证。权限恢复后重新核验原目标／版本／预算，再续同一待办；不自动复活已终结Issue、清零费用或创建替补Attempt。

### 7.4 GitHub接入事实与尚未闭合点

GitHub App用户令牌受用户权与App安装资源范围共同限制，不能用它查询到的仓库交集宣传“用户全部可参与仓库”。GitHub允许用户授权App而尚未安装，但资源访问仍受安装范围约束。依据：[GitHub用户身份访问说明](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-with-a-github-app-on-behalf-of-a-user)。

首批认证推荐优先使用GitHub App细粒度用户授权；仓库发现表达实际coverage，缺安装外私仓发现时标partial／APP_INSTALLATION_SCOPE。J1的完整参与仓库目标仍保留为接入缺口，不能把“仅已安装仓库”偷偷改成最终产品范围。另一个候选是独立OAuth App的账号发现授权，但其repo scope包含广泛仓库读写，不能称为“只读账号绑定”或默默向用户请求。是否增加这条明确授权路径与页面入口，须作为认证接入方案继续对齐；本任务没有创建App、索要token或访问私仓。依据：[GitHub OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps)。

官方GET /user/repos列举用户拥有、协作以及组织成员资格可访问的仓库；实际覆盖还受使用的token和组织条件限制。只有成功走完适用分页且不存在已知覆盖限制才可报告complete；上游分页与本地稳定ID游标需要独立发现批次／归并，不把上游page直接伪装成固定快照。依据：[GitHub仓库列表](https://docs.github.com/en/rest/repos/repos#list-repositories-for-the-authenticated-user)。认证回调state和PKCE依据：[GitHub OAuth授权流程](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)；具体所选GitHub App流程还须按其对应参数契约验证。

GitHub App对应的[用户令牌生成流程](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)也列明state和PKCE S256，故§7.2的回调保护可作为所选方向的设计要求；真实回调绑定、刷新并发与撤销传播仍须独立验收。

以上核对仅为公开文档事实，不是本地登录、邀请仓库、组织SSO、权限撤销或完整枚举实测。当前B01可交付身份责任／凭据边界／核验表，但认证线协议、账号发现覆盖和设置密钥全流程未收口。
