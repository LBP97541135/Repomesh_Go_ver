## 3. B方案：登录、重连、退出与恢复

### 3.1 身份与最少内部记录（均待审）

| 内部责任 | 保存内容与约束 |
| --- | --- |
| 登录尝试 | 不可预测的尝试标识、state验证摘要、发起浏览器绑定摘要、用途login或reconnect、允许的站内返回目标、期限、代次及终结原因。PKCE verifier只在服务端受保护存储，短期使用后清理。 |
| 服务端会话 | 不可预测Cookie的验证摘要、稳定userId、账号停用代次、创建／最近有效活动／绝对到期时间及撤销时间；CSRF绑定本会话。服务端不保存可回显的会话Cookie正文。 |
| GitHub连接 | 稳定外部账号、加密访问／刷新令牌及其版本／真实到期信息、本地连接代次和检查观察。凭据明文不进入日志、队列、浏览器或恢复索引。 |
| 授权观察 | actor、host、稳定仓库ID、操作能力、凭据版本、accessEpoch、allowed／denied／unknown、原因和时间。读权与App工作能力分别保存，不从登录成功推出允许。 |

生产Cookie沿既有建议采用__Host-前缀、Secure、HttpOnly、SameSite=Lax、Path=/、不设Domain。本批候选要求同源HTTPS接入；本地HTTP开发例外与测试配置以后明确，不让生产自动降级。登录尝试绑定Cookie与正式会话分开，均不使用localStorage保存凭据。

所有非回调写请求核精确Origin；已登录写请求再核当前会话CSRF。未登录发起登录采用同源JSON请求并拒绝缺失／不匹配Origin，由服务器创建浏览器绑定和state。跨站回调是OAuth协议的专门入口，不要求它携带业务CSRF；它必须通过state、PKCE及发起浏览器／代次检查。普通GET不提交项目或其他业务。

### 3.2 成功流程与竞态边界

1. 用户点登录，Web创建有期限的尝试。目的地只允许解析后的站内白名单页面；拒绝外部URL、协议相对地址及编码绕过，不把业务草稿、仓库名称或密钥放入state／returnTo。
2. Web生成GitHub授权跳转；App client_id、固定callback、state和PKCE来自部署及该尝试，页面不能自行更换供应商地址或scope。浏览器跳GitHub，由用户授权。
3. 回调先核尝试、浏览器、期限与代次，以数据库比较更新领取唯一的交换责任。外部token交换在事务外；同一尝试不得并发或重复换code。重复／过期／旧代次回调不能再签会话。
4. 服务端取得token后查GitHub当前账号，用真实稳定ID选择本地主体；新身份和连接绑定依唯一约束保存。reconnect必须与发起时绑定账号相同，不符合则保留旧绑定、提示重新选账号；不能自动迁项目或合并身份。
5. 短事务重新核本地账号、尝试／连接代次，保存加密凭据版本与新会话摘要、终结尝试。外部结果迟到、用户已注销或新尝试使旧代次失效时，不允许旧回调重建登录。
6. 提交后才发送正式会话Cookie，并以303返回该尝试固定的resultPage。页面分别读取原尝试结果和当前/api/session；按认证候选A02核验Destination后，由用户明确继续。认证成功不直接跳回业务页，也不自动重放旧写入。

“同一浏览器开始新登录尝试会使旧尝试失效”是本方案候选；多标签页旧流程应提示重新登录，不反复互相签入。已登录账号重连与初次登录分开；新标签页不能借旧匿名回调切换当前账号。退出只撤销请求session及其绑定代次的未完成尝试；仅当前BrowserBinding代次仍与请求session相符时推进失效。迟到的旧session注销不能撤销新session或新尝试。

GitHub官方列明App用户授权流程的state、PKCE S256、client secret服务端交换和身份查询；这些是上游能力事实，上述尝试／会话记录及恢复处理是RepoMesh提案。[官方用户令牌流程](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)

### 3.3 失败、未知与重新登录

| 情形 | 候选处理及页面影响 |
| --- | --- |
| 用户在GitHub拒绝 | 有效state绑定下终结此次尝试，显示未完成登录；允许用户显式发起新登录，不自动反复弹授权。 |
| state／浏览器／PKCE不符，尝试过期或已消费 | 不签入、不改账号。能可信映射原尝试时返回其固定resultPage；非法state或无法可信映射时返回固定/login。不得反射任意错误描述、凭据或原始returnTo。 |
| token交换超时／进程中断，无法知道code是否已消费 | 尝试保留未知／终结依据，禁止重复交换旧code。若正式会话不存在，由用户重新登录取得新code；认证重做不触发业务写入。没有通用上游“找回遗失token”能力承诺。 |
| 已拿token但账号查询临时失败 | 在同一未过期尝试内可重试只读身份查询；不得先绑定猜测账号。尝试失效后不把晚到结果写入新连接。 |
| 首次登录提交成功、响应／Cookie是否到达未知 | 先GET/api/session；200只证明当前本地会话有效，页面按当前返回的稳定身份继续，不反推该次尝试的提交结果；401则显式重新登录，不通过重放callback再造Cookie。可能遗留的不可达会话受期限约束并可清理。 |
| 已有有效会话下，账号重连结果／响应未知 | 保留本次重连待核状态。GET/api/session的200甚至githubConnection=connected都不能证明本次重连提交，也不能因此再次交换原code。需要核本次尝试结果及其与当前连接代次的对应关系；查询身份、请求和结果字段沿[认证候选 §5](authentication-browser-api-draft.md#5-尝试查询与重连回执)，采用并实现前不把重连恢复标完成。 |
| 本地会话到期／注销 | 清对应身份敏感视图、缓存与订阅。重新登录后核对稳定userId；只有同主体才能按已有契约查询原业务操作，不能靠登录成功自动重发。 |
| token刷新明确失效 | 标连接缺失或需重新授权的已知事实，同账号重连；本地仍有效会话可进入允许的修复页面，GitHub读权不能沿用失效观察。 |
| token刷新结果未知 | 按凭据版本保存未知并停止并发刷新旧token；先核原版本／可能已保存的新版本。不能获得有效凭据时提示同账号重连，不把未知当撤权或刷新成功。 |
| 注销请求响应丢失 | 页面保持注销结果待确认，GET/session核状态；仍有效时允许对当前会话再次注销。只清当前浏览器Cookie不能证明服务端已撤销；数据库失败不能报注销成功。 |

刷新需在外部调用前领取该连接版本的唯一刷新责任，结果用CAS和账号／连接代次写入。原刷新执行者未终结且结果不明时，不因租约过期发起并行刷新；受控重连可用新代次替代，旧结果不能覆盖新凭据。GitHub说明使用refresh token成功后旧refresh token及旧access token失效，故最终CAS本身不足以阻止上游重复刷新。[官方刷新语义](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens)

本地会话期限与GitHub令牌期限不同；以实际响应期限保存，不把12小时会话当12小时GitHub授权。初次登录／用户主动重连轮换浏览器身份；服务端常规token刷新不要求所有浏览器同步换Cookie，但须更新连接代次并使旧外部观察失效。本项是对后端专项“更换凭据后轮换”范围的待审细化。

回调URL中GitHub提供的code／state只用于该端点，接收后立即回到无敏感查询的站内页；回调及代理访问日志不记录查询串，不加载第三方资源，响应禁缓存并禁外发Referer。认证错误页不直接展示供应商响应正文。

### 3.4 交页面维护的候选HTTP职责

下列路径与行为均未采用，完整请求、响应、错误及返回目标已经列入[唯一认证候选](authentication-browser-api-draft.md)。本表只说明内部责任，不维护第二套HTTP字段。本稿不增加现有/api/session字段。

| 候选入口 | 用途及结果职责 |
| --- | --- |
| POST /api/auth/github/login | 未登录同源发起；仅接收允许的站内返回目标。返回服务器生成的授权导航目标，页面执行顶层跳转；不让fetch跟随跨站OAuth充当登录。 |
| GET /api/auth/github/callback | 仅接收GitHub回调，完成§3.2的验证；以站内重定向清除code／state，不在JSON返回token。 |
| POST /api/auth/github/reconnect | 有效会话及CSRF，同账号修复连接；绑定现有稳定账号和连接代次，不提供换绑。 |
| POST /api/auth/logout | 当前会话及CSRF；仅撤销请求session及其绑定代次，具体比较沿§3.2。注销响应不发送删除会话Cookie的Set-Cookie头，旧Cookie由服务端拒绝并按原期失效。会话已失效时经同源检查幂等204，不撤销新会话或其他主体。不撤销GitHub App、不取消已提交业务。 |
| GET /api/auth/attempts/{attemptId} | 原尝试回执按认证候选核发起浏览器绑定；reconnect另核原actor或同actor轮换会话，结果与当前session分读。 |
| GET /api/session | 沿已有契约：有效会话与GitHub连接观察分开；本地401不是GitHub超时的替代。 |

认证结果页、Destination、限流参数、错误映射、回调303及原尝试查询以[认证候选](authentication-browser-api-draft.md)为准；草稿清理和原业务恢复另见[页面恢复候选](first-batch-recovery-design.md)。现有GET/api/session不承担原尝试回执职责，不新增session字段，也不允许匿名查询任意登录尝试。

## 4. A方案：发现来源、覆盖与权限

### 4.1 为什么首批保持“当前已发现”

GitHub App用户token同时受用户与App资源范围限制；不能用安装token越过用户读权。GET /user/repos支持按拥有／协作／组织成员列出当前token可访问的仓库，需要适用权限且有上游分页。OAuth App的repo scope则包含广泛读写能力，不能标成只读账号发现。[用户token说明](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)、[账号仓库API](https://docs.github.com/en/rest/repos/repos#list-repositories-for-the-authenticated-user)、[OAuth权限范围](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps)

推荐首批只启用已明确授权的GitHub App路径，使用当前用户token的账号仓库结果，不额外抓取全站公开仓库、不索取PAT或宽repo授权。即使走完上游分页，也只能表达当前凭据覆盖；安装范围外私仓仍可能遗漏。既有coverage=partial／APP_INSTALLATION_SCOPE原义保持，nextCursor=null不升级为complete。完整J1另留后续方案，不能声称已满足。

授权App和安装App是不同动作；本站收到installation_id或浏览器“安装成功”回跳不能直接授予能力。只接受受控GitHub查询得到的当前安装、仓库与权限事实；未实际核实为unknown。首批若要提供安装修复入口，其跳转／返回校验需要另列契约，不在登录接口暗中兼任。

### 4.2 内部发现与现有列表的衔接

待审建议：后端记录发现批次，绑定actor、host、连接版本、扫描进度及实际覆盖原因；仓库按GitHub稳定ID归并。本地游标绑定主体、查询和批次／最后扫描位置，不公开上游page或凭据。每次返回先核当前本地代次及仓库读权，再投影名称；旧批次不能绕过撤权。

上游分页不是跨请求不变快照。扫描中出现新仓、改名、转移或权限变化时不能承诺一次遍历无遗漏。每页工作须有界；扫描未完、限流或预算耗尽保留partial／unknown及实际续查责任，不能把截断称全量。如何分段扫描／封存批次、游标过期与新发现刷新，须与页面现有游标错误及搜索保选行为继续细化；不在本稿把候选总数固定为100。

沿现有契约区分三种数量：列表一页最多100、单次明确新增集合最多100、保存后项目范围最多100；候选可发现总量没有因此限定100。q只筛当前可披露候选，未找到不证明账号没参与。

| 观察 | 外显处理沿现行契约 |
| --- | --- |
| 仓库用户读权有效，App工作能力缺失 | 可返回仓库并明确App不足；仍可选择及保存项目。 |
| 仓库用户读权有效，App查询超时 | 可返回仓库，App能力unknown；新建Issue不能把它当允许。 |
| 用户读权未知或已拒绝 | 不返回旧ID／名称。新增集合任一未知阻止整次含增量保存；旧已保存仓库保留在范围内。 |
| 有可靠子集但覆盖不全 | 返回明确partial或unknown覆盖，允许明确选核实子集；不提供全账号“全部”保证。 |
| 外部失败且没有可靠结果 | 按既有503处理，不伪造空数组和complete。 |
| 新登录／重连／本地失效代次改变 | 旧发现及授权观察不能直接沿用；页面回读并核仍有效的选择，不能静默删改项目范围。 |

本稿不把App“Metadata读取”当必要工作能力齐备。创建Issue所需的App权限集合必须按实际准备、读取、分支／draft PR等责任逐项建立能力策略；具体权限清单与安装申请仍是前置缺口，未配清单时不能报告appCapability=allowed。实际执行再次核具体动作，不因建项放行获得任意写权。

## 5. C方案：真实配置来源及固定版本

### 5.1 来源分工（待用户决定）

| 必要输入／观察 | 推荐真实来源与管理者 | 固定与失效处理 |
| --- | --- | --- |
| 模型连接与模型参数 | 当前用户在已采用模型设置页显式保存；owner自己的供应商分组和一个明确模型。 | 保存产生不可变配置快照；modelProfile关联具体供应商／模型／SecretVersion。字段、唯一性及保存恢复由后续专用契约完成。 |
| 模型Key | 同页只写提交；服务端受控加密形成SecretVersion，默认编辑保留原版本。 | 原始Key不进项目API、来源、日志、事件或待办。新版本不自动切项目和在途Issue；不增加临时.env Key入口绕过设置。 |
| 执行配置 | 部署负责人登记真实允许环境和版本化执行profile；首批页面读取可引用记录。 | 登记需明确可用环境类型、容量约束及执行政策，不能包含任意命令／宿主挂载。登记不证明executor已运行或环境Ready。 |
| 预算／时限／额度 | 部署负责人登记明确政策与适用主体／范围；余额／占用来自本地权威账本或实际可核实的配额源。 | policy版本和适用关系可追溯；不存在权威来源时未知，不写0或无限。费用计量、预留／结算及跨操作并发额度协议另行补齐。 |
| 默认引用 | 部署负责人显式登记允许用户引用的默认映射；用户模型默认／共享不开额外UI。 | 没有登记则defaultProfileId为空；inherit固定解析当时版本或保持未解析。以后补默认不能暗改旧配置。 |
| GitHub App配置与工作观察 | 部署配置提供固定App身份／callback／权限策略版本及秘密引用；GitHub适配器取得实际安装、仓库、权限观察。 | 本地声明只说明期望，实际allowed必须有当前证据。App不足／unknown允许受限项目，阻止不满足条件的Issue。 |
| 凭据保护基础 | 部署负责人提供独立根密钥／秘密服务引用，受控服务使用；GitHub client secret、App私钥、用户token、模型Key分用途授权。 | 根密钥不与数据库备份放一起；缺解密材料或服务不可用时不能签入／解密／声明配置可用，也不自动生成替代密钥。 |

配置来源候选采用“受控导入版本化记录”，不在每次读取时把环境变量临时拼成假profile。导入的身份、参数、允许引用主体、版本／来源及操作记录须持久保存，重复导入相同身份版本不能覆盖正文；修改生成新版本，引用解析和权限检查仍由业务层处理。**导入命令／Schema和秘密存储具体产品未设计，不属于本稿可执行交付。** 这组选择的目的，是决定首批由谁提供有效记录，为后续机器契约划定范围。

独立执行配置编辑页可按首批表暂缓；真实执行profile、适用预算／额度却不能省略。Worker并发1是已有默认方向，也要有实际解析结果才能显示，null不能冒填1。未启用真实运行消费者不妨碍保存业务和后续责任，但不构成执行可用。

### 5.2 配置检查与真实测试不同

管理面checks只核当前主体可引用、固定版本可用、密钥版本存在／可用、必要参数和适用政策。不得仅凭数据库有一条profile就认定可用；需核真实来源、解密能力及已定义的条件。检查不能发起暗中的可能收费模型请求，也不证明远端当前接受Key或模型调用成功。

逐模型测试应消费用户明确选择的已保存快照及单独的原操作身份；测试费用、出站限制、有效期、明确失败与未知查询必须在Key／测试协议中补齐。本稿不新增“所有建项必须近期测试通过”的门槛，也不取消原来必要条件；测试结果是否进入某种创建政策，若后续提出须单列决定。

### 5.3 从新部署到可创建Issue的依赖顺序

1. 部署方准备真实GitHub App身份／回调／必要权限策略和独立秘密基础；完成认证契约后才能取得稳定用户及当前授权。
2. 登记实际执行profile、预算／时限政策和配额来源、允许引用范围及可选默认；没有这些记录时返回缺项或未知。
3. 用户按已采用设置准备供应商／模型／Key，等专用保存／测试契约收口。保存与测试分开，测试不自动应用。
4. 项目可先保存受限。用户显式配置提交或专用应用才固定有效版本；专用模型应用比较预览与projectRevision，并精确保留execution原引用及有效版本。
5. Issue创建按现行options和提交校验核本次仓库／会话／配置／额度；满足后按原事务保存全部业务、事件和后续待办。没有处理器如实保持内部未接入责任，不显示假preparing或ready。

各步是设计依赖，不是本次部署／运行指令。任一前置协议未闭合，就不能声称已完成全新部署到成功建项链路。

## 6. 设计验收清单与剩余交付

下表是后续实现需要验证的用例，本次未运行。

| 用例 | 可观察的合格结果 |
| --- | --- |
| 两个并发callback；已退出后旧callback迟到 | 同尝试最多一次token交换；旧尝试不重建会话／覆盖连接。 |
| 旧session的注销请求或响应晚到，新登录已经完成 | 旧请求只影响原绑定代次，响应无删除Cookie头；新session及新尝试不被旧注销撤销。 |
| 首次登录数据库提交成功但Cookie响应丢失 | session查询确认当前身份或显式新登录恢复；不推断特定尝试成功，没有自动提交项目／Issue。 |
| 原会话有效且连接已connected，新的重连响应丢失 | 仍显示本次结果待核，不能用session=200判成功；依据后续唯一认证契约查询原尝试及当前连接代次，不重换旧code。 |
| 重连时GitHub选错账号／同名或同邮箱账号 | 旧稳定身份与项目归属保持；不同账号不能冒领或合并。 |
| 刷新上游成功、响应丢失／旧进程迟到 | 不并行重复刷新旧版本；新重连代次不被旧结果覆盖，未知不写成已撤权。 |
| 上游仅安装交集、跨页改变、组织限制／限流 | coverage准确；缺席不证明无权；无可靠结果503；不漏保手选集合。 |
| 名称缓存存在但当前读权未知 | 不回传旧ID／名称；写入不借旧allow放行。 |
| 根密钥／secretVersion／execution／配额源缺失 | 项目按现行规则可受限保存，Issue必要条件不足或未知被阻止；无假默认。 |
| 默认变更后仅改项目名称；模型专用应用时execution默认已变 | 前者保留原配置；后者按专用协议精确保留原execution有效版本，失效仍受限。 |
| 业务已提交后注销／后续处理器未接入 | 原业务、幂等回执、事件、待办仍在；不丢责任、不伪造运行状态。 |

后续仍需：页面唯一认证HTTP契约及登录结果原型、完整发现批次／游标与修复入口、App逐动作权限清单、秘密首次设置／恢复产品方案、版本化执行／额度导入契约、Key／逐模型测试／精确应用协议。跨页面数据库约束与故障验收继续按原持久化设计；完整MCP、首次消息／运行准备与受限执行、Python等未完记录不删除。
