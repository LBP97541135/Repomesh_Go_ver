# 联调环境、固定组合与 mock 数据

状态：已确认产品设计；2026-09-08 根据用户对 C1—C6 的确认及 C4 修改记录。未部署或执行验证。

## C1：基线和候选组合

项目接入不要求用户选择分支，Manager 按 Issue 和已有明确要求确定目标分支，见 [J1 项目配置](project-configuration-design.md)。首次计划记录各仓目标分支的固定基线 SHA。每次验证记录完整候选组合；未改动但参与联调的仓库也固定版本，不在执行中追踪最新分支。候选或基线变化后，重新判断旧证据的适用性。

## C2：环境准备职责

各仓 Leader 提供构建、启动、依赖和迁移说明；验证负责人组织环境准备 Worker 按说明准备服务、配置和数据。未启用专用验证小组时，由 Manager 承担相应组织职责。业务仓脚本或代码有缺陷时，交回对应仓库 Team 修复，验证环境不向业务仓推送修复。

## C3：按验证 Attempt 隔离

首期为每个验证 Attempt 提供独立服务、配置及测试数据，避免不同执行互相污染。共享基础镜像和只读缓存可作为实现优化，不改变独立代码副本和执行归属。

## C4：Leader 提供 mock 数据

- 测试使用 mock 数据，由 Leader 提供，并给出对应的生成、装载或使用说明。
- 各仓 Leader 提供与其业务及接口契约相符的数据；验证侧组织准备和执行，记录数据版本、初始化说明及测试账号的可见范围。
- 支付筛选的数据应能区分适用验收规则中的业务状态，并能重复准备。
- 本项确认数据来源和职责。哪些外部依赖使用 mock、哪些被测链路实际运行，需要在具体检查范围和环境清单中表达，不能因采用 mock 数据就自动宣称真实跨仓链路已通过。
- 缺失业务解释仍按 ADR-0004 的模式规则处理，Leader 提供数据不替代业务解释的决定记录。

## C5：核对实际运行对象

验证前核对实际运行源码版本、构建产物、配置和数据记录，形成可追溯环境清单。版本或前提不匹配时，不能用该次运行证明目标组合通过。

## C6：失败、重建与清理

先保存日志和失败现场，再按固定清单重建。配置或数据变化产生新记录，候选变化产生新组合。验证完成并保存证据后释放运行资源；需要复查时按记录重建。

上述清理针对联调环境。生产部署和业务数据恢复按已确认 [CS12](changeset-design.md)处理：首期由相应有权限的人执行，RepoMesh 记录方案、对象、结果和证据。

## 场景

```text
各仓 Leader：固定候选 + 运行说明 + mock 数据
                         |
验证侧：准备本次 Attempt 环境
                         |
核对实际 F1 + B1、配置、数据与账号范围
                         |
执行检查 -> 保存证据
                         |
失败：保留现场后重建 / 完成：保存证据后释放资源
```

环境清单字段、数据打包格式、实际版本探测、依赖 mock 的标记和重建机制仍需技术细化。相关检查分类、必检门槛及证据要求见[验证节点设计](verification-node-design.md)。
