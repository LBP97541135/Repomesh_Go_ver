# ChangeSet 产品与架构设计

用户已全部采用 CS1—CS14。本文件记录已确认规则，架构边界见 [ADR-0008](../adr/0008-changeset-attribution-and-history.md)。当前未实施或运行验收；逻辑结构与字段示意见[结构说明](changeset-structure.md)。Issue 创建及其主 ChangeSet 回执以[创建契约](issue-page-create-api-contract.md)为准，其余 ChangeSet 明细字段和具体存储／API 契约继续细化。

## 基本归属与记录

- Issue 指 RepoMesh 内部的一条统一需求事项，可以涉及一个或多个仓库，由项目 Manager 统筹。GitHub issue 是外部来源或跟踪记录。
- 一条 RepoMesh Issue 默认一个主 ChangeSet；明确创建时按现行契约与必要会话、来源、幂等结果和待办原子登记，允许候选、组合和 PR 暂时为空。首次会话消息提交后或页面建项提交后异步准备／恢复实例，见 [ADR-0018 现行补充](../adr/0018-provision-instance-after-first-draft.md)；会话可先于 Issue 存在并关联多项，不因会话变化重建 ChangeSet。
- 本轮修复保留同一 ChangeSet，串联仓库、Candidate、Delivery Combination、计划与验收依据、证据、PR 和交付历史。
- Candidate 正式提交即收录，关联产物版本及来源 Task／Attempt；未被接受也保留检查结果和原因，后续候选不覆盖旧记录。正式组合选择与诊断使用的区别见 CS3。
- Agent 先读带来源引用的摘要，再按需查询关联记录和原始证据。摘要结论可定位来源，缺失证据如实显示。
- 已提交、被接受、组合通过、可审查、已合并及 issue 完成分别表达；ChangeSet 不增加权限，也不替代计划获准与生效的控制。

## CS1—CS14 已确认决定

| 编号 | 主题 | 已确认规则 |
| --- | --- | --- |
| CS1 | RepoMesh Issue 与 GitHub issue 怎样关联 | 一条 RepoMesh Issue 可关联零到多条 GitHub issue，标明来源或跟踪关系；重复导入同一来源先查已有映射，不自动合并需求。首期先支持关联，创建、评论、状态同步及关闭外部 issue 不默认启用，权限与接入单独确定。 |
| CS2 | 交付完成后新增工作、重开或拆分怎样归属 | 本轮未完成的修复继续原 ChangeSet。完成后新增范围建立关联的新 RepoMesh Issue 和 ChangeSet；误标完成可追加更正并恢复处理。跨 issue 记录依赖，首期不引入自动合并或嵌套 ChangeSet。 |
| CS3 | 哪些 Candidate 可以选入正式交付组合 | 业务仓候选经 Leader 内部初审接受后成为可选输入，Manager 按该次检查的范围、前提和有效计划选定固定组合；未修改的参与仓库固定基线。未接受候选可用于明确的诊断，但不冒充已接受候选；新候选到来不替换已启动验证的组合。 |
| CS4 | 代码、判据或环境变化时，究竟新增什么记录 | 任一仓库版本变化建立新 Delivery Combination。代码组合不变，但验收依据、Skill、配置或 mock 数据变化时，新增绑定相应上下文的验证记录并重新判断证据；单纯补充证据不强制新建组合，历史记录保留。 |
| CS5 | Candidate、分支、PR 和真实 commit 怎样关联 | 使用固定 commit 和实际产物关联，分支名或 PR 编号不能单独代表被验证版本。沿用 E 的同仓持续更新 PR；rebase、外部追加提交等导致实际 head 变化时重新匹配候选及证据。PR 无法继续复用时记录替代 PR 与旧 PR 的关系，不抹去旧记录。 |
| CS6 | ChangeSet 的总体状态怎样表达 | 分别记录执行进展、验证结论和交付进展，摘要可同时显示“执行已结束、验证未通过、部分仓库已合并”，并列出阻塞原因。整体结论根据相关记录汇总，不让一个笼统成功状态掩盖未完成部分。 |
| CS7 | 谁记录事实，谁作出判断，怎样更正 | 执行 Agent 提交产物、陈述及证据，沿用 Leader／验证负责人／Manager 的检查和协调职责。RepoMesh 保存来源、操作者、时间及可核查的执行结果，外部状态以实际观察为依据；判断和更正追加记录，摘要引用来源，不覆盖原始历史或把建议写成已发生事实。 |
| CS8 | 幂等标识、并发更新和重启恢复怎样处理 | 本地 Issue 与主 ChangeSet 作为一次原子登记。每个逻辑操作有独立标识，绑定目标和输入摘要；同标识不同输入拒绝。并发更新校验目标版本，对同一目标的冲突操作串行处理；重启和超时先核查本地及远端结果再恢复，不承诺跨系统只执行一次。 |
| CS9 | 什么时候算本次变更完成 | 约定交付物和适用验收完成，必做事项已处理；涉及代码时，所有必需 PR 已由人合并，最终实际组合具有适用的有效证据。无需修改的仓库不制造 PR；无代码变更按对应交付约定判断。代码交付与部署上线分别记录，关闭 GitHub issue 不是必需完成依据。 |
| CS10 | 跨仓 PR 按什么顺序合并 | 按兼容性选顺序，由 Manager 给出依据，人执行合并。支付筛选若 F0＋B1 已验证可用，可先 backend 再 frontend；若其他顺序更安全则选其他顺序。不存在安全过渡组合时，先形成兼容改造或协调发布方案，不声称多仓 Git 合并具有原子性。 |
| CS11 | 基线变化或一仓已合并、另一仓受阻怎么办 | 记录各仓真实状态，明确显示部分合并。将实际已合并版本作为后续组合输入，重新判断受影响证据；在已有授权和计划内继续处理剩余工作，不自动撤销已成功部分。出现需要恢复的影响时，转入明确的恢复处理，不能把部分成功标成整体完成。 |
| CS12 | 关闭 PR、撤销代码、恢复部署和恢复数据怎样区分 | 未合并 PR 的取消记录在原 ChangeSet；已合并代码的撤销由人发起关联恢复 Issue／ChangeSet，相关仓 Team 产出撤销 PR，人合并。首期部署与数据恢复由相应有权限的人执行，RepoMesh 记录方案、对象、结果和证据。恢复关联原变更，不删除原历史；这属于交付处理，不给 YOLO 插入逐项执行审批。 |
| CS13 | Agent 可以查哪些 ChangeSet，怎样定位 | 默认读取当前 ChangeSet；允许在既有有效权限内，按 RepoMesh Issue、仓库、commit、PR 查找相关历史，再按需读取明细。读取结果标明所属组合、记录时间和来源；跨项目查询首期不默认开放，不因有关联就放大查看权限。 |
| CS14 | 哪些历史和证据保留，哪些可以清理 | 项目存续期保留归属、版本关联、决定和操作结果；必要验收证据随交付档案保存，临时运行材料按项目清理策略处理。明确标注附件已归档、过期或缺失；历史结论保留，但缺失正文不冒充当前仍可复核的证据。具体容量和保留期限作为实现配置细化。 |

## 执行和交付职责

Manager 始终承担 RepoMesh Issue 的总协调职责，对人统一沟通。各仓 Leader 内部初审、验证侧执行与复核、仓库 Team 修复等职责继续按现行 ADR 执行。RepoMesh 保存真实来源与操作记录，并实际控制授权、容量、计划应用和任务启动。

代码交付、人工审查／合并与生产部署分别表达。恢复流程不把 YOLO 改为等待逐项同意的运行模式；YOLO 仍不能扩大授权、预算上限或放宽既定验收条件。外部 GitHub issue 关联也不等于默认授予 Issues API 写权限。

## 尚需技术细化

- 逻辑结构的精确字段、引用格式、唯一约束、索引、分页及 API／工具契约。
- 原子登记、目标版本校验、冲突串行化、远端核查与重启恢复的具体实现。
- 状态枚举及组合覆盖的计算细节、合并前后 SHA 与证据适用性的可执行检查。
- 查询权限、证据存储与归档、附件可用性、容量和保留期限。
- 与 Graph 插件、AgentTeams 任务及运行记录的适配与运行验证。

上述是实现细化，不重新将 CS1—CS14 的产品方向列为待决定。Skill 工程整体暂缓、当前 YOLO 与后续审批、项目配置及页面／接口各自的采用范围见 [HANDOFF](HANDOFF.md)。F／G 的合并和恢复议题以本次 CS9—CS12 的确认内容为准，不整体恢复旧建议。
