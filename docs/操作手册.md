# RepoMesh 操作手册

> 面向部署者与运维者。2026-09-20 编写，含当天两次线上事故的处置办法。

## 一、系统由什么组成

| 组件 | 作用 | 部署位置 |
|---|---|---|
| `repomesh-web` | HTTP 面：浏览器控制台、项目/issue/审核台/仓库/模型/技能/决策链 | 服务器 systemd |
| `repomesh-coordinator` | 后台大脑：DAG 调度、规划派发、自动托管（发现链）、收产物 | 服务器 systemd |
| `repomesh-host-executor` | 唯一动主机的手：起 agent 进程、铸 installation token、交付记账 | 服务器 systemd |
| PostgreSQL | 全部业务事实（`repomesh_*` 多个 schema） | 服务器本机 |
| nginx | TLS + 反代到 `127.0.0.1:8080` | 服务器本机 |
| AgentTeams 控制面 | 智能体 runtime（embedded kube 模式），队伍/worker 都是**真容器** | docker 容器 |

**一句话**：web 只读写事实，coordinator 决定"下一步派谁"，host-executor 真的去跑。
三者都不缓存业务状态 —— 重启后按库里的事实继续。

## 二、部署与更新

### 2.1 正常更新（推荐）

```bash
# 本地
git push origin main
```

推 `main` 即触发服务器自动部署：拉取 → `go build` 三个二进制 → 重启三个 unit。
**部署期间约 6 秒 502 属正常。**

### 2.2 手动部署（自动部署失败时）

```bash
ssh -i repomesh.pem root@8.210.190.41
cd /opt/repomesh/src && git pull
export PATH=/usr/local/go/bin:$PATH
go build -o /opt/repomesh/bin/repomesh-web        ./cmd/repomesh-web
go build -o /opt/repomesh/bin/repomesh-coordinator ./cmd/repomesh-coordinator
go build -o /opt/repomesh/bin/repomesh-host-executor ./cmd/repomesh-host-executor
systemctl restart repomesh-web repomesh-coordinator repomesh-host-executor
curl -s https://crazykitties.cn/healthz      # 看 version 是否是刚编的那个 commit
```

### 2.3 数据库迁移

```bash
/opt/repomesh/bin/repomesh-web db migrate     # 只做结构变更，可重复执行
```

> **编号规则（踩过坑）**：迁移文件是 `internal/database/migrations/NNNN_名字.sql`，
> **编号必须全局唯一**。本仓与另一个 agent 并行开发，出现过两边都写 `0053_` 的情况 ——
> 重号会让 `db migrate` 失败，**新包起不来、部署静默失败**（服务还跑着旧二进制）。
> 新迁移一律取 `origin/main` 里最大号 +1。

## 三、日常运维

```bash
# 三进程状态
systemctl is-active repomesh-web repomesh-coordinator repomesh-host-executor

# 看日志（按域过滤，别裸 tail —— tick 行会把有用信息淹掉）
journalctl -u repomesh-web         --since '10 min ago' | grep -v 'pipeline: tick' | tail -30
journalctl -u repomesh-coordinator --since '10 min ago' | grep -v 'pipeline: tick' | tail -30
journalctl -u repomesh-host-executor --since '10 min ago' | tail -30

# 健康
curl -s https://crazykitties.cn/healthz        # {"status":"scaffold","version":"<commit>"}

# 库
psql 'postgres://repomesh:***@127.0.0.1:5432/repomesh?sslmode=disable'
```

**看什么指标算正常**：

| 现象 | 含义 |
|---|---|
| web 日志里 `project request failed ... status=404 code=XXX_NOT_FOUND` 持续刷 | 某个读面把"正常空态"当错误回 —— 见 §5.3 |
| coordinator 里 `autohost discovery step deferred` 反复出现同一条 issue | 那条 issue 卡住了，看 reason |
| host-executor 里 `交付记账跳过非任务引用` | 正常（规划 run 不属于任何任务） |
| PG 日志 `invalid input syntax for type uuid` | 有人把非 uuid 当 uuid 用 |

## 四、事故处置

### 4.1 【真实事故】AgentTeams 被灌爆 → 全站卡死、登录不上

**症状**：`healthz` 超时、SSH 卡在 `banner exchange`、控制面 `:8090` 返回 502、
`load average` 冲到 100+（而单进程 CPU% 都不高 = 大量进程在抢/等）。

**根因**：某次"接入即建队"对**几十个历史仓库**逐个建队，每队 2 个 worker，
每个 worker 是一个真容器 → 42 支队 / 124+ 容器挤在一台机器上。
更糟的是建队失败时**远端可能已建好、本地没落库**，重试不断堆出孤儿队。

**止血（按顺序）**：

```bash
# ① 先停掉"还在建队"的源头
systemctl stop repomesh-web

# ② 再停掉所有 AT worker 容器（load 的真正来源）
docker ps --format '{{.Names}}' | grep agentteams-worker | xargs -r docker stop

# ③ 用控制面 API 删队（比删容器更彻底）
T=$(grep -i '^AGENTTEAMS_CONTROLLER_TOKEN=' /etc/repomesh/env | cut -d= -f2-)
curl -s -H "Authorization: Bearer $T" http://172.18.0.2:8090/api/v1/teams \
  | python3 -c 'import sys,json; print(" ".join(t["name"] for t in json.load(sys.stdin)["teams"]))' \
  | tr ' ' '\n' | while read n; do
      curl -s -o /dev/null -w "%{http_code} $n\n" -X DELETE \
        -H "Authorization: Bearer $T" "http://172.18.0.2:8090/api/v1/teams/$n"
    done

# ④ 清本地台账（下次按新规则重建）
psql "$DB" -c "DELETE FROM public.repository_teams"

# ⑤ 起回来
systemctl start repomesh-web
```

**根治**（已落代码）：建队**只发生在"逐仓确认接入"那一步**（一次动作恰好新增 1 个仓），
批量接入 / 扫描挂载 / 新建项目都不建队；那条"每 5 分钟扫掠补队"的循环**已删除**。

### 4.2 【真实事故】迁移编号撞车 → 部署静默失败

**症状**：push 了、GitHub 上有 commit，但 `healthz` 的 version 一直是旧的。

**根因**：两个 agent 都写了 `0053_*.sql`。

**处置**：`ls internal/database/migrations | sort | uniq -w4 -d` 查重号 → 把后写的改成
下一个空号 → push。**部署失败不会自动告警，必须每次核 `healthz` 的 version。**

## 五、验收（浏览器全链路）

> 演示要能录视频：**对话流、worker 日志、产出内容都要在界面上看得见**，不是只看后端跑通。

1. **建 issue**：`#/issues/new` → 填需求 →（可选）勾仓库 → 选「自动托管」或「人工参与」
   → 发送。**仓库可以不选**：没点名时由 agent 从项目全部仓库里发现。
2. **看发现链**：issue 详情左树 ①需求分析 → ②候选评分 → ③分档 → ④计划 → ⑤物化。
   每步都该看到"谁产的、技能是什么、结论是什么"。
3. **看对话流**：右栏消息流要有流水线自己说的话（执行者跑完/测试结论/规格变更请求）。
4. **看 worker 日志**：任务卡里展开 agent 的 stdout/stderr（`agent-stdout.log`）。
5. **看产出**：交付清单（各仓提交/分支/PR/迁移/数据基线/测试证据），失败要能定位到
   **哪个仓库、哪个阶段**。
6. **看门**：`人工参与`模式下 ③ 分档审批与 ⑤ 物化确认**必须等人**；
   `自动托管`模式由协调器代行（日志里能看到 `autohost: approving tiers` / `materializing tasks`）。

**验收清单（每条都要亲眼看到）**：issue 列表 / 新建 / 处理 / 审核台 / 仓库 / 技能 /
历史决策 / 模型 / 观测 / 设置，全部无 5xx、无"服务端暂时不可用"。

## 六、环境变量与开关

| 变量 | 作用 |
|---|---|
| `REPOMESH_DATABASE_URL` | 主库 |
| `AGENTTEAMS_CONTROLLER_URL` / `_TOKEN` | AT 控制面（未配则相关路由如实回 503） |
| `MATRIX_HOMESERVER_URL` | Matrix 消息面探针（设置页"选检"用） |
| `REPOMESH_REPOSITORY_TEAM_WORKERS` | 每支仓库队几名执行者，默认 1（越界退回默认） |
| `REPOMESH_POLAR_BRANCH_DSN` / `_BASELINE_DB` / `_CLUSTER_ID` | PolarDB 数据库分支 |

配置文件在 `/etc/repomesh/env`（**不要**用 `systemctl show -p Environment` 看，看不到）。

## 七、已知限制（如实记录，不粉饰）

1. **建队不再自动补历史仓库**：55 个已接入仓库里只有你逐仓确认过的才有队。
2. **控制面容量有限**：embedded 模式一台机器，队伍数量要自己控（一次别超 ~5 支）。
3. **`/api/plans/{id}/versions/{n}` 未实现**：前端已不再调用（Python 时代接口）。
4. **部分读面仍把空态当 404**（topology / policy-draft）：会刷日志，不影响功能。
5. **历史"空候选"issue 会卡在审批**：修了池子口径后新 issue 不受影响；
   老 issue 需要 `ReopenEmptyCandidates` 重跑 ②（已实现，待接线验证）。
